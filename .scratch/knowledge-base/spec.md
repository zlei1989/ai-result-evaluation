# VitePress 知识库：拆解 docs 档案为五域知识文章

Status: resolved

## Problem Statement

仓库的知识以两种形态堆积在 `docs/`：三家厂商 FAQ 与 `powershell.md` / `playwright-mcp.md` 是持续追加的活文档；`docs/superpowers/` 下的 specs / plans / notes 是 57 份、约 3.2 万行的冻结档案，按时间戳而非领域组织。对人，按问题找知识像考古——想配一家新厂商，答案散落在一份 spec、三份 plan、十几份 note 里；对 AI（仓内 coding agent），没有主题索引与稳定导航，每次都要全量扫描。两者都缺一个「即 AI 读、又人读」的知识库。

## Solution

在 `docs/` 原位搭 VitePress 站点，把冻结档案全量提炼成按五域组织的知识文章：协议规范、功能说明、架构设计、FAQ（两层）、规约守卫。文章自含全部现时结论（抽象纳入、可倒推原文内容），正文不反链冻结档案；活文档原文编入站点、只新增目录层索引。知识库建成后冻结档案整体退役删除，知识文章成为唯一真源，并以活文档纪律与仓库共同演化。AI 侧入口为 AGENTS.md 指针 + `llms.txt` 清单 + 内容守卫。

遵循 ADR `docs/adr/0001-retire-frozen-archives-single-source.md`（终结过程档案形态、单一真源）与 GLOSSARY.md 的术语（冻结档案 / 活文档 / 知识文章 / 关账回写 / AI 读）。

## User Stories

**站点与导航**

1. 作为开发者，我想 `pnpm docs:dev` 起一个本地站点，以便用浏览器按主题浏览全部知识。
2. 作为开发者，我想侧边栏按五域组织（协议规范 / 功能说明 / 架构设计 / FAQ / 规约守卫），以便按问题域而不是文件名找知识。
3. 作为开发者，我想站点构建产物可部署但默认只在本地/内网消费，以便不承担公网内容审查（FAQ 与档案含厂商运行期细节与内部判据）。
4. 作为开发者，我想首页给出知识库地图与各域一句话定位，以便首次进入就知道去哪找什么。

**AI 读**

5. 作为仓内 coding agent，我想 AGENTS.md 有一节「知识库」指针指向五域结构与主题索引，以便接任务时按指针直达对应文章。
6. 作为外部 AI 工具，我想构建期生成 `llms.txt`（全站文章清单 + 一句话摘要），以便经 HTTP 抓取消费知识库。
7. 作为仓内 coding agent，我想文章标题与报错原文都可 grep，以便拿报错搜索即命中（FAQ 故障索引按现象原文列条目）。
8. 作为 AI 读者，我想每篇文章按固定六节骨架组织，以便预期每节内容、稳定提取。

**协议规范域**

9. 作为适配层维护者，我想读《Provider 抽象与 run 入口》了解 `agentProvider.run` 唯一入口、metadata 能力查询与权限档，以便不绕开抽象层直连厂商。
10. 作为适配层维护者，我想读《消息规范》了解现行 v3 口径与已真机验证的事件形状，以便知道每条消息字段的权威定义。
11. 作为适配层维护者，我想读《事件流》了解行级事件流与 SSE 双流的分工，以便消费执行过程而不误解两条流。
12. 作为适配层维护者，我想读《进程生命周期》了解 spawn 到整棵回收的口径与清理失败处置，以便不再踩 EPERM 类坑。
13. 作为适配层维护者，我想读《新增 SDK 接入流程》按七步清单与判据接入新厂商，以便不靠试错。
14. 作为接 Claude Code 的开发者，我想读《Claude Code 接入》知道 skills 注入、MCP、子会话用量、思考块的具体技术细节，以便落地时一次到位。
15. 作为接 Codex 的开发者，我想读《Codex 接入》知道 app-server 协议、`wire_api: 'responses'` 约束、结构化输出与 reasoning 缺失的处置，以便避开已知坑。
16. 作为接 DSH 的开发者，我想读《DSH 接入》知道 pi-ai 双协议路由、逐消息用量、会话过滤，以便正确配置供应商。
17. 作为评测平台使用者，我想读《三家横向对比》对比内置工具、MCP 接法、skill 注入差异，以便选型与写跨厂商代码。

**架构设计域**

**FAQ 域**

**规约守卫域**

37. 作为守卫作者，我想读《变异验证》了解「没见过失败的守卫不算守卫」，以便给回归守卫做变异验证。

**维护与演化**

39. 作为知识库维护者，我想知识文章按活文档纪律维护、关账时回写对应文章，以便知识库不落地即过期。
40. 作为知识库维护者，我想有内容守卫（自含、骨架、标题、llms.txt 同步、单一真源），以便违规文章进不了门禁。
41. 作为未来维护者，我想 ADR 0001 解释为何仓库没有过程档案，以便不再提议重建。

## Implementation Decisions

- **站点形态**：VitePress 站点内嵌 `docs/`（srcDir 即 `docs/`，配置位于 `docs/.vitepress/`）。`docs/` 保持 markdown 真源、原位不动；不建 workspace 包、不进依赖方向表（`docs/` 不是 `@aieval/*` 包，boundary 测试只逐条比对表内 8 包清单）。根 eslint 的基础规则天然覆盖 `docs/.vitepress/` 的 TS 文件，工具链文件须过 `pnpm lint` / `pnpm typecheck`。本地/内网口径，不上公网。
- **五域 25 篇知识文章 + 2 目录层 + 5 活文档编入**：协议规范 9 篇；功能说明 8 篇 + 《功能总览》目录层；架构设计 4 篇；FAQ《故障索引》目录层（方案层为三份 FAQ 原文编入，单一真源、追加流不变）；规约守卫 4 篇新文章——「PowerShell 安全」「Playwright MCP」两页为活文档**原文编入**（侧边栏入域，不新写、不重写）。抽屉不单独成篇，按使用环境并入主功能文章。
- **知识文章自含**：抽象纳入全部现时结论，正文不出现指向冻结档案的链接；活文档内部互链与 FAQ 条目链接允许。结构只跟领域逻辑（CRUD、操作拆分），不迁就历史文档边界；历史文档仅作提炼取材，取材来源只记录在实施票据内部，不进正文。
- **文章骨架六节**：①一句话定位 ②页面形态与交互 ③数据与契约 ④状态机/时序（协议规范域为 wire 形态与事件）⑤已知边界与取舍 ⑥相关链接（活文档互链）。标题规范：无编号前缀、≤10 字、领域词、不用内部代号。
- **活文档编入**：三份厂商 FAQ、`powershell.md`、`playwright-mcp.md` 原文渲染进站点，不重写不复制；站点目录层只新增索引页。
- **AGENTS.md 更新**：新增「知识库」一节（五域结构与入口指针）；新增「关账回写」纪律（关账时同步回写对应知识文章，不再新增过程档案）；修正指向将被删除的冻结档案的引用（P2 断链修复时完成全部修正）。
- **冻结档案退役（P2）**：P0/P1 期间作为提炼原料保留原位；P2 删除 `docs/superpowers/`，同步修复约 20 处源码注释直链、AGENTS.md 引用、eslint 报错文案中的档案路径；档案形态终结，此后不再新增。
- **llms.txt**：构建期生成全站页面清单（新写页面与编入活文档）+ 一句话摘要，随每次 `docs:build` 更新；同步守卫按「清单与已发布页面集合一致」比对，漏收一篇是静默漏测。
- **分期**：P0 = 站点骨架 + 五域导航 + llms.txt + AGENTS.md 指针 + 《功能总览》+《故障索引》+ 厂商接入三篇（引用密度最高，先验结构）；P1 = 其余 26 篇全量提炼（按域可并行）；P2 = 冻结档案退役 + 断链修复 + AGENTS.md 工作流改造。

## Testing Decisions

- **好测试只测外部行为**：守卫测试只读磁盘文件内容断言不变量，不 import 生成脚本、不断言其内部结构；解析失败必须响亮报错而非静默通过（「漏收一篇文章是静默漏测」）。
- **三道缝**：
  1. **构建缝（最高缝）**：`pnpm docs:build` 退出 0。VitePress 把内部死链当构建错误，一道缝同时验收配置合法、导航完整、互链无死链、llms.txt 生成。
  2. **内容守卫缝（vitest node 环境，`// @vitest-environment node`）**：`docs/` 自带 vitest 配置，根 `vitest.config.ts` 的 projects glob 增加一行以收集（新增一个 project；改收集方式后按仓规核对用例总数）。守卫清单：自含守卫（知识文章正文不得反链冻结档案，P0 起生效）、骨架守卫（六节齐全）、标题守卫（无编号前缀、长度上限、禁内部代号）、llms.txt 同步守卫（清单与已发布文章集合一致）、单一真源守卫（FAQ/powershell/playwright 无仓内第二份副本）、断链守卫（全仓冻结档案引用计数，P2 放行判据为 0）。
  3. **既有缝回归**：boundaries 测试对 AGENTS.md 依赖表的逐字解析不得被 AGENTS.md 编辑碰坏；`pnpm lint` / `pnpm typecheck` 保持绿。
- **先例**：守卫测试风格仿 `package-dependency-boundaries.test.ts`（读文件、解析失败抛错、真源唯一不复制清单）。冒烟按仓规四要素（范围清单、操作路径、证据、未覆盖项），`pnpm docs:dev` 起真站、按真实用户路径浏览与搜索。
- **变异验证**：每个新增内容守卫按仓规做变异验证——人为制造该守卫要拦的缺陷（如正文塞一条冻结档案链接）、确认守卫红、还原、核对文件哈希。没见过失败的守卫不算守卫。
- **P2 退役门禁**：删除冻结档案前，断链守卫的引用计数必须为 0（约 20 处源码注释 + AGENTS.md + eslint 文案全部修复后），才允许执行删除。

## Out of Scope

- 公网部署与内容审查（构建产物可部署，但不做面向公网的逐篇脱敏审查）。
- 全文搜索（VitePress 本地搜索或外部引擎接入）。
- 站点视觉定制（主题定制、品牌化、自定义组件）——用默认主题的配置能力（nav/sidebar）即可。
- docs 工具链之外的任何产品代码改动（P2 断链修复仅改注释与文档，不改运行时逻辑）。
- 冻结档案的逐篇翻译或摘要外发。
- `packages/server/agents/README.md` 等包内 README 的知识库化（它们已是良好的活文档）。

## Further Notes

- 遵循 ADR 0001：本 spec 落地的知识库建成（P2 收口）后，仓库不再有过程档案形态；本文件自身按关账回写纪律熔炼进知识文章后，tracker 文件按 `.scratch/` 约定处置。
- FAQ 目录层的「可 grep」判据：现象标题照抄报错原文（含报错码与英文原句），与三份 FAQ 的既有纪律一致（「同一现象只留一条」「改写自己的话就搜不到了」）。
- 提炼 P1 文章时，若发现冻结档案之间存在相互矛盾的事实，以「现时结论」为准并标注该冲突于文章「已知边界与取舍」节；两份档案都过期的，按 git 时间序以晚者为准。
- VitePress 默认主题的 sidebar/nav 需要显式列出 29+2 个页面；清单变更时须同步 llms.txt（同步守卫会拦漏收）。
