# ai-result-evaluation —— AI 生成代码评测工具

固定同一道题，并固定同一起点，让每个候选（`模型 × 智能体`）在**隔离的工作区**里各自独立完成一遍，
再用**同一把尺子**打分，最后并排比较。

解决的问题：比较不同模型与智能体写代码的能力，目前只能靠零散的对话记录和主观印象，
缺少可复现、可横向对比的依据。

## 评测口径

| 项 | 值 |
|----|----|
| 起点 | 用例固定本地仓库加 commit 这一对；每个候选行从同一个 commit 独立克隆并建自己的 `test/{rowId}` 分支 |
| 考题 | 用例里的考题提示词，交给智能体在工作目录里自行完成 |
| 评分 | **默认走纯文本 API**：评分标准项表格 + 代码改动交给评分模型，不入仓库、不跑 agent；也可按轮开启「使用智能体评分」，由评分智能体在**该行工作区里**打分（见使用手册「③ 建评测」） |
| 得分 | 逐项**二元判定**（达成 / 未达成，没有部分分）+ 总分（= 达成项权重之和）+ 每项理由 + 一句话总评 |
| 可比性 | 候选行的工作区、分支全部隔离；评分的输入（diff 上限）与尺子（**评分表快照 + 评分模型 + 评分通路**）可追溯到每一行 |

评分口径写在**用例自己**的评分表里（组 → 评分项：ID / 目标 / 权重），每个候选行按同一张表逐项判定
（达成即拿到该项全部权重，未达成 0 分）。
评分**默认**走纯文本 API 而非 agent 会话：成本低、快、完全可复现；代价是看不到测试运行结果，只能凭代码本身判断。
要评「塞不进一次请求」的大改动，可以按轮开启「使用智能体评分」，改由评分智能体在该行工作区里自行查看代码
（见使用手册「③ 建评测」）；代价是它可能改动工作区，那条 `WARN` 与处置见「排障」。

## 快速开始

前置：Node.js ≥ 20、[pnpm](https://pnpm.io)（corepack）、系统 git CLI。

```bash
pnpm install      # 仅允许 pnpm（preinstall 强制）
pnpm dev          # 开发服务器 http://localhost:3083
pnpm test         # vitest 全量测试
pnpm typecheck    # 全链类型检查
pnpm lint         # ESLint 全量检查
pnpm build        # 生产构建
```

单包开发：`pnpm --filter @aieval/<包名> <脚本>`。
起服务后到 `/settings` 配一个模型供应商（名称 / 协议类型 / API 地址 / API 密钥）与默认评分模型；
配置落在 `~/.aieval/config.json`（可用 `AIEVAL_CONFIG_DIR` 覆盖）。

## 使用手册

这一节是**从零到出分**的操作路径：装什么、在哪配、怎么建用例与评测、产物落在哪、出错怎么办。
名词（路由、错误码、界面文案）都对着实现核过；界面位置以本机实测为准。

### ① 配置：供应商 / 评分 / 工作区

配置入口是 `/settings`，四个 Tab：**界面主题** / **模型供应商** / **评分配置** / **工作区**。
配置整体落在 `~/.aieval/config.json`（可用 `AIEVAL_CONFIG_DIR` 指向别处）。

**模型供应商**（Tab「模型供应商」→「添加供应商」）：弹窗里填 名称 / 协议类型 / API 地址 / API 密钥。
保存后表格按 名称 / 协议类型 / API 地址 / 模型数 / 操作 五列展示，密钥只显示掩码
（格式为前 3 后 4，例如 `PRO******AGED`），HTTP 出口里没有明文字段。

**模型清单有它自己的对话框**（每行操作列的「模型」按钮，排在「编辑」之前）：
拉取模型、手工增删、逐条设置窗口与输出上限都在那里；「编辑」弹窗只剩四个接线字段，
里面有一条 Alert 指路。清单维护是高频动作、改接线是低频动作，两者不再挤在一个弹窗里。

协议类型决定这个供应商的模型**能喂给哪些智能体**：

| 协议类型 | 能喂给 |
|---|---|
| OpenAI 兼容（`openai`） | Codex |
| Anthropic 兼容（`anthropic`） | Claude Code、DSH（DeepSeek Harness） |

于是「API 地址」要按协议填到不同的根：OpenAI 兼容填到 `/v1`（或网关要求的 chat-completions 根），
Anthropic 兼容填到 `/anthropic` 一类的 Messages 根——服务端只去掉结尾多余的斜杠，不猜路径。

**模型清单要手工维护的两种情形**：

- 上游连 OpenAI 风格的清单接口都没有（`{地址}/models`、`{地址}/v1/models`、站点根的 `/models` 与 `/v1/models` 都 404）——「拉取模型」会给出**点名试过的每一条路径**的可见原因，模型名只能手工添加；
- 新建供应商时还没有 id（表格里也还没有这一行），弹窗只给一条 Alert 说明「保存后可维护模型清单」——保存后点这一行的「模型」按钮即可拉取或手工增删。

两种协议都能点「拉取模型」自动拉取，**协议不参与判定**，按地址形态依次试四条候选：
`{地址}/models` → `{地址}/v1/models`（地址已以 `/v1` 结尾时跳过这条）→ 站点根的 `/models` → 站点根的 `/v1/models`，
**只在 404 时**换下一条（401/限流/5xx 不回退——那些说明路径是通的）。
于是填到 `/v1`、填到网关根、填到 `/anthropic` 一类 Messages 根、填到 `/api/v1` 这类带前缀的地址都能拉到。
结果是**合并而不是覆盖**：手工加的条目（来源标签为「手工维护」）不会被拉取结果冲掉。

**评分配置**（Tab「评分配置」）：

- 默认评分模型：按供应商分组的下拉，候选池覆盖两种协议（文本 API 通路不经过智能体，因此不做协议过滤）；
- 默认评分智能体：Claude Code / Codex / DeepSeek Harness **三选一，可清空**（清空 = 未配置）。
  只在打开「使用智能体评分」的轮次里起作用，决定由**哪家 CLI**去驱动「默认评分模型」那一对。
  它与默认评分模型**协议必须匹配**——智能体驱动不了另一种协议的模型：**Codex 只能驱动 OpenAI 兼容的模型，
  Claude Code 与 DSH 只能驱动 Anthropic 兼容的模型**。不匹配的候选在该下拉里**禁用**，标签写成
  「<智能体名>（与当前默认评分模型协议不匹配）」；已存的值事后变得不匹配时，卡片上方出**红色 Alert**
  点名智能体、它接受的协议与当前模型所属的协议。**保存不被阻止**：服务端不拒收「协议不匹配」这一对——
  两个下拉可以按任意顺序填，填一半就报错会让人存不下中间状态；真正的拦截在**创建评测**与**评分**两处。
  兼容性判据取自「当前默认评分模型所属的**供应商**协议」，所以只在**取不到协议**时不生效、这一格照常可选：
  默认评分模型**未配置**，或它指向的**供应商已被删除**（协议跟着一起没了）。**只是模型被删**（供应商还在）
  时协议仍然已知 ⇒ 判据照常生效，不匹配的候选照样禁用。这一格的可选性与「模型是否悬空」无关。
- 输出契约（只读）：评分模型只输出一个 JSON——对评分标准项里**每一项**给出「达成 / 未达成 + 一句理由」，不给总分；
- 检测 diff 上限：默认 **256 KB**（`diffBudgetBytes = 262144`）。

> 这里**没有**「单行超时」这一格（2026-09-28 用户口径）：执行与评分都**不限时间**，一行只会因为
> 「跑完 / 失败 / 用户点终止」结束。旧 `config.json` 里遗留的 `rowTimeoutMs` 由 zod 丢弃，无需迁移。

**工作区**（Tab「工作区」）：工作区根目录默认 `~/.runs`，服务端在读取时把 `~` 展开成真实家目录。
点「校验并保存」时服务端会**真写一次探针文件再删掉**（只检查父目录存在不够：磁盘满、无权限、路径过长
都只在真正写入时才失败），失败会给出可区分的具体原因。校验通过或失败都会保留输入框里的值，
失败时落盘值不变。本机实测：正例回绿并给出可用路径，负例（同名文件占位）回 `NOT_WRITABLE` +
「无法创建工作区根目录：…（EEXIST: …）」，且盘上值未变。

### ② 建用例

`/cases` →「创建用例」→ **右栏展开表单**（是列表 + 右栏，不是弹窗、也不是整页；右栏宽度可拖）。

一个「来源类型」单选 + 六个字段，校验行为：

| 字段 | 行为 |
|---|---|
| 来源类型 | **本地目录** / **远端仓库**；决定下面「代码仓库」填什么、以及要不要填分支。它只是界面上的选择，服务端一律按**字符串形态**判定来源（填错态不会让服务端判错） |
| 标题 | 必填；只有空格会被字段级拦下 |
| 考题提示词 | 必填；交给智能体在工作目录里自行完成 |
| 评分标准项 | 一组二级表格（组 → 评分项：ID / 目标 / 权重）；可点「智能生成」按题面补充条目、「智能识别」把粘贴的评分要求解析成表格，解析后**仍可手改**；保存时非空（至少一组一项、权重为正整数、有值的 ID 不重复） |
| 代码仓库 | 本地绝对路径**或** git 地址（`ssh://` / `http(s)://` / `git://` / `file://` / `user@host:path`），旁边「校验」按钮回显仓库名与分支 |
| 分支 | 仅远端来源可填；留空 = 远端默认分支 HEAD，填了用该分支 tip 且每次评测重新解析 |
| commit hash | 留空 = 默认分支 HEAD；可从「重新加载候选」的最近 20 条里挑（候选按「来源 + 分支」取）；**手工输入任意合法 hash 必须可行**（40 位不会被截断） |

**评分模型不在用例上**（2026-09 起）：用例表单里没有「默认评分模型」这一格，用例的评分模型与
「智能生成 / 智能识别」用的模型一律取设置页「评分配置」的全局默认。历史 `config.json` 里残留的用例级覆盖值会被忽略，
保存一次用例后从盘上清掉。

**远端仓库的认证走本机 git**（SSH key / 凭据助手），工具本身**不保存任何凭据**、也不需要填账号密码。
远端来源**首次校验**会把仓库镜像到 `{workspaceRoot}/remotes/`（大仓库可能较慢；同一仓库跨用例复用这份镜像）；
之后**每次校验、以及跟随分支 / 默认分支的每一轮评测都会更新镜像**（钉死某个 commit 的轮次刻意不抓取），
所以这些轮次的 tip 是最新的；更新镜像时一并对齐镜像 HEAD 指向的默认分支名（远端改了默认分支名也能跟上），
而 commit 候选直接从镜像读（不联网）。
`file://` 地址同样按远端处理（指向本机上的另一个 git 仓库，一样先镜像再评测）。

「智能生成 / 智能识别」在**未配置**评分模型时禁用，悬停给出指向设置页的提示。判定看的就是**设置页的全局默认**——
用例上不再有可以覆盖它的那一格，所以这是唯一的去处，也是唯一会生效的配置。

两个负例的实测口径：`not-a-repo` 这类普通目录 → 「不是 git 仓库：<路径>（fatal: not a git repository …）」；
40 个 0 的 hash → 「commit 不存在：<hash>（仓库：<路径>）」。两者都不会放行保存。

### ③ 建评测

`/runs` →「创建评测」→ 右栏表单：

- **用例**：Select，选项形如「冒烟-最小示例 · repo · efc5a0a」（标题 · 仓库名 · commit 短哈希）；
- **执行模式**：单选的「串行」/「并行」（**串行在前**），**默认串行**；
- **使用智能体评分**：`Switch`，**默认关闭**。打开后这一轮的评分步骤不再是一次文本 API 请求，而是由
  设置页的**默认评分智能体**在**该行工作区里**自行查看改动后打分——改动很大、塞不进一次请求的上下文时用它
  （文本通路超上限只能按文件裁剪，分数照样出得来，但那是在残缺输入上得出的）。开关打开而设置页**没有**
  默认评分智能体时，表单当场给出内联 `Alert` 指出路，而不是等候选跑完几分钟才在评分步骤失败；
  它是**轮级**选择：创建时快照进 `run.json` 的 `useAgentJudge`，**创建后不可改**（沿用执行模式的既有口径）。
  一轮里只有一把尺子，行与行之间才可比——「重新评分」也沿用本轮的这一格，不能在重评时换通路；
- **候选行**：每行一个 智能体 + 模型，可「添加候选」。

**模型池按协议过滤**：模型下拉只列本行智能体协议下的模型，并标出来源（「手工维护」或自动拉取）。
过滤后为空时该行内联 `Alert` 说明原因与出路，而不是让人选完到运行时才失败。

**创建后不会自动开跑**——创建只是把这一轮存下来，要另外点「开始」。

### ④ 开始与观察

- **开始**：吸底操作栏的「开始」会先弹确认框，列出本次将执行的候选清单；已出分（已评分）的行**不在**清单里，
  即「开始」只跑未完成的行。
- **终止**（整轮）：吸底栏的「终止」，弹 `Popconfirm`，确认后杀掉正在跑的 agent 子进程；串行模式下还没轮到的行记 `skipped`。
- **终止**（单行）：只有**运行中**的行卡片上才有这个按钮。智能体不支持中途取消时文案不同——DSH 的
  `cancelMidTurn` 为 `false`，按钮写「关闭运行时」（通过关闭运行时来终止，而不是打断在途的一轮）。
- **并行 / 串行**：并行 = 同时开跑；串行 = 一行跑完**含评分**才起下一行，排队中的行会写明为什么在等。
- **隔离**：每行有**独立工作区与独立分支**（`test/{rowId}`）。串行也**不是**共用目录——同 agent 同模型的两行，
  工作目录与分支依然互不相同。

### ⑤ 看产物

每张行卡片有三个抽屉：

| 抽屉 | 内容 |
|---|---|
| 查看日志 | 该行的执行日志：流式追加、可开「自动滚底」、可「下载」为 `.log`（内容与抽屉逐字一致） |
| 变更详情 | 代码改动：三样合并 = 已提交改动 + 未提交改动 + 未跟踪新文件。**逐文件**列出（文件名 + 该文件的 diff），滚动时文件名吸顶；正文在该文件进入视口时才加载；超出 256 KB 上限被丢弃的文件会显式标注「未包含在本轮评分输入中」 |
| 评分详情 | 总分 + 满分（= 这一轮评分表的权重之和）+ 逐项「达成 / 未达成」与**每项理由** + 一句话总评 + 评分模型与评分时间 + 输出约束（schema 约束 / 提示词约束）+ 模型原始返回。**总分与满分都原样取自这一分自己的记录**（总分 = 达成项权重之和，界面不重算），未达成的项用语义色标出；评分表里有、判定里没有的项显式写「缺少判定」。**哪一个模型/智能体打的这一分写在这一行**：文本通路是「评分模型：X」，智能体通路是「评分智能体：X · 模型：Y」 |

出分后卡片按**总分降序**排列，前三名带排名徽标；同分并列同名次（不会硬拆成 1、2 名）。

**两条通路在这一页分得开**：评分详情那一行与日志抽屉里的 `评分` 事件行共用同一个口径——智能体通路写
「评分智能体：<名字> · 模型：<模型>」（日志行写成「<名字>（智能体）· <模型>」），文本通路只写模型名。
「这一分是哪条通路打的」是**记在行级** `score.judgeAgentKind` 上的快照（文本通路为 `null`），
不是在渲染时读当前设置：设置页事后改配置，历史行照样说得清自己的分是怎么来的。

**「输出约束」只陈述我们提交了什么**，不是对返回形状的承诺：`schema 约束` = 这一分是带着一份 JSON Schema
去要的（claude-code / codex 两家支持），`提示词约束` = 只有输出契约文本（文本通路与 dsh）。它**不表示**
上游照 schema 返回了——网关可能把那一格丢掉，那样模型照样回散文，而这一分仍然记着「我们要求了 schema」
（spec §9 第 1 条）。所以同一次评测里两种约束强度会同时存在，比较分数时先看这一格。

**总分算式**：**达成项的权重之和**；满分 = 全部项权重之和（由每个用例的「评分标准项」决定，不强制 100 分）。
实测例子：某轮评分表里 A1 = 18 分、D1 = 14 分，两项都达成 ⇒ 总分 32 / 满分 32；只达成 D1 ⇒ 14 / 32。
模型**不给总分**，它只逐项给「达成 / 未达成 + 一句理由」。

### ⑤′ 重试：三种失败、三条出路（手动出口叫「重新执行」与「重新评分」）

评分结果异常与执行失败**各有出口**，不要拿「新建一轮评测」当唯一补救手段（那会连带重跑候选 agent，分钟级成本）。
**两个手动出口是「重跑」出口，不只是「失败恢复」出口**（用户口径 2026-09-28 **晚间**：已出分、无报错时取消禁用）：
只要这一行**跑过一次且产出了改动**，两个按钮都给——已经出分的行同样可以「换个评分模型重算一遍」
或「整段重跑一次」。误点的代价由按钮上的 `Popconfirm` 二次确认承担（它会说清「现有分数会被替换」）。

| 发生了什么 | 出口 | 成本 | 说明 |
|---|---|---|---|
| 评分模型回了散文 / 半截 JSON / 漏了一项 | **自动**：结构检查 → 把错误回问模型 | 一次额外请求 | 最多回问 2 轮（共 3 次请求）；每一轮都在日志抽屉里留一行「第 N 轮返回未通过结构检查：<原因>」。仍不合格才落 `failed` + `JUDGE_PARSE_FAILED`，文案里写明「已回问模型 N 轮」 |
| 网络抖动 / 网关 5xx（如「服务维护中」）/ 限流 | **自动**：原请求重试 | 2 × 0.6 秒 | 只重试瞬时面：`AUTH_FAILED`（密钥错）与「已中止」一次都不重试；重试复用**同一段对话 / 请求体**，不是重新组装 |
| 候选 agent 失败 / 超时 / 被终止 / 被重启打断，或就是想**整段重跑**这一行 | **手动**：行卡片上的「重新执行」 | 分钟级（会重跑候选） | 只重跑**这一行**，不重跑别的行、不改轮级模式；走 `Popconfirm` 二次确认。**可用面**：不在跑 + 有可比基线 + 有 diff（＝「跑过一次且有产出」）。**已经出分的行也给**（晚间口径）；没跑过的行按钮禁用并给出原因 |
| 只是评分那一步失败，或想**换个评分模型之后重算分** | **手动**：行卡片上的「重新评分」 | 几十秒（不重跑候选） | 只重跑评分，沿用本轮评分通路（轮级开关创建后不可改），评分模型按当前配置重解析，**评分表用这一轮创建时的快照**（改用例的评分表不会换掉它）。**可用面**：与「重新执行」同一三条硬前提（不再看失败发生在哪一段）。已经出分的行、候选阶段失败的行都给；重评**先清空旧分**，失败会丢掉上一次的分数（历史仍留在事件日志的 `score` 事件里） |

- **瞬时失败还会自动重跑整行**（最多 2 次，间隔 3 秒）：`AGENT_FAILED` / `AGENT_LOAD_FAILED` /
  `RATE_LIMITED` / `INTERNAL` 属于这一类；**超时不在里面**——「超时」现在只可能来自适配器**自报**
  （2026-09-28 起本工具不设任何时间上限），自动再赌两次没有意义，正确处置是看那一行为什么自己收了场。
- **重试过这件事看得见**：卡片右上角出现「已重试 N 次」徽标；`run.json` 的每一行有 `attempts`
  字段（**累计**，不因新一次尝试而清零——「试了三次才成功」与「一次就成功」含义相反）；
  每一次尝试还落一条到该行的**尝试账本** `attempts.jsonl`（`{workspaceRoot}/{runId}/rows/{rowId}/`），
  它**累计、永不清空**——自动重试每轮都会清空 `events.jsonl`，所以「哪几次失败、为什么失败」
  只在那里查得到（实测踩过：界面显示「已重试 5 次」而日志抽屉里零条重试记录）。
- **失败发生在哪一段仍然落盘**（`run.json` 的 `rows[].error.stage` = `agent` / `judge`）：
  两段失败的行状态与错误码可以**逐字相同**（候选超时与评分超时都是 `timed-out` + `AGENT_TIMED_OUT`），
  这一格回答的是「刚才到底哪一段坏了」。它今天**只用于叙述与排障**——两个按钮的可用性判据都不读它
  （2026-09-28 晚间起）：该走哪个按钮由使用者按成本自己选。
- 「重新执行」与「重新评分」是**两个按钮**：前者连候选 agent 一起重跑（分钟级），后者只重跑评分（几十秒）。
  合成一个会让人按下去才知道跑的是哪一段。
- 行卡片上的按钮顺序是**用户指定的版面口径**（2026-09-28）：查看日志 / 变更详情 / 重新执行 / 评分详情 / 重新评分
  （用例按可访问名取 DOM 顺序钉住这一条，改顺序必须显式改用例）。
- 这两个按钮都是**行级**的：不需要先把整轮跑一遍，也不会动到别的行。服务端拿同一份判据抛 `409`
  （判据只有一份，在 contracts 的 `canRetryRow` / `canRescoreRow`）。

### 数据落在哪

| 路径 | 内容 |
|---|---|
| `~/.aieval/config.json` | 设置 + 供应商 + 用例（可用 `AIEVAL_CONFIG_DIR` 覆盖） |
| `{workspaceRoot}/cases/{caseId}/cache/` | 用例级缓存仓库（首次评测时克隆一次） |
| `{workspaceRoot}/remotes/{slug}-{hash8}/` | 远端仓库镜像（`slug` = 地址末段去 `.git`，`hash8` = 归一后地址的 sha1 前 8 位）；**跨用例复用**，删用例不会删它 |
| `{workspaceRoot}/{runId}/run.json` | 这一轮的快照（模式、行清单、每行状态与计量） |
| `{workspaceRoot}/{runId}/rows/{rowId}/workspace` | 该候选行的工作副本（独立分支 `test/{rowId}`） |
| `{workspaceRoot}/{runId}/rows/{rowId}/.agenthome` | 该候选行的智能体独立配置目录 |
| `{workspaceRoot}/{runId}/rows/{rowId}/events.jsonl` | 该行的执行事件日志（执行的唯一真相源；**只含当前这一次尝试**） |
| `{workspaceRoot}/{runId}/rows/{rowId}/attempts.jsonl` | 该行的**尝试账本**：第 N 次尝试的开始与结局（**累计、永不清空**）。自动重试每重试一次就会清一次 `events.jsonl`，所以「一共试了几次、每次为什么失败」只在这里查得到 |

**改工作区根目录不迁移已有产物**：旧轮次留在旧根目录下，不会自动搬家；历史评测显示它自己的
`workspaceBase` 实际路径。注意读侧（列表 / 详情）只扫**当前**根目录，所以改过根目录之后，
旧轮次既不在列表里、详情也取不到——把根目录改回去即恢复。彻底解决需要新增一份落盘物（一份记录历史
根目录位置的 已知根目录索引），本期未做。

**升级到「评分标准项」口径（2026-09-29）之前的旧数据不做兼容**——它有两种形态，症状与出路都不同：

- **旧用例**（`config.json` 里只有 `judgePrompt`、没有 `rubric` 的那些）**在使用时被拒绝**：
  取详情 / 编辑 / 用它建评测都会拿到中文 `INTERNAL`「这个用例是旧版数据（没有评分标准项），
  请删除它或重新创建：<caseId>」。列表**照常列出**它（否则连删掉它的入口都没有），但它已经没法再用——
  那段 `judgePrompt` 是旧口径（五个维度各 1–5 分），出路是**新建一份用例**（评分口径现在只有
  「评分标准项」这一份真源，也没有把自由文本转成表格的迁移工具）。**旧的那条不会被自动清理**：
  它照常留在 `config.json` 里（工具不删除、不迁移任何历史），要删请自己手动删；
- **旧轮次**（`run.json` 里没有 `rubric` 快照的那些）**被列表跳过**，不会拿一张不存在的评分表把分数显示错。
  症状是「评测记录凭空少了几轮」，所以服务端在扫描时记一条中文 `WARN`——「有运行快照因评分口径升级
  不再兼容，已从列表跳过（列表显示的轮次会比磁盘上的少）」，并带上条数——把它与「产物真的没了 /
  工作区根目录改错了」区分开。旧轮次的目录留着只占磁盘、不影响新评测；**工具不会自动删它们**，
  要清请自己手动删对应目录。

### 分数怎么来的

- 评分表是**二级表格**（组 → 评分项：ID / 目标 / 权重），每项**二元判定**（达成 / 未达成，没有部分分）：
  总分 = **达成项权重之和**，满分 = 全部项权重之和（不强制 100 分）；模型**不给总分**，
  于是「模型算错总分」这一整类问题从根上消失；
- 评分有**两条通路**，一轮只用一条（轮级开关「使用智能体评分」，创建后不可改）：
  - **文本 API 通路**（默认，开关关闭）：**评分标准项表格** + 代码改动一次性交给评分模型，
    **不入仓库、不跑 agent**。好处是便宜、快、完全可复现；代价是**看不到测试运行结果**，只能凭代码本身判断；
  - **智能体通路**（开关打开）：由设置页的「默认评分智能体」（Claude Code / Codex / DSH 之一）在**该行工作区里**
    自行按文件读改动后打分，评的模型仍是设置页「评分配置」里那把尺子（用例上没有覆盖它的地方）。两条通路给的必须是**同一把
    尺子**：围栏剥离、**评分表里每一项都必须有判定（缺一项即整行失败，缺项不等于未达成）**、
    总分一律按「达成项权重之和」重算，一个字都不差。代价是评分智能体**可能改动
    工作区**（见「排障」里那条 `WARN`），且它自己的用量**不进快照**（只在日志抽屉里）；
- diff 超过上限（默认 256 KB）会按文件裁剪，卡片上标「diff 已截断」——文本通路的这一轮是在**不完整输入**下得出的，
  被丢弃的文件清单也在抽屉里（智能体通路没有这条裁剪：改动由它自己按文件读）；
- **执行与评分都不限时间**（2026-09-28 用户口径）：本工具不再有任何行级超时——一行只会因为
  「跑完 / 失败 / 用户点终止」结束。代价照实说：一次挂住的上游调用会把该行一直留在运行态，
  出路只有行卡片上的「终止」；
- **「轮次」= 一次模型 API 往返**（2026-09-28 用户口径）：一次请求带着 `role=user` 的上下文、
  模型回一条 `role=assistant` 的答复，算一次；工具**不**数 CLI 自己的「turn」（codex 的
  `turn.completed` 与 dsh 的 `turn/end` 都是整段任务一条，照它们数出来永远是 1）。三家各自的计数来源：
  Claude Code 数主循环 `assistant` 消息的 `message.id`（与 SDK 的 `num_turns` 同口径，异常不一致时在日志里留一条 WARN）、
  DSH 数 `step/start`、Codex **近似**数模型产出条目（`reasoning` / `agent_message` 按 `item.id` 去重）——
  codex 的 JSON 事件流里没有逐次请求事件，所以这一格是近似值（实测偏差方向：一次调用同时产出推理与答复时偏高，
  模型不产出推理摘要时偏低）。轮次在跑动期实时跳动（每观察到一次往返就发一条 `usage` 事件），
  与 token 各自独立——采不到 token 也照样数轮次；
- **不同轮次之间的分数不可比**：尺子变了分数就没有可比性——换过评分模型、**换过评分标准项**（改过用例的评分表）、**换过评分通路**（一条文本 API 评分、
  一条智能体评分时尤其）、或改过 diff 上限，都会让两轮的分不在同一个口径上。**同一轮内**的行用同一把尺子、行间
  可比；跨轮比较前先确认这两项配置一致；
- 计量采不到时显示「未采集」「不支持计量」，**不是 0**；
- **评分结果先过结构检查，不合格就回问模型**（最多 2 轮，共 3 次请求）：这是「结果异常」的自动处置，
  它与「重新执行」不是同一件事——修复只改**形状**（评分表每一项一条判定、合法 JSON），
  **不改尺子**（总分始终由系统按「达成项权重之和」加总，不采信模型自报的任何分数）。仍然不合格才落 `failed`，
  文案里写明已回问几轮，最后一轮的原文进日志抽屉；
- **瞬时失败会自动重试**：文本请求最多 3 次尝试（网络 / 5xx / 限流），整行最多 2 次重试；
  每一次都留痕（日志一行 + `attempts` 计数），不静默吞掉。

### 本期不做

分布式执行 / 多用户与权限 / 凭据管理（远端仓库本身已支持，认证走本机 git）/ 自动合并或改进被测代码 / 历史评测趋势统计；
评分口径由用例自己的评分表定义（一轮按创建时的快照评分，不随用例改动而变）；DSH 的 token 计量采不到时显示「不支持计量」，不填 0。

### 界面用到的接口

界面上的每个动作都对应一条真实的 Next 路由（每功能一文件）。下表是主要出口，完整契约以
[`docs/superpowers/notes/2026-09-22-features-plan-interfaces.md`](docs/superpowers/notes/2026-09-22-features-plan-interfaces.md) 为准：

| 路由 | 作用 |
|---|---|
| `/api/settings` | 设置读取与保存（含工作区校验） |
| `/api/providers`、`/api/providers/{providerId}` | 供应商 CRUD |
| `/api/providers/{providerId}/models`、`/api/providers/{providerId}/models/fetch` | 模型清单手工维护与自动拉取 |
| `/api/cases`、`/api/cases/{caseId}` | 用例 CRUD |
| `/api/cases/validate-repo`、`/api/cases/commits`、`/api/cases/generate-judge-prompt` | 仓库校验、commit 候选、评分标准项的智能生成 / 智能识别（同一接口，按 `prompt` 是否为空分派） |
| `/api/runs`、`/api/runs/{runId}` | 评测创建、列表与详情 |
| `/api/runs/model-options` | 候选池（按协议过滤） |
| `/api/runs/{runId}/start`、`/api/runs/{runId}/abort` | 开始与整轮终止 |
| `/api/runs/{runId}/rows/{rowId}/abort` | 单行终止 |
| `/api/runs/{runId}/rows/{rowId}/rescore` | 重新评分——只重跑该行的评分步骤，**不重跑候选 agent**、不重建工作区、不改分支与 diff 摘要；沿用本轮的评分通路（轮级开关创建后不可改），评分模型按当前配置重解析，**先清空旧分**（重评失败会丢掉上一次的分数，历史仍留在事件日志里）。行卡片上是 `Popconfirm` 二次确认；可用判据是 `canRescoreRow`（不在跑 + 有可比基线 + 有 diff），**含已经出分的行**（2026-09-28 晚间口径），没跑过的行禁用并给出原因，真调到服务端抛 `CONFLICT`。原因**由 `Tooltip` 承载**（鼠标悬浮禁用按钮弹出），而它挂在**外层 `span`** 上才收得到事件——这一条 jsdom 验不出来（合成事件照样冒泡），改动后要在真实浏览器里悬浮一次 |
| `/api/runs/{runId}/rows/{rowId}/retry` | 单行**重新执行**（路由名仍是 `retry`）——**连候选 agent 一起重跑**（工作区重新准备、分支重建、评分重跑）；不重跑别的行、不改轮级模式。可用判据 `canRetryRow` 与重评同一组硬前提（跑过一次且有产出），**已经出分的行同样给**（用户口径 2026-09-28 晚间）；服务端与界面共用同一份判据，按钮同样是 `Popconfirm` + 外层 `span` 上的 `Tooltip`，不可用时服务端抛 `CONFLICT` |
| `/api/runs/{runId}/rows/{rowId}/log`、`/api/runs/{runId}/rows/{rowId}/stream` | 执行日志（一次性读取与 SSE 实时流） |
| `/api/runs/{runId}/rows/{rowId}/diff` | 代码改动（按需现算） |

## 代码在哪

```text
ai-result-evaluation/
├── apps/web-next/     # 唯一应用：Next.js（页面壳 + 路由转调服务层）
├── packages/server/   # core（工作区引擎，零外部依赖）/ agents（智能体适配）
```

服务端各包**零框架依赖**：厂商 SDK 只允许出现在 `agents`。依赖方向单向，
由 `withBoundary()` 的 eslint 规则硬约束而非口头约定，边界含动态 `import()`、`require()`
与跨包相对引用。持久化走磁盘文件（JSON + JSONL 事件日志），不引入数据库。
