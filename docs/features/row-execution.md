# 行执行与日志

## 定位

一行候选从发起到落终态的全部执行事实，以及人在哪里看到这些事实。行执行 = 状态机 + 八步内部时序 + `events.jsonl` 唯一真相源；观测面 = 执行日志抽屉（轮次时间轴 + 折叠面板 + 子任务面包屑）+ 行卡片实时计量 + 逐消息用量页脚 + 轮次 Tooltip + 抽屉底部的输入区与排队区（人工消息这一面）。

## 页面形态与交互

- **执行日志抽屉三区**：固定区（事实条 + 领域事实 + 面包屑 / 工具条 + 原文行，四行）→ 滚动区时间轴（**虚拟列表是唯一滚动容器**）→ 浮动件「回到最新（N 轮未读）」。抽屉标题恒「执行日志」，`WIDE_DRAWER_SIZE = max(61vw, 800px)`。**时间轴的组成按顺序是**：首条「考题提示词」卡片（`userPrompt`，来自账本里那条 `origin: 'case-prompt'` 的消息）→ 补充提示 → 各轮；**每换一段插一个段标题**（只在主会话节点画）：一行「追问 ×N」+ 这一段的开始时刻 + **那句追问的正文**，正文排在这一段的**第一个轮次之前**。段标题的内容来自**段这一层**的数据（`AgentLogModel.segments`：段号 / 时刻 / 那句人话），与轮次分组无关；正文取段首那一轮的 `role: 'user'` 文本块，**取出来之后轮次的展示块里就没有它了**（同一句话不许画两遍）。投递顺序不保证问答顺序——一次追问是又开一次 `run()`，那一段的第一条适配器消息可以在那句追问自己落账本之前就落地（真机多次如此），故那句人话的落点只认段号、不认投递先后。`buildRenderBlocks` 规则 3 的兜底定位键因此**单独一格**（`LogTurn.fallbackMessageId` = 投递顺序上第一条块的消息 id），不读展示块的第一条。守卫：`build-model.test.ts`「轮内顺序：人说的话排在模型答复之前」/「追问那句落在**它自己那一段**（段标题里）」/「首段不进段标题」、`virtual-turn-list.test.tsx`「VirtualTurnList：段标题」五条、`fixtures.test.tsx`「追问段的标题读得出那句人话」。
- **每轮按「思考 → 工具调用 → 正文」呈现**：思考 / 工具默认折叠；连续工具调用合并一个面板（组头 `工具调用 × N`）；`task`（计划清单）与 `ask-user`（问答）两族从工具组提出单独成卡、原地出现、切断合并链。**提出去的调用仍然是它自己结果的主人**：配对键是 `callId`、范围是这一轮，卡片就是那次调用的显示位——卡片画了结果（`task` 面板并入 `panel.result`；`ask-user` 卡片已收场且原文到手）时结果归卡片，不再另起一条「孤立结果（配不上调用）」；卡片**没有**结果可画时（还没收场、或收场了但原文没采到）结果照旧独立成条，**不吞**。守卫：`render-blocks.test.ts`「卡片接管的调用，结果归卡片」五条。
- **正文块的流式观感**（`XMarkdownText`，`@ant-design/x-markdown` 外壳）：流式期间（块 `assembly === 'open'`）开 `enableAnimation`——每个**新到片段**各自 200ms 渐显（同一文本节点纯追加时旧 span 不重挂、新增部分单独成 chunk），**这是正文在流式时的全部动效**：块底下不再有「转圈 + 正在思考」那一行（它是一段与正文无关的持续动效，在一段已经读得通的正文底下只会被读成空白），`tail` 也刻意关着（`false`）——「还在写」的信号就是新内容自己在淡入。**块 id 挂在 `mergeKey` 上而不是 `messageId`**（`build-model.ts` 的 `blocksOf`）：装配器对同一条逻辑消息**每次投递都发新的 `messageId`**（全局序号递增，`mergeKey` 才恒定），而块 id 是界面块的 React key——挂 `messageId` 上时流式每帧 key 全变 ⇒ 正文块整棵重挂 ⇒ 淡入整段从头重放，页面上就是「内容一直在更新、却一直在闪烁」。守卫：`x-markdown-streaming.test.tsx`（追加片段各自淡入、无 `xmd-tail`）、`text-block-streaming-stability.test.tsx`（帧序列推进时正文块不重挂、chunk 只增不减）、`text-block-view.test.tsx`「不该有「正在思考」那一行」。
- **工具行摘要行**（每条工具收起态唯一可见的一行）= `[一块身份牌子] [一句话]`。牌子**族名优先**（「跑命令」/「读文件」…），没有族映射才回落工具名本身（`Bash`，等宽）——`Bash` 与「跑命令」是同一件事的两种说法，各占一头（行首 / 行尾）就是说两遍（用户口径）。**那句话三级回落**：① 数据层算好的 `tool-call.summary`（**摘要主体**：`Check surefire report summaries`、`src/index.ts:10-120`、`2 步`，不含 `调用工具 <名>：` 前缀）；② 老记录（没有这一格）回落 `input.description`；③ 再回落参数原文首行。**取参口径**（用户裁定）：`description` 优先（有目标时拼 `描述（目标）`），没有就**按族自己拼**（每族一种拼法，逐族清单见《消息规范》）。这一格的两个约束：dsh / claude 的 Bash 类调用把 `{command, description}` 一起送来，照原文首行渲染就是一行 **1495px 的 JSON**，而「这一步在干什么」只在 `description` 里；反过来，**只留描述又会让同一行里两次 `exec_command` 长得一模一样**——Codex 侧压根没有 `description` 这一格，它的 `command` 就是唯一区分，所以两个都要。**工具名一个字没丢**：摘要行让位给族名时它落到展开后的正文（「工具原名」那一行，没采到就写「工具原名未采集 · 原因」——不编名字）。`description` 由数据层抽成 `ToolInput.description`（`build-model` 的 `serializeInput`，缺席 / 只有空白 ⇒ `null`，**不拿别的字段凑**——它与派发调用的子任务名是同一格），组件不自己反解原文；参数原文一字不少地留在展开后的正文（`input.text`）。守卫：`build-model.test.ts`「工具入参：原文与 `description`」/「`tool-call.summary`（数据层算好的那一句）原样搬到界面块上」 + `tool-item-detail.test.tsx`「行首是族名…」/「没有族映射…」/「摘要行优先用数据层算好的 `summary`」/「老记录没有 `summary` 这一格 ⇒ 回落到 `description`」。
- **面包屑只看该节点自己的消息**；每段下拉 = 该层级兄弟列表、当前项 disabled。时间轴首条是**考题提示词**（`SessionNode.userPrompt`）：数据来自账本里那条 `role: 'user'` + `origin: 'case-prompt'` 的消息（编排层在把这一轮交给厂商之前落的账，见《消息规范》），正文与时刻分别取它第一个 `text` 块与行开始时刻；那一格同时**从轮次里剔出去**（同一句话不在时间轴上画两遍）。找不到那一条（旧运行、还没跑过的行）就整块不渲染——**不回落去读用例**（题面可被编辑、用例可被删除，读它就是在说「现在这份」而不是「当时那份」）。
- **子任务占位条在「派发那一刻」就出现**：派发点（那次派发工具调用之后）上的一条卡片，Tag 是「运行中」，右侧「进入 ▸」是进入该子任务节点的**唯一**入口（面包屑只能回退、不能前进）。判据是**那条行要能挂到某一轮上**——界面按「`parentCallId` == 那次调用的 `callId`」或「任务名 == 派发入参的 `description`」二选一认；两条都拿不到时那条行落不进任何一轮（**没有卡片、也没有入口**，与它有没有正文无关）。适配器的义务因此不是「派发时投一条行」那么宽：**投出去的行必须能定位**，派发那一刻拿不到名字或调用 id 的家，要等另一条消息到达后补投一条更完整的（dsh 的 `subagent/catalog`、pi 的扩展事件总线）。**子任务正文可能晚于卡片**——pi 的子会话正文**首选 wire 通道**（订阅子会话事件，逐字增量 + 收尾快照；父会话派发期几乎不产事件，靠本层自造的合成帧换来排空），转写文件只是**兜底**（wire 不可用时整行退到它，落 `source: 'session-file'` 并带「补录」角标），所以卡片出现到第一轮正文之间的空窗通常在毫秒级（空态是「这个子任务还在跑 · 逐步骤正文还没到」，不是「没有对话记录」）；dsh 的子会话事件与主会话在同一条通知流里，卡片出现时正文通常已经在。
- **流式滚动「跟随最新」**：默认开，用户一上翻自动关，角落浮出「回到最新」；与工具条开关同一份 state。
- **四类东西出口分立**：`log` 原文 → 「原始输出 N 条」独立二级抽屉（逐字原文、默认收起；`log` 事件不进时间轴）；无法归一载荷 → `unrecognized` 块；真实附件 → `attachment` 块；完整台账 → 仅「下载台账」（与时间轴是两条内容，不要求逐字一致）。
- **环境抽屉**是 `agent-log` 内部件（关闭联动是结构保证）：四组（用户层 / 厂商系统层 / 运行配置 / 实测统计）；缺失项给 `MissingReason` 原因文案；「已调度的工具」与「用过的工具及次数」分列。**实测统计组里另有「流式增量」一格**：它读行快照的 `EvalRow.streamingDelta`（增量帧只广播不落盘，这是事后唯一痕迹），三态各自成句——**没观测**（格缺席）/ **观测到 0 条**（能力位声明 `yes` 的家也可能一条都不投：开关没生效、插件没挂上）/ **N 条 · 末帧累积 M 字**（正文不落盘，中断行只能回答「写到哪」）。
- **`ask-user` 卡片**：外壳是 `Card`——**卡面标题只写「问题 N 个」+ 收场态，问题类型不进卡面**（`header` 是某一问的事），下面**一问一格折叠面板、默认全部收起**（面板标题 = 问题类型 + 题目 + 「可多选」，面板体 = 选项与作答），**原文入口（「原始结果」+「重新读取」）在卡面 footer**、没采到原文时整格不画。**「还在等」因此不必靠展开**：等待态写在卡面那枚「等待答复中… 12m」，故问答卡片**一格默认展开键都不加**。七种收场（`answered` / `auto-resolved` / `skipped` / `timeout` / `unavailable` / `rejected` / `canceled`）+「还没收场」独立一支；本仓 `approvalPolicy: 'never'` ⇒ `unavailable` 是中性已知边界；卡片是只读复盘视图，应答面在弹层（三个 HTTP 端点见下一条）。**「其它（自由输入）」那一格只在有自由输入内容时出现**（`answers[].custom` 为空——含还没作答、以及写了但内容为空——就不画那格卡片；不画卡片不等于丢内容，同段作答区里的「选项里没有的」标签照旧直接铺在问题下）。
- **应答面**（浏览器 → **运行中的**评测唯一的一条数据面通路；反向的控制面通路只有「终止」）：三个端点是 `GET /api/ask-user`（待答快照，裸数组，每条给 `askId` + 轮 / 行 / 段 + 问题 + `askedAt`）、`GET /api/ask-user/stream`（信号式 SSE，只推「变了，重读」）、`POST /api/ask-user/answers`（`{askId, answers}`，应答面的唯一写入口）。三条口径：① **快照是唯一读侧、挂起表是唯一写侧**——表是进程内的一份内存状态（`askId → {定位, 问题, 时刻, 决议函数}`），不落盘，于是**服务一重启那些提问就无从应答**（旧 `askId` 一律 404，在跑的行走既有的重启恢复）；② 应答按 `askId` 幂等——**首个生效（200）**、后到 409、未知 404，答完之后该问从快照里消失；③ 答案与问题**逐问对上**（数量与顺序都要一致），对不上是 400 且**不消耗**这一次应答机会。
- **底部输入区（人工消息这一面）**：`AgentLogLayout` 的 `footer` 槽是滚动区**之后**的第三段固定区（缺席 ⇒ 一个节点都不渲染；它在时滚动区自己按它的高度缩水，零高度算术）。**只有「这一轮的闸门开着 **且** 这一行此刻还有活在跑」时才渲染**——取件发生在**这一行**的投递循环里，一行收场之后再送话永远等不到取件，给一个发了没人收的输入区等于把「投不进去」说成「能投」（判据是契约的 `isRunningRow`，与「能不能重跑」同一个落点）。四条形态：① 输入区就是一行（`Sender`，回形针在框内左侧、同时是点选与拖拽落点，发送键用 X 自带的圆形上箭头）；② **附件清单住框上方一行 chips**，先落盘拿到路径才允许发送（登记那一刻正文与清单就是完整事实）；③ **排队区在输入区上方**——一条直出、两条起收进折叠面板并**默认收起**（收起态露出「N 条排队消息」这个计数：那两颗操作按钮被藏起来之后它是唯一的可见信号），`gone` 不进这一区（画出来就是把一条已经消失的消息说成还在等）；④ **紧凑密度只套输入区**，整支抽屉的字号不动。**「删除」是双态动作**：还在排队的那条直接摘掉、已交给厂商的那条走撤回，成不成由**这一家这一档的声明**决定（两颗按钮的可用性与悬停文案全部由声明派生，界面一处都不判厂商；读不到声明一律置灰并如实说「读不到」）。撤回成功后**文本与附件一起回填**输入框（补到现有内容**前面**、换行隔开），交给过厂商的那条另给一条一次性提示——它可能已被模型看到，重发会变成两条。
- **单行执行**：一个按钮按行态分叉「开始执行 / 重新执行」，确认框必须点名范围（首跑：「只跑这一个候选：本轮其他行（含已经执行过的行）都不会重跑。」）；**只动这一行**——其他行的状态 / 分数 / 计量 / diff / attempts / 事件日志逐字不变、串行队列不推进。重新评分：`Popconfirm`「只重跑评分步骤，候选 agent 不会再跑；现有的分数会被新的评分结果替换。」
- **卡片底部活动行两档**（用户口径「不断打字」）：有实时正文时走**打字档**——只显示**最后一个非空段**（按 `\n` 切段：换行即清空重打，入场动画靠段号当 React `key` 重挂元素）+ 还在写时挂 `▍` 闪烁光标；没有正文时回到**静态档**（工具块 `summary` → `log.summary` → 状态回落文案，高光扫过）。数据来自 `useRunActivity`（`AgentMessage` 那条流，带 `?replay=0` 不回放历史），刷新页面后由 `log.summary` 兜底——**实时优先、历史兜底**；终态整行收起（`activityText` 对非运行态返回 `null`）。

## 数据与契约

- **行状态机**（完整枚举）：

  ```text
  pending → preparing → running → (agent 完成) → judging → judged
                    ↘ failed / timed-out / canceled
  串行被终止时未轮到的行 → skipped
  服务重启时仍在运行的行 → interrupted（不自动续跑）
  ```

  | 状态 | 含义 |
  ||---|---|
  | `canceled` | 用户按了终止，当时**正在跑**的行 |
  | `skipped` | 串行模式下用户终止时**还没轮到**的行 |
  | `timed-out` | **骨架的看门狗**判定这一行**静止**超时（连续 180 s 没有任何产品事件，或一次模型往返超过 600 s）。它**不是**工作时长上限——「执行不限时间」不变；也**不进自动重试**（与 `canceled` 同一条判据）。归因码 `AGENT_TIMED_OUT`，界面标签「已超时」 |
  | `failed` | agent 非零退出 / 启动失败 / 评分调用失败 / **评分智能体改了工作区** |
  | `interrupted` | 服务重启时仍在运行（`recoverInterruptedRuns` 把 `running`/`preparing`/`judging` 全标它） |

  `preparing` 阶段失败（复制失败、commit 不存在、远端不可达、工作区不可写）仍落 `failed` 并保留错误详情，不静默跳过。可重评终态 = `judged` / `failed` / `timed-out` / `canceled`。

- **十类事件**（全行级、每行带单调 `seq`）：`status` / `log`（带 `summary?`）/ `vendor-system` / `usage` / `diff-summary` / `ask-user`（一次提问的收场：收场方式 / 等待时长 / 提问工具来源，与账本那一半共用 `askId` / `callId`）/ `inject-message`（一条人工消息最后去了哪：`delivered` / `retracted` / `already-consumed` / `discarded` / `timed-out`，与账本那一半共用 `messageId`）/ `score` / `error` / `end`。`setRowStatus` 落点唯一：改状态 + 落盘快照 + 追加 `status` 事件**成对**；`EvalRow.error.stage`（`'agent' | 'judge'`）是**自动重试的单位判据**：失败在评分段（`'judge'`）⇒ 只重跑评分、候选产出一个字不动；在候选段 ⇒ 整行重跑（见《评分》「评分段失败只重跑评分」）。
- **`usage.tokensBasis`**：`'reported'` 才回写 `run.json`；`'estimated'` 只走事件流；缺省按 `'estimated'` 安全侧；`turns` 与两格子智能体分量恒回写。**用量里程碑（整行只出一条）**：取候选阶段里最后一条**主会话**带计量的 `usage`（读数本身是厂商口径——累积的家给累计值、逐次的家给最后一次调用的值；整行累计恒在顶部事实条）。**候选阶段的闸门是「一开一关」**：`judging` / 终态帧**关**（它们之后报的读数是评分智能体的，落 `judge-events.jsonl`），`preparing` / `running` **重新开**——一次追问或一次重跑就是又开一个候选阶段。只关不开的话，追问那一段的读数全被当成评审者的丢掉，里程碑会冻在首段最后那条读数上（数字是旧的、位置也落在中间那一轮）；`重新评分` 只落 `judging`、不落 `preparing`，故不会误开这道门。子会话读数一条不进；孤儿抹成 `turn: null` 按时刻归位不丢。**归属**：有归属键时挂**段号最大**的那一轮（同号在两段各有一轮时），落点因此就是时间轴上最后那一条用量。守卫：`build-model.test.ts`「追问那一段的读数照样算数」「多段之后仍不吃评审者的读数」。
- **子智能体三格**：`{0,0,0}` / `0` = 确实没有（「本次未观察到」），`null` = 没采到（**逐格各判**「全量或 null」+ **逐格**点名 WARN：用量那一格来自总线终态载荷、轮次那一格只在 `Agent` 工具结果的 `details.turnCount` 里，后台档结构上拿不到 ⇒ 用量照交、只有轮次记 null）；恒有 `subagentTokens ≤ tokens`（逐格）、`subagentTurns ≤ turns`。
- **三处用量形制**：顶部事实条 = **整行累计**（正体 secondary）；轮末里程碑 = 整行一条 Tag 色块；消息页脚 = **本条消息自己那次调用**（italic，`data-usage-footer`，`usage === null` 整行不渲染、同一逻辑消息多个块只出一行）。
- **人工消息这一面**（人往运行中的这一轮送的那句话；闸门是**轮级快照** `EvalRun.injectMessages`，缺省 false —— 关着时适配器一格都不挂，既有行为逐字不变）：行上另有两格 **`sessionId`**（这一行跑在哪条会话上；旧产物缺格读 `null` ⇒ 界面如实拒绝续接，**不许静默从头跑一遍**）与 **`followUps`**（已经**送达**的人话条数，**与账本对齐、不与队列表对齐**——账本里 `origin: 'human'` 的每一条都算：往运行中的一轮送进去的，以及每一次追问自己那一句；候选卡片上的「人工消息 ×N」读它——那一格是**总数**，运行中插的话与跑完之后的追问都算）。**追问轮次另有一格 `followUpRounds`**（这一行被追问过几次，只数跑完之后另起一段那一支）。两个读数在同一个场景里取值不同：先往运行中的一轮送进去 2 条、跑完再追问 1 次 ⇒ 卡片「人工消息 ×3」（账本里 3 条人话）而行快照的 `followUpRounds` 是 1。**行日志里那句 `[人工追问 ×N]` 读的是轮次那一格**——所以它说的是「第几次追问」，与卡片那个「被人工干预过几次」的总数不是同一个数。**两档投递边界**：`'round'` = 下一次模型往返之前（「立即发送」）、`'idle'` = 这一整轮没活可干了（「排队」）；**「等一次工具调用跑完」那一档刻意不存在**（四家在那一点都没有投递面）。**队列表**是服务端进程内的真相源（键 `runId + rowId`；`messageId` 由客户端铸，同时是幂等键、账本钥匙与附件目录名），一条走四态 `queued` → `delivered` → `consumed` / `gone`；**发送幂等**（重复提交 ⇒ 200 + 同一条，不新增、不再投递）、**改期单向**（只能由「排队」变「立即」、交出去之后改不了）、**撤回与「删除未投递项」是同一个端点**（服务端按状态分派：`queued` 摘表、`delivered` 走厂商撤回、`consumed` ⇒ 409 + 原因、重复撤 ⇒ 200 +「已经处理过」、未知 id ⇒ 404）。**落盘时刻 = 适配器真把消息交给厂商那一刻**：账本加一条 `role: 'user'` + **`origin: 'human'`** 的消息（`source: 'hook'`，正文只放人写的那句话、附件另成块），行级事件加一条 `inject-message`，两处共用同一把钥匙。**附件**落 `rowDir/attachments/<messageId>/`——在工作区**之外**（不污染 `git diff` 与评分面）而在 `runDir` **之内**（随 `deleteRun` 一次删干净）；上限**单文件 20 MB / 单条消息 10 个**（前后端读 `@aieval/contracts` 的同一处常量，服务端必须拦——界面能被绕开）；**重跑清、追问不清**。
- **判据函数族**：`canRunRow`（不在跑）、`canRetryRow`（不在跑 + `baselineCommit !== ''` + `diff !== null`，与前者单调）、`canRescoreRow`、`hasLiveRows`、`isSameRowTarget`。
- **评分阶段的两份产物独立**（用户口径「与执行日志分开」）：`judge-messages.jsonl` / `judge-events.jsonl`，与行的 `messages.jsonl` / `events.jsonl` 同目录同级。分流判据是**产出者**——评审者那次 `run()` 交出来的事件与消息（含 `usage` / `vendor-system`）全走评分两份，编排层自己的行级事件（`setRowStatus` / 降级留痕 / `score`）仍落 `events.jsonl`。两条流的 `seq` **各自一套**，重跑 / 重评与候选同一条清空口径。读数：`…/judge/messages`、`…/judge/events`（各含 `/stream`，记录流支持 `?replay=0`）。

## 状态机与时序

**八步内部时序**：

1. 建工作区 `{workspaceRoot}/{runId}/rows/{rowId}/workspace/`；
2. 取基线：远端 `ensureMirror` → `resolveRemoteRef`（本轮唯一一次 fetch）；本地从用例 cache **文件系统级目录复制**（不是每行克隆）→ `git checkout -B test/{rowId} <40 位 hash>`（一条命令同时切基线并重建行分支，重跑不因分支已存在而失败）；
3. 注入隔离配置：`CLAUDE_CONFIG_DIR` / `CODEX_HOME` / `DSH_HOME` → `{rowDir}/.agenthome/`；claude 另加 `settingSources` + `settings.env` 钉路由；
4. 跑智能体：`getProvider(kind).run`，工作目录 = workspace，`permission: 'full'`（评分智能体 `'read-only'`，独立 `.judgehome`）；
5. 收集计量（token 三元组含子分量、轮次、耗时、退出状态）；
6. 算 diff：`git diff {commit}..HEAD` + `git diff HEAD` + `git status --porcelain`（`--intent-to-add` 登记未跟踪）**三样缺一漏改动**；被 gitignore 的文件不进产出；`diffBudgetBytes` 默认 256KB，超限按文件裁剪并显式标「已截断」；
7. 评分（两条通路共用 `parseJudgeResponse` + `finalizeScore` + `judgeStageAttempt` 骨架）；
8. 落盘：事件追加 `events.jsonl` + 快照写 `run.json`。

- **缓存策略**：用例级 cache 不存在 / 来源缺失 / 来源已变才完整克隆一次；**重跑同一行先确保缓存、再清上一轮行产物**（清完而克隆失败会留下无工作区中间态；此顺序失败时旧产物仍在，重跑幂等）。分支名用 `test/{rowId}`（行 id 不用轮 id，多候选共用会互踩）。
- **`retryRow` 放行三级**：该行在跑 ⇒ 409「请先终止它，再执行」→ `rowAborts`/`retryTasks` 在途 ⇒ 409「上一次的运行还没收尾，请稍候再试」→ `!canRunRow` ⇒ `retryRefusal` 竞态兜底。**已知缺口**：`POST …/retry` 准备阶段是同步重活（镜像 fetch + 复制 + checkout），远端仓库 + 冷镜像时可超 5 分钟才返回；编排层已用 `await yieldToEventLoop()` 移出调用栈，但仍整段占住事件循环；强杀 / HMR 重启会留在途锁（只能杀残留进程恢复）。
- **`rescoreRow` 四硬口径**：追加事件不 `resetEvents`、不递增 `attempts`；入口区可整体回退；终态复检——用户先终止则状态保持 `canceled` 分数只进事件日志；`diff` 一字不动。
- **实时状态**：评测页信号驱动重验（`GET /api/runs/events` SSE；`PUT /api/runs/{id}` 落盘即 `event: run-updated`，毫秒级）；有活在跑时至多 60 秒一次慢兜底。

**人工消息的取件与收场**（三个时刻各自回答一件事）：

- **取件**：端口只有 `drain(两档之一)` 一格、没有「有新消息」的信号 ⇒ 节拍 = **适配器认的那个通知边界**（`'round'` 在「一批工具跑完」那一刻、`'idle'` 在这一整轮收场那一刻）；`'round'` **只**取要求「立即发送」的条目，`'idle'` 取全部且要求「立即发送」的排在前面（它等得更久）。取走 ≠ 已交付：`state` 回答「还能不能要回来」，`deliveredAt` 要等适配器真的交出去才写。
- **队列非空先不收场**：候选段收尾时若还有没投递的条目，按能力分派——声明说「已收工的一轮还能被唤醒」**且**我们接了那条唤醒路径 ⇒ 起新一轮；否则**等这一批的等待预算**（缺省十分钟、编排层早一秒，与提问应答面同一条「早一秒」的理由：表由编排层收，两条计时器同时到点时输的那一侧意味着表里留着一条再也投不出去的东西）。**起算点是「适配器已收工、只剩队列」那一刻**，不是条目自己的 `createdAt`——那会把一轮跑 30 分钟时的一条正常排队项误杀。到点该批落 `gone`（原因「等太久了」）+ 各一条行级事件；**今天没有一家接了唤醒路径，故四家一律走预算**。
- **行收场**：行落终态 ⇒ 该行所有还没投递的条目落 `gone`（原因「这一行已经结束」）+ 行级事件 + 清表。它与等待预算是**两件事**（前者管「这一行真的结束了」，后者管「还要等多久」），原因不同、界面上的话也不同。注入面与提问应答面**不互斥**：两格可以同时开着，那一刻这一行在等两样东西，收场时一起收。
- **追问**（对**已经跑过**的行：接着同一段上下文再跑一段）：**不 prepare**——`runRow` 那条路会整删 `workspace/` + `.agenthome/`，而 `.agenthome` 正是三家的会话落点，走它等于把要续接的会话删掉（症状是「追问之后智能体什么都不记得了」，静默且像模型变笨）；追问复用行工作区与既有会话，状态照走 `preparing`（复用那段已验证的竞态处置：落状态 → 让出事件循环 → **复检终止**，不复检会把行从 `canceled` 复活）。**计量口径与 `runRow` 相反、不可互换**：`tokens` / `turns` / `durationMs` **累加**（这些是人真花掉的）、`diff` 天然相对 `baselineCommit` 累计（工作区没重置）、`score` 由收尾**无条件自动重评**覆盖、**`attempts` 不变**——它答的是「这一行走过几次尝试」，而追问没有「从头」。追问**不进 `attempts.jsonl`**；每次追问落一条行级事件，行快照的两个计数各记各的（都**与写它们的那一段代码同段**）：`followUpRounds` 随那条事件一起加一（日志里那句 `[人工追问 ×N]` 读它）、`followUps` 随这句话落账本一起加一（卡片「人工消息 ×N」那个读数，与账本对齐）。拒绝面各给一句可直接展示的中文原因，**都不许静默从头跑**：正在运行中（该把话发进输入区排队）/ 上一次运行还没收尾（稍候再试）/ 没有可续接的会话 / 工作区已被删除 / 用例已删除 / 追问带的附件不存在 / 这一家不支持续接。追问**不自动重试**：一次追问失败之后该由人决定「再追问一次」还是「点重新执行」。**两个计数随「重新执行」归零**：那一步会 `resetRecords` 清空 `messages.jsonl`（下一次尝试是新的对话），而这两格的口径就是「与账本对齐」——留着旧数的症状是候选卡片的「人工消息 ×N」与空账本对不上，且下一次追问的段号 = `followUpRounds + 1` 会让新账本里第一个段标题写成「追问 ×4」（前三段根本不存在）。**`attempts` 刻意不在这一组**：它是累计事实，清零会让「试了三次才成功」看成一次就成功。**那一段自己的段号 = `followUpRounds`**（`AgentMessage.segment`，第一次跑那一段缺席即 0）：追问是又开一次 `run()`、厂商轮次从 1 重新数，两段的 `mergeKey` 会**逐字相同** ⇒ 账本的覆盖累积键与时间轴的轮次分组键都带段号（`(segment, mergeKey)` / `(segment, round)`，见《消息规范》），时间轴上以一行「追问 ×N」分隔。**段内的一切共用一个段号**：适配器投的消息（快照与增量两条出口）、人在这一段里插的话、那条追问自己的账本记录。行级事件带的是厂商口径的 `(subagentId, round)`（**里面有号没有段**）⇒ 同一号在多段出现时归**段号最大**的那一轮。

## 已知边界与取舍

| 边界 | 处置 |
|---|---|
| `AskUserInteraction` 的 `settled` 支的产出方在**编排层**：答复落进消息账本的 `tool-result` 那一半（`structured` 是契约的 `AskUserResultSchema`），卡片的**数据层**（`build-model` 的 `settledAskUserOf`）按 `callId` 跨账本配对后回填 | 只有在**这一轮开了应答面**（`EvalRun.askUser`）时才可能有答复——没开的轮次里那一支仍然走不到（那时一个提问都没有），卡片照旧显示「还没收场」；`unavailable` 这一档对应的正是「没有应答面」 |
| 挂起表只活在内存里：服务重启后旧 `askId` 一律应答不到（404），不是静默悬挂 | 有意如此（「待答」是只存在于内存里的一刻）；在跑的行由重启恢复路径收场 |
| **队列表也只在内存里**：服务端重启后旧条目不存在，那几句人话再也投不出去 | 与挂起表同口径（如实声明，不做持久化欠条）；界面按快照显示，不假装它们还在队列里 |
| **`consumed` 是惰性判定**：我们不为每一条已投递消息养一个厂商侧观察者，只在撤回尝试那一刻读一次厂商侧 | 刻意不做持续对账（有的家根本没有队列快照）；「已经交给模型了，撤不回来」这句话因此只在撤回那一次说得出来 |
| **`'idle'` 档在本轮收场那一刻才登记** ⇒ 同一条运行内几乎没有「撤回窗口」 | 这是 `'idle'` 的定义（这一整轮没活可干了）的必然结果，不是缺陷；刚点发送就发现它已经排队完毕是常态 |
| 在途取件的节拍 = 通知边界（端口没有「有新消息」的信号） | 界面上的「排队中」必须容得下这段延迟，**不许渲染成「已送达」**；输入区下面那行常驻提示就是为它写的 |
| 撤回能力按家分档：只有整条队列全清的家（pi）在 `delivered` 上**禁用按条撤回** | 声明驱动（`flush-only`）：`clearQueue()` 之后要重排其余条目，而「清」与「重排」之间的窗口会让重排的条目**第二次**进模型——拿一个会双份的机制实现「删除」比暂时做不到更坏 |
| 读不到这一家的能力声明（这一家整组没交，或元数据还没到）时输入区**置灰**，并如实说「读不到声明」 | 缺席**不读作支持**：猜错会让界面说谎（按钮可点、消息静默消失）；置灰 + 一句原因比编一份「都支持」诚实 |
| 追问的**入口可用性**是读侧算的（`followUpAvailability`）：七档拒绝里有的事实（工作区还在不在 / 用例还在不在 / 这一家的声明）浏览器一格都看不到 | 界面不自己编一句「这一家不支持续接」——读侧与写侧走同一个 `canFollowUpRow`，点下去与按钮上的话永远一致 |
| 追问那一段**不开提问应答面**（模型这一轮问不出「等人答一句」那个工具），但**照开人工消息面** | 两件事：应答面是另一条独立的面（挂起表 + 三个端点），要开得单独定口径；注入面与续接是契约的两格、正交，行在跑人就能送话 |
| `unsettled` 任何地方赋不出来 ⇒ **被强杀的子任务会永远显示「运行中」** | 要补装配层判据：收场事件没到 + 整行已终态 ⇒ `unsettled` |
| 真机密度与基线不一致：`/runs` 页抽屉在紧凑 `ConfigProvider` 之外（fontSize 14 / Tag 高 22），基线是紧凑数（Tag 21.4 等） | 二选一未裁决；在裁决前别拿基线数对真机截图 |

## 「候选未作答」这一格（`EvalRow.emptyAnswer`）

**它回答什么**：这一行的**候选阶段**有没有真的答出东西来。它存在的原因是：候选回**空答复**时，
行照旧走到 `judged`、照旧拿分，而**产物里原本没有任何字段**记下「它没答」——`messages.jsonl`
只剩考题那一行、事件流少一条答复 log。界面因此会把一次「没答」显示得和正常一样。

**三态，缺一不可**：

| 取值 | 含义 |
|---|---|
| `true` | 候选侧**没答**（运行成功、但没交出任何正文） |
| `false` | 候选侧答了 |
| **键缺席** | **未记录** |

**为什么「未记录」是键缺席、而不是 `false`**：对**旧的**行我们**并不知道**当时有没有答，
把缺席读成 `false` 等于**断言「它答了」**——而 `false` 恰好是要防的那个误读方向
（真出了空答复却照旧拿分的行，回看时反而显示正常）。同 `subagentTurns` 那条
「缺席 = 未采集、不与 0 混同」的口径；写法上它与 `subagentTokens` / `subagentTurns` 一样
用条件展开，**不把「没采到」写成一个值**。

**判据取自哪里**：适配器出口的 `(ok, finalText)` 两个已有值。**不需要适配器多交一格** ——
四家适配器的投影都「空正文不进 `finalText`」（codex 那边还特意显式排除空块，理由写在它的注释里：
写进去会把「没采到」伪装成「答复了空串」），所以「上游回空正文」与「压根没回话」在出口同形。
判「有没有正文」用 `null` 或**纯空白**，不依赖上游那条「空正文不进 `finalText`」的守卫。

**两条边界**：只由**候选那一趟**写（追问答了 ≠ 候选答了）；**重试会覆盖**它 —— 记的是
「最后一次候选执行」的观测结果，与 `tokens` / `turns` 同口径。⇒ 重置一行时它必须被**清掉**
（`delete`，不是赋 `null`），否则换了模型的行回到「待开始」时，卡片还挂着**上一趟**的断言。

**没答不等于没分**：`emptyAnswer: true` 的行照旧有 `status: 'judged'` 与分数 —— 这两件事一起看，
才是「它没答，但系统当时照常给它评了」这个事实；界面要把这一格显出来，别让它在读数里隐形。
