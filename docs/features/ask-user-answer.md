# 提问与应答

## 定位

评测跑起来之后，**模型会问人**：cc / codex / dsh 走厂商自带的提问工具，pi 走我们注册的宿主工具。

这一面回答「那一问现在在谁手里、人在哪里答、答完怎么回到模型那儿」。三层都在：**传输那一层**（待答提问的进程内真相源——挂起表——与对外的三个 HTTP 端点）、**编排那一层**（把提问登记进表、把答案落进消息账本与候选级事件），以及**界面那一层**（应答弹层 + 全局宿主）。编排那一层按轮**显式开启**（`EvalRun.askUser`，缺省关）：没开启的轮里编排层**不传回调**，一次都不调用，四家行为逐字不变——这也是「有人答」这件事事后可分辨的判据。

一条提问从发出到收场只经过两个事实源：**挂起表**（进程内内存，写侧）与**快照端点**（读侧）。两者不是两份数据，快照就是表的投影。

## 形态与交互

三条 HTTP 通路，都在 `/api/ask-user` 下：

| 通路 | 方法 | 请求 | 响应 |
|---|---|---|---|
| 待答快照 | `GET /api/ask-user` | 无参数 | `PendingAskUser[]`（裸数组） |
| 待答信号流 | `GET /api/ask-user/stream` | 无参数（SSE，无 `afterSeq`、无 `Last-Event-ID`） | `event: ask-user-changed` 帧 + 一行**空的** `data:`，**无 `id:`**；打开即 `: ready`，静默期 15 s 一条 `: keep-alive` |
| 应答提交 | `POST /api/ask-user/answers` | `{ askId, answers }` | `{ askId, answer: { outcome: 'answered', answers }, answeredAt }` |

状态码：首个应答 `200`；同一 `askId` 的第二份提交 `409 CONFLICT`；未知 / 已取消 / 重启过的 `askId` `404 NOT_FOUND`；请求体不合法或答案与问题逐问对不上 `400 INVALID_QUERY`（**不消耗**这一次应答机会——改一版重发仍然能答）。

快照里一条的形状（`PendingAskUser`）：`askId` / `runId` / `candidateId`（可为 `null`）/ `stage`（`'agent'` 或 `'judge'`，与 `EvalCandidate.error.stage` 同词表）/ `questions`（归一后的问题数组，与消息账本 `tool-call` 那一半同一份）/ `askedAt`。**不带宽商上下文**（工具名、调用 id、厂商等待预算）：那些只为回灌答案时取用，界面没有消费方；界面要的排障线索是 `askedAt`（等了多久）与问题条数。

一份答案沿用消息账本那一份（`AskUserAnswer`）：`{ header, selected, custom }`。**配对键只有 `header`**，`selected` 装**选项标签**；`custom` 的 `null` = 没写自己的话、`''` = 写了但内容为空。答案与问题**逐问对上**（数量与顺序都要一致）才收下——回灌进厂商钩子的那一份是按位置对齐的，错一次就是「答案配到了另一个问题上」。

**用户写的那句话在四家都到得了模型**，落点由问题那一格的 `allowOther` 决定（它表达「用户能不能自己写一句话」，弹层据此在选项之外画出自由输入框）：

| 家 | 这一格从哪来 | 弹层写的自由输入怎么回到模型 |
|---|---|---|
| cc | 恒 `true`——厂商的提问工具入参里没有这一格，而它自己的 schema 写明「'Other' 选项由界面自动提供」 | 单选取代选项、多选与选项**拼成同一个数组**，值与选项标签同走 `updatedInput.answers`（键＝题面文本） |
| dsh | 恒 `true`——厂商的答复项恒带可选 `custom`（「supplements a multi-select answer or replaces a single-select choice」） | 经应答者插件的答复批次 `{id, selected, custom}` 交回进程内服务 |
| codex | 厂商在题目上声明（`isOther`） | 与选项标签并入 `{answers: {<id>: {answers: [...]}}}` 同一个字符串数组 |
| pi | 宿主工具的入参 schema 里有 `allowOther`（我们自己写的） | 宿主工具同进程 `await`，答复直接渲染成模型看到的那段文本 |

界面上这两格的关系**按单选 / 多选分档**：

- **多选 = 并存**：自由输入是补充项，勾选的标签与那句话**都**进答卷（选项不因输入而禁用）；
- **单选 = 覆盖**：用户一写话，选项整组**禁用**（不可点选）、提交的 `selected` 为空数组；清空输入框 ⇒ 选项当场恢复可选。

上面那张表里四家都接得下这两档，但**区分度不一样**：cc / dsh / pi 都能让模型看出「哪几条是选中的、哪一句是用户写的」（cc 是数组里的不同元素，dsh 是 `selected[]` 加 `custom` 两个字段，pi 是两段渲染文本）；**codex 只有一个字符串数组**，两者进去后是一串平铺的字符串（信息不丢、区分不了）——这条边界登记在 `providers/codex/ask-user.ts` 的答复组装那一段。

这条口径的产出方是弹层（`AskUserPanel`）、消费方是复盘卡片与四家适配器；**消费方不得假设两格互斥**（多选两格同时有值是常态，而历史记录里单选也可能两格都有值）——见[《契约体系》](/architecture/contracts) 里 `AskUserAnswerSchema` 那段口径与[《Claude Code 接入》](/protocols/cc)、[《DeepSeek Harness 接入》](/protocols/dsh) 的《提问与应答面》。

既然配对键只有标题，**同一次提问里两条题目共用一个标题**（空标题也算）时，一份答复在结构上就说不清答的是哪一题 ⇒ 这一问在**发出前**整场收场为 `unavailable`，一次都不问人。刻意**不**折叠、**不**去重：那会静默改写模型实际问的是哪几题，而按题序另配一份答案等于给配对造第二个键，回灌时照样配错。

## 数据与契约

- **挂起表**（`@aieval/evaluator` 的 `ask-user.ts`）：`askId → { 定位（轮 / 候选 / 段）, 问题与厂商上下文, 提问时刻, 决议函数 }`。与编排层既有三条进程内总线（事件 / 记录 / 运行信号）同形——**挂 `globalThis`**，dev 的 HMR 会把模块作用域的表裂成两半（症状是连接开着、快照恒空）；表里存的是**决议函数**不是 promise，应答到达时当场结束等待，而「等」的那一侧（`Promise.race([等待, 候选终止, 预算])`）归调用方。
- **唯一的收口** `settle(outcome, answers)`：先出表、再决议、再发信号。三个调用点——应答（`answered`）、候选终止（`canceled`）、超时（`timeout`，由调用方的预算产生）。
- **已答名单**：答过的 `askId` 单独记一份只增不删的集合，唯一职责是把 **409 与 404 分开**（出表之后「刚才有人答过」与「这个 id 从没存在过」在表里长得一样，而客户端动作相反）。取消与超时不进名单：那一问没有被谁答过，此时到的人与「从没问过」是同一件事。
- **变更信号总线**：登记、答复、取消三处各发一条**无负载**的信号，订阅表与表同挂 `globalThis`。信号只推「变了，重读」——把清单塞进帧里，乱序到达时旧帧会盖住更新的缓存，快照就成了第二份真相。
- **契约**（`@aieval/contracts` 的 `ask-user.ts`）：`PendingAskUserSchema` / `PendingAskUserListSchema` / `AskUserAnswerRequestSchema` / `AskUserAnswerAcceptedSchema`，问题与答案两格复用消息账本那一份。`askId` 走**请求体**而不在路径里：这一问属于哪一轮哪一行已经在服务端的表里，放进路径只会让客户端为了拼一个 URL 先读一遍快照。

## 状态机与时序

```text
（编排层）登记 askId ──▶ 进表 + 发信号 ──▶ 客户端的信号流收到一帧 ──▶ 重读快照
                                                                        │
                        出表 + 决议 + 发信号 ◀── 校验逐问对上 ◀── POST /answers
                                 │
                                 └─▶ 等待方拿到 outcome: 'answered' + answers（继续这一次运行）

候选终止 / 超时 ──▶ settle('canceled' | 'timeout') ──▶ 出表 + 决议（answers: null）
```

三条不变量：

- **快照只含还没答的**：答复、取消、超时之后该问必须从清单里消失（出表与决议在同一处发生，顺序是「先出表」——决议会让等待方在同一微任务里继续跑，可能立刻登记下一问）。
- **首个生效**：`askId` 是幂等键。并发两份提交只有一个进表决议，另一份拿 409。
- **进程重启 = 表为空**：挂起表**不持久化**，「待答」是只存在于内存里的一刻，落盘只会造出一张重启后无人能兑现的欠条。重启后旧 `askId` 一律应答不到（404），在跑的候选走既有的重启恢复路径收场，不是静默悬挂。

**编排层是提问的登记方与答复的落盘方**（`@aieval/evaluator` 的 `ask-user-settlement.ts`，接在 `run` 的 `onAskUser` 那一格上）——这一层做四件事，口径都与「这一问」无关地成立：

| 环节 | 口径 |
|---|---|
| 开启闸门 | 按轮读 `EvalRun.askUser`；没开启 ⇒ 回调**一格都不传**，适配器那一侧连厂商钩子/开关/工具都不挂 |
| 登记与等待 | 登记进挂起表后等三方之一：有人答、候选终止信号、这一问自己的等待预算。预算取厂商给的（今天只有 codex 那一格会给）否则缺省十分钟 |
| 等待上限早一秒 | 编排层的上限比端口自己那条兜底**早一秒**到点：端口到点只是「不再等这一问」，它**不认识挂起表**——不先收掉，快照与弹层上会一直挂着一条再也答不了的提问 |
| 落盘 | 答复落进行的消息账本的 **`tool-result` 那一半**（`structured` 是契约的 `AskUserResultSchema`，问题那一半在 `tool-call`），并追加一条候选级 `ask-user` 事件（收场方式 / 等待时长 / 提问工具来源），两处共用 `askId` / `callId`；这一步正是只读卡片 `settled` 一支的产出方 |

三条配套口径：**答复是主事实、落盘是记录**（落盘失败只留 ERROR 日志，不改写交回模型的答复）；**落盘过与事件/消息同一条终态闸门**（行已落终态时适配器收尾期吐出的记录一律不落）；**子智能体提问的兜底在这一层**（请求带 `subagentId` ⇒ 立即落 `rejected`、不进挂起表——四家依据不同，这一句是唯一共用的那一点）。

## 前端宿主

应答面在界面上是**一个全局弹层**，不是每个页面各挂一份：宿主挂在应用根的 Provider 上（`apps/web-next/app/providers.tsx` → `AskUserHost`），任何页面、任何路由都能被它打断。它只做拼装，判定与文案在数据层（`@aieval/client` 的 `ask-user.ts` / `ask-user-queue.ts`，队列推进是纯函数，有独立用例）。

| 环节 | 现在是什么 |
|---|---|
| 订阅 | 挂载拉一次 `GET /api/ask-user`，之后由信号流推着**重读**；断线重连本身也当一条信号补读（信号不重放，不补就会漏掉断线期间登记的那几问）。信号帧的载荷是**空串**（内容由快照给），客户端只认事件名；但帧里那行 `data:` 不能省——SSE 规范里没有 `data` 字段的块**根本不派发事件**，省掉它订阅端一个事件都收不到，症状是「模型提问了，不刷新页面就一直不弹」 |
| 排队 | 顺序**就是快照的顺序**（挂起表按提问时刻给清单）；客户端不另排一次，否则「两次登记的间隙里读到过一次快照」会把后问的排到先问的前面 |
| 一次一条 | 只画队首那一问，换题按 `askId` 强制重挂（面板的步进与草稿是它的内部 state，重挂才不会把上一题的选择带进下一题） |
| 回传 | 点「完成」→ `POST /api/ask-user/answers`；**收到 200 才出队**。失败、409（别处先答了）、404（已收场）都让这一问留在队列里，原因用 `message` 提示，用户可以再答一次 |
| 关闭 | 关掉**不是**回答：不发请求、队列一条不少，只是这一问不再自动弹；右下角带待答条数的浮动入口是回到它的路 |
| 面板 | ui 包的 `AskUserPanel`：底部弹入、一题一步、四种作答形态；它不调接口、不提示错误，开关与在途标志全由宿主喂 |

三条不变量（每条都对应一次真实的误操作或误判）：

- **关掉不等于答**：误点叉或遮罩不会给厂商递一个空答案、也不会让这一问消失——行侧照旧在等，用户随时能从浮动入口回来答（最终由这一问自己的等待预算收场）。
- **多标签页不做所有权**：任一页答都生效；答完之后服务端推一条信号，两页各自重读快照，发现清单里没有它了就收掉弹层（本页没答过也照收）。代价是两页可能各弹一条，先答的那一份生效。
- **紧凑密度自己包**：全站的紧凑只在页面壳（`PageShell`）子树里生效，而宿主挂在页面壳**外面**（它必须全局可见），故由 `AskUserHost` 自己套一层 `compactTheme(mode)`——不套这一层弹层会按默认密度渲染（正文 14px，而页面上是 12px）。设置页那点差异接受：弹层是全局打断，按全站默认密度渲染是对的。

## 已知边界与取舍

| 边界 | 处置 |
|---|---|
| 回答的是**人**：值守的人不在时，这一问由它自己的等待预算收场 | 上限是「厂商给的预算 > 缺省十分钟」，且这一段时间算「还在动」（静止超时豁免），故不会永远挂着；代价是没人值守的轮会为空等烧掉这段时间 |
| 快照只在**挂载 / 信号 / 重连**三处读，没有定时轮询兜底 | 这三处覆盖了「有新提问」与「别处答了」的全部来源；真停在旧清单上时刷新页面即可（快照是权威读侧） |
| POST 的响应丢失（服务端其实已受理）表现为这一问仍在队列里 | 再答一次会拿到 409「已经被回答过」，用户据此知道它其实已经答完；不做本地乐观出队正是为了不把这种情形显示成「答完了」 |
| 只做「模型提问」，**不做工具批准面** | 工具批准是另一条通道；codex 的审批类服务端请求仍然只归类不回帧（提问类走另一条方法名，回帧） |
| 收场方式里的 `auto-resolved`（厂商自己到点收掉）**不是每家都有** | codex 的等待预算 `autoResolutionMs` 已 `@deprecated` 且实测恒 `null`、`isBlocking: false` 也不让它收场 ⇒ 那一家的每一次提问都由我们回帧收场（没人答回空表，收场落 `timeout` / `unavailable` / `canceled`），落不出「厂商自动决议」 |
| 收场方式里的 `skipped`（用户跳过）**今天没有产出方** | 弹层那条路走的是「允许空答案推进」——空答卷收场为 `answered`，不是 `skipped`；要有这一档，得先裁定「跳过」在界面上长什么样、以及它与「答了但都没选」的区别 |
| 多标签页不做所有权 / 租约 | 任一页答都生效，信号广播让两边同时收下；代价是两页可能各弹一条，先答的那一份生效 |
| 挂起表**跨进程 / 多实例不可用** | 单 Next 服务进程是既有前提，本功能不引入消息层 |
| 已答名单随进程寿命单调增长（每条约几十字节） | 有意如此：`askId` 是 UUID，命中它只可能是同一问的第二份提交；一份名单换一个准确的 409 |
| 子智能体提问按「不能向用户提问」收场 | 适配器那一侧先判（cc 看工具选项里的子智能体身份、dsh 侧厂商自己拒），编排层的回调**再兜一次**（请求里带 `subagentId` 就落 `rejected`）；两种情形都不进挂起表 |
