# 单行执行（只跑当前候选项）设计 — 2026-09-29

> 用户口径原文：「**重新执行，只执行当前候选项，不要完成后重新执行下方已经执行过的候选项**」。
> 路径分类：**bounded**（改的是仓里已有的单行执行链路：`retryRow` → `runRow` → `finalizeRun`），
> 设计在对话里过审后直接实施，没有单独的 plan 文档。

## 1. 问题

单行出口（`retryRow`）从一开始就**只动一行**，但它挂着一道硬前提
`canRetryRow = 不在跑 + baselineCommit ≠ '' + diff ≠ null`，也就是「**至少跑过一次**」。
后果：**没跑过的候选行**（`pending` / `skipped`）那一格按钮是禁用的，用户只能点「开始」——
而「开始」的语义是 `isRunnableRow` 判出来的**所有可执行行**（spec §5.3），
它会把本轮失败过的行一起重跑。「我只想跑这一个候选」在这条路上**无处表达**。

三行串行的典型形状：第 1 行已出分、第 2 行没跑过、第 3 行已出分。
用户要的只是把第 2 行跑起来；旧行为下唯一的按钮会把第 1 行的分钟级成本再烧一遍。

## 2. 决策

### 2.1 判据分两档（contracts）

| 判据 | 回答的问题 | 条件 | 谁在用 |
|------|-----------|------|--------|
| `canRunRow`（**新增**） | 能不能**就现在**把这一行跑起来 | `!isRunningRow` | 服务端放行、按钮 `disabled` |
| `canRetryRow`（不变） | **重**跑这一行有没有对照物 | 不在跑 + 有可比基线 + 有产出 | 按钮**文案**与确认框措辞 |

为什么不是把 `canRetryRow` 直接放宽：它回答的是「有没有对照物」，而「没跑过」恰恰是
**首跑的正常形态**——把两件事塞进一个判据，下一次要区分「首跑 / 重跑」时又要拆回来。
两者是**单调关系**：能重新执行 ⇒ 必然能单跑，反之不然（守卫在 `run.test.ts` 的 `canRunRow` 组里）。

### 2.2 一个按钮，文案按行态分叉（ui）

- 没跑过的行 ⇒「**开始执行**」；
- 跑过的行 ⇒「**重新执行**」（原有文案，一字不改）；
- **正在首跑**的行（`preparing` / `running`，还没有基线）也显示「重新执行」——它确实已经跑起来了，
  写成「开始执行」会让人以为还没开始。故文案判据是 `canRetryRow(row) || isRunningRow(row.status)`，
  不是单纯的 `canRetryRow`。

确认框同样分叉，且**都必须点名范围**（这句话就是用户那句口径的落点）：
- 首跑：「只跑这一个候选：本轮其他行（含已经执行过的行）都不会重跑。」；
- 重跑：「…只跑这一行，本轮其他行不动。」

### 2.3 允许与其他行并发（用户裁定）

本轮其他行在跑**不拦**单行执行（用户口径：「单行执行就是要现在只跑它」）。风险与手动点
「重新执行」同级，不是新增的：`retryRow` 的互斥只针对**这一行**（`rowAborts` / `retryTasks`），
它防的是「两条执行同时改同一行的状态」。

### 2.4 服务端只换判据，执行体一个字不改

`retryRow` 仍然是「同步落 `preparing` → 起 `runRow` → `finally` 里补一次 `finalizeRun`」，
只是放行判据换成 `canRunRow`，并按行态写不同的日志与事件标记（`[开始执行]` / `[重新执行]`）。
`retryRefusal` 因此收成一句**竞态兜底**：走到它只可能是「读快照时不在跑、落状态前那一拍它跑起来了」。

## 3. 不变量与守卫

**唯一承重不变量**：单行执行**只动这一行**——本轮其他行的状态、分数、计量、diff、`attempts`
以及它们的事件日志与尝试账本全都逐字不变，串行队列不推进。

守卫（`orchestrator-single-row.test.ts`，三行串行夹具：跑第 1、3 行后只跑中间那一行）：

1. 逐字比对两行的**全部字段**（`JSON.stringify` 相等）；
2. 两行的 `events.jsonl` 条数与 `attempts.jsonl` 条数都不变；
3. `fakeAgents.calls` 只多一次 ⇒ 真的只有这一行跑过。

## 4. 变异验证（每条守卫都见过它失败）

| # | 人为造回的缺陷 | 变红的守卫 |
|---|----------------|-----------|
| 1 | `retryRow` 的放行判据换回 `canRetryRow` | `orchestrator-single-row.test.ts` 两条 + `orchestrator-retry.test.ts` 一条 |
| 2 | 把单行任务接到**轮级** `executeRun` 上 | 同上（连带跑整轮） |
| 3 | `finally` 里顺带把其他可执行行也起一遍 | 「其他两行逐字未变」：`expected 'preparing' to be 'pending'` |
| 4 | `canRunRow` 抄成 `canRetryRow` 的复制品 | `canRunRow` 真值表 4 条 |
| 5 | 按钮的 `disabled` 用 `canRetryRow`、文案用 **不**含 `isRunningRow` 的版本 | `eval-row-card.test.tsx` 6 条 |

每处改完都还原并核对 SHA256 未变（`run.ts` / `orchestrator.ts` / `eval-row-card.tsx` 三个文件）。

## 5. 已知问题（本次**不修**，另行处置）

1. **`POST …/retry` 会被准备阶段阻塞**：`runRowAttempt` 的 `prepareRowWorkspace` 是**同步**重活
   （真 git 镜像 fetch + 复制 + checkout），而它跑在 `retryRow` 返回之前 ⇒ 远端仓库 + 冷镜像时
   该请求可能挂几分钟（实测一次 >5 分钟，客户端先超时）。既有的
   `orchestrator-retry.test.ts` 只断言「同步返回的快照是 `preparing`」，**不覆盖响应时延**，
   所以这条在测试里一直是绿的。
2. **强杀重启会留下在途锁**：服务被强杀（`next dev` 的 HMR 也会走这条路）时，
   被 `recoverInterruptedRuns` 标记为 `interrupted` 的行，可能仍有一个**活着的**
   `runRow` 任务与厂商 CLI 子进程留在旧模块实例里 ⇒ 那一行此后一律 409「上一次的运行还没收尾」，
   只能杀掉残留进程才恢复。同一次事故还观察到候选阶段的 `attempts` 计数出现一次丢失更新
   （快照 3、账本 2）。
