## ② 操作路径

1. **造夹具**（`PUT /api/runs/bea0564d-…`，全量行集合）：在原两行之间插入一个新的未跑过的候选行
   `8f3ea38f-446c-41c6-a04e-b9c0823c3c26`（codex · `jd/GLM-5.3-Flash` · likecode2），
   原两行带 `id` 原样回传以保住它们的成绩 ⇒ 得到「已出分 / **未跑过** / 已出分」的三行串行轮次。
2. 打开 `/runs?panel=detail&id=bea0564d-…`；
3. 在中间那张卡片上点「**开始执行**」→ 读弹层（`.ant-popover` 文本）；
4. 点弹层「确定」→ 观察网络请求与三行状态；
5. 轮询 `GET /api/runs/{id}` 直到该行落终态；期间用 `GET` 复核另两行**逐字**未变。

## ④ 未覆盖项与后续计划

1. **`POST …/retry` 的响应时延不达标（本次实测暴露）**：点「确定」后请求在准备阶段被**同步**
   占住（`runRowAttempt` 的 `prepareRowWorkspace` = 真镜像 fetch + 复制 + checkout），
   实测这一次超过 5 分钟才返回（浏览器侧先超时，用户看不到任何反馈）。
   既有用例只断言「同步返回的快照是 `preparing`」，不覆盖时延 ⇒ 计划：把准备阶段挪出请求路径
   （`prepareRowWorkspace` 之后 `yield` 或整体下沉进异步任务），并补一条「POST 在 1 秒内返回」的守卫。
2. **强杀 / HMR 会留下在途锁**：本轮冒烟中途改代码触发了 `next dev` 的重编译，被
   `recoverInterruptedRuns` 标记为 `interrupted` 的那一行**仍有一个活的 `runRow` 任务与
   `codex.exe` 子进程**留在旧模块实例里，于是后续重试一律 409「该行上一次的运行还没收尾」，
   直到手工杀掉残留进程。计划：恢复时清 `rowAborts` / `retryTasks`，并让适配器在父进程退出时
   带走子进程。
3. 同一次事故里观察到候选阶段 `attempts` 的一次**丢失更新**（快照 3、账本 2）——与第 2 条同源
   （旧实例的收尾写在快照上覆盖了新值），一并归到那一条处置。
4. 「在跑的行禁用 + 悬浮原因」的真机悬浮验证（`Tooltip` 挂 `span` 那条只能真机验的口径）
   留到下一次：需要一个正在跑的窗口，而本轮每个候选都是分钟级成本。
5. 本次冒烟**改了夹具**：轮次 `bea0564d-…` 现在多了一行（`8f3ea38f-…`，已 judged、100 分）。
   原两行的成绩与判定时刻一字未动，需要复原时删掉那一行即可。
