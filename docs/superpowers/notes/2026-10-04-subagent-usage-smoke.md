## 4. 发现：codex 的**嵌套**子智能体漏计（真缺口，未在本轮修复）

codex 那一行的 `.agenthome` 里有 **4 个 rollout**，事件流只点名了其中 1 个为 receiver：

- `01a107a6…` `source:"exec"`、无父 → 主线程（进合计）；
- `01a107a7-250e…` `source.subagent.thread_spawn.parent_thread_id=01a107a6…`、depth 1 → **depth-1 子智能体（被正确计入分量）**；
- `01a107a8-951e…` 与 `01a107a8-e992…` —— `source:"exec"`、**无父线程**、cwd 都是本行工作区、时间落在本行窗口内（16:04:11 / 16:04:32）。
  内容证据：前者的最终答复是 **`SUBAGENT_OK`**（子智能体握手语），后者在本行工作区里读 `index.html`、验 CDN 返回码、起无头浏览器复验——
  **两者都是子智能体**，但主线程的事件流**从未点名**它们（`collab_tool_call` 只出现在主线程，且只点名了 `01a107a7…`）。
  子线程 `01a107a7…` 的 transcript 里出现 `spawn_agent` 与 `01a107a8`，但没有 `collab_tool_call` 记录 ⇒ 它们是**由子线程派发的嵌套子智能体**。

**影响**：这两条的用量（归一后 `1773/8320/20` 与 `4424/202752/5626`）没进 codex 那一行的分量，
即该行的子智能体用量**少报约 6,197 / 211,072 / 5,646**（相对已计入的 34,828/975,360/17,081 约 15–20%）。
`attempts.jsonl` 只有 1 次尝试 ⇒ 不是重试串号；`receiver_thread_ids` 只在主线程出现 ⇒ 取数面结构上看不到嵌套。

**可行的修法（留给后续任务，需先定口径）**：
① 递归发现——读每个子线程的 transcript，从 `spawn_agent` 工具调用的**输出**里取新线程 id，逐层展开；
② 或「本行 home 里除主线程外的全部会话」——简单，但**会把同一行历次失败尝试的会话也算进来**（本仓实测有 14 次尝试的行），需要先按 attempt 划界。
两条都需要一条新的守卫与一次 spec 修订；本轮**未擅自改**。
