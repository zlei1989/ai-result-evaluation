# 密钥与环境变量

密钥管理横跨三层，每层各有不可逾越的硬边界。本文把散落在代码注释与工作规范里的密钥纪律收拢成一份现时口径：**key 只从环境变量读**是探测脚本的硬规则；**落盘明文、出口掩码**是供应商密钥的存储形态；**每行独立环境、绝不写宿主**是适配器的注入铁则。

## 定位

密钥与环境变量的读写规则，按所在层分三类：

| 层 | 密钥形态 | 硬规则 |
|---|---|---|
| 探测脚本（probe） | 网关 API key | 只能从环境变量读，源码出现明文 key 即缺陷、需轮换 |
| 供应商配置 | apiKey 落盘明文 | 落盘 `0600`，HTTP 出口只有掩码 `apiKeyMasked`，绝不回传原文 |
| 适配器运行期 | 注入子进程环境 | 每行独立 `HOME`，替换型构造，宿主 `process.env` 只读不写 |

三层共享一条横向纪律——**测试环境 ≠ 运行环境**：单测绿不等于真机绿，环境差异（打包器改写、解析器差异、子进程环境差异）必须在写用例时就被点名，否则假绿会漏进主干。配置目录的解析优先级为 `AIEVAL_CONFIG_DIR` > `~/.aieval`；测试一律用 `setConfigDirForTesting` 指向临时目录，绝不触碰真实 `~/.aieval`。

## 形态与交互

供应商密钥从用户输入到代调上游的完整流向：

```
用户输入 apiKey
  ↓
落盘 Provider（明文，写盘时 0600 收紧属主权限）
  ↓ HTTP 出口
ProviderView（剥掉 apiKey，只带 apiKeyMasked：前 3 位 + *** + 后 4 位）
  ↓ 运行期
适配器从落盘配置取原 key，注入子进程环境（替换型构造）
  ↓
厂商 SDK 读环境变量，代调上游网关
```

掩码函数的分寸刻意收紧：保留前 3 后 4，中间用 `*` 填满；长度不足 8 时整体掩码——避免前 3 与后 4 重叠导致原文泄露过多。空串返回空串，界面据此区分「未配置」与「已配置但隐藏」两种状态。

探测脚本（probe 系列）访问网关时，密钥一律走 `AIEVAL_PROBE_GATEWAY_API_KEY` 环境变量。历史版本在源码里留过硬编码 key，属已识别缺陷：它意味着该 key 已随源码入库，必须轮换，不能只删代码了事。

## 数据与契约

供应商密钥的契约是**落盘明文 + 出口掩码**的两面形态。落盘的 `Provider` 携带原 `apiKey`（服务端必须拿原 token 才能代调上游），对外的 `ProviderView` 用 `omit` 剥掉 `apiKey`、用 `extend` 补上 `apiKeyMasked`。这个拆分保证：HTTP 层无论如何写路由代码，都不可能把明文泄出去——出口形态本身就不含该字段。

适配器运行期的注入是**替换型**：以宿主环境为底构造新对象，把该行的 `HOME` / `USERPROFILE` / 厂商配置目录全部指到行级独立目录，再叠加厂商密钥变量。构造完成后交给子进程，宿主 `process.env` 一个字节也不动。三家厂商的注入变量：

| 厂商 | 注入的环境变量 |
|---|---|
| Claude Code | `ANTHROPIC_BASE_URL`、`ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`CLAUDE_CONFIG_DIR` |
| Codex | `OPENAI_API_KEY`（经 `env_key` 机制）、`CODEX_HOME` |
| DSH | 路由密钥经行级独立变量注入、`DSH_HOME` |

配置文件的写盘是**先建临时文件（创建即 `0600`）→ rename 覆盖**的两步原子操作，绝不先删目标再重命名——中间崩溃会让配置连同密钥一起彻底消失。

## 机制与演化

**为什么注入必须替换型而不是粘性写回**：评测是多行并行的，若把密钥写进宿主 `process.env`，第二行起就再也拿不到自己的路由——写入是粘性的，会覆盖第一行。替换型构造让每行拿到一份独立的环境快照，互不串扰。这也是「宿主环境只读」铁则的根因：写宿主不只是污染，还是并行的正确性缺口。

**为什么临时文件要在创建时就带 `0600`**：如果先按默认权限创建再 `chmod`，中间有一个短暂的可读窗口——同机其他用户能读到密钥。创建即收紧把窗口压到零。Windows 上 `chmod` 只能近似（NTFS 权限模型不同），尽力而为、不阻断写入。

**为什么配置损坏时抛「含路径的中文原因」**：密钥落在 JSON 配置里，解析失败最常见的形态是 `SyntaxError`。如果不包装，用户看到的是一行英文报错，排查方向被带偏。含路径的中文原因把「哪个文件、什么问题」一次讲清。

## 已知边界与取舍

- **探测脚本的硬编码 key 需轮换**：旧版本源码里残留硬编码网关 key，即便代码已改读环境变量，已入库的 key 本身已泄露，轮换动作不能省。这是遗留事实，不是可选项。
- **Windows 无 POSIX 权限位**：`chmod 0600` 在 NTFS 上只是近似，属主隔离依赖用户目录边界。跨平台硬隔离需要操作系统级凭据库，超出本仓范围。
- **测试环境 ≠ 运行环境**：单测的 mock 层（jsdom、注入桩）与真机差异是假绿的温床。写用例时必须显式点名「这条断言在真机上依赖什么环境条件」，否则单测绿只是自欺。已知的具体形态：打包器对动态导入的改写、子进程环境变量继承差异。
- **配置目录解析的两级优先**（`AIEVAL_CONFIG_DIR` > `~/.aieval`）是测试隔离的基础设施，但测试仍应显式用 `setConfigDirForTesting`——依赖优先级本身不构成隔离，显式指向临时目录才构成。
