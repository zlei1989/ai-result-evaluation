# 知识库口径

## 定位

`docs/` 原位构建 VitePress 知识库：`pnpm docs:dev` 起本地站浏览，`pnpm docs:build` 构建并重新生成 `docs/public/llms.txt`。知识按五域组织，接任务先按域找文章，别全仓扫描。本页定的是「写在哪、写到什么程度、什么时候写」的口径：五域分工、终态写作、关账回写，以及过程记录与知识库的边界。

## 形态与交互

### 五域

| 域 | 位置 | 收什么 |
|----|------|--------|
| 协议规范 | `docs/protocols/` | providers 抽象与 run 入口、消息与事件、进程生命周期、新增 SDK 接入流程、四家厂商接入与横向对比 |
| 功能说明 | `docs/features/` | 按功能模块组织的现时行为说明；目录层是《功能总览》 |
| 架构设计 | `docs/architecture/` | 分层与依赖方向、契约体系、界面原语与主题、工具链与命令聚合 |
| FAQ | `docs/faq/` | 四份厂商 FAQ 原文 + 目录层《故障索引》；按报错原文索引，可 grep |
| 规约守卫 | `docs/guard/` | 密钥与环境变量、冒烟方法论、变异验证、测试策略、注释与日志、知识库口径；PowerShell / Playwright MCP 两份活文档也在这里 |

### 目录层

- 全站地图：`docs/index.md`。
- 功能域目录层：`docs/features/index.md`《功能总览》。
- FAQ 目录层：`docs/faq/index.md`《故障索引》。
- `docs/public/llms.txt` 是构建期由 `docs/.vitepress/build-llms.mjs` 按 `pages.mjs` 生成的**副产品**（页面清单 + 一句话摘要），不是主判据。

### 过程记录与知识结论

- 冒烟记录落 `.scratch/<feature-slug>/smoke.md`；变异矩阵同目录。两者都带日期与证据链，是过程，**不进知识库**。
- 关账时把设计决策回写进对应知识文章的小节，**不新增过程档案**（ADR 0001）。
- FAQ 追加条目时同步《故障索引》目录层，少一条即未关账。
- 过程可追溯性交给 git 历史与 `.scratch/` 台账；知识库只收其中**能长期成立的那部分结论**。

## 数据与契约

**终态口径（知识文章与代码注释共用这一条）**：**只写终态**——「它现在是什么、为什么这样设计、当前有哪些已知边界与未证实项」。**不写过程**：日期、票号 / 需求号、评审编号、变更史（「原先」「曾经」「从 X 改成 Y」「已删除」）、实测与验证的叙述（哪次跑的、跑出什么、变异见了什么红）、提交哈希——一律不进文章、不进代码注释。理由：读者要的是「现在怎么用、为什么这样」，而过程文字会随代码腐烂成假话（改一处忘一处，比不写更坏）；过程的可追溯性交给 git 历史与 `.scratch/` 台账。

- **写使用视角**：读者是「要用这个功能 / 这个包的人」，写他拿它做什么、看到什么、按什么顺序操作、踩哪一格会怎样；内部实现只写到「用的人需要知道为什么」为止（含包名、函数名、契约字段）。反面是写给改代码的人看的实现导读——那样文章会被重构追着改。
- **与「关账回写」不冲突**：ADR 0001 要回写的是**结论与判据**（这条口径是什么、判据钉在哪、边界在哪），不是「这次是怎么发现、什么时候改的」。
- **实测数字分两种**：描述**现时约束**的留（「行内首次注入 17.2 s / 61 MB ⇒ 等待预算 ≥20 s」——数字是事实，也是设计理由）；描述**过程**的删（「某日实测发现 X，于是从 A 改成 B」）。
- **`docs/guard/` 的方法学文章同样只写做法与判据**；针对某一次改动的「实测记录」小节不留在知识库里。
- **例外**：**按四格格式写的 FAQ 条目**（厂商四份在 `docs/faq/**`；跨家 / 环境类的那几条落在它们各自的主题文章里，如《进程生命周期》）——那里的「日期」格写的是「这个故障何时被观察到」，是条目身份的一部分，不受本口径影响；判据是**格式**（现象 / 日期 / 根因 / 解决方案四格齐），不是文件路径。

## 机制与演化

**为什么只写终态**：文章是给「现在要用它的人」读的。过程文字（哪次跑出什么、从哪个版本改过来）在代码演进后迅速失真，读者无法分辨哪句还成立；终态文字只描述当前事实与依据，改代码时只需改一个地方。ADR 0001 把这一条落成纪律：知识文章取代过程档案，档案退役后不再新增。

**为什么 llms.txt 不是主判据**：它是构建期副产物（页面清单 + 一句话摘要），给机器快速定位用；路径稳定、文件可 grep、`AGENTS.md` 指针可导航才是「AI 读」口径。把 llms.txt 当主判据会让「生成器漏页」与「知识缺失」混为一谈。

## 已知边界与取舍

| 边界 | 处置 |
|---|---|
| 知识文章与活文档的边界 | 活文档（FAQ 四份、PowerShell / Playwright MCP）按「发现即追加」生长；其余按六节骨架写，只写终态 |
| 过程记录不进知识库 | 冒烟、变异矩阵落 `.scratch/<feature-slug>/`；知识库只收能长期成立的结论 |
| `docs/` 不是 workspace 包 | 测试收集靠显式路径 `docs/vitest.config.ts`；改收集方式后核对全仓用例总数 |
| 页面集合的真源 | `pages.mjs` 是站点配置、llms 生成器与内容守卫三方共用的唯一真源；新增 / 排除页面只改这里 |
| 单一真源 | 活文档位置即真源；仓内不得出现第二份副本（守卫钉死） |
| 构建期死链 | `ignoreDeadLinks: false`；nav / sidebar 只能链向已存在的页面 |
