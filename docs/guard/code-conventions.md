# 注释与日志

## 定位

注释与日志是两种不同的「写给下一个人的话」：注释解释**这段代码现在为什么这样写**，日志记录**运行期发生了什么**。两者共用一条时间口径——只写终态，不写改动史与验证过程；过程归 git 历史。

## 形态与交互

### 注释

- TS/TSX 用 JSDoc；中文，简洁、专业的口语，先说「做什么」再说「怎么做」。
- 文件头写明职责与注意事项。
- 方法、条件分支、事件处理、数据转换等独立功能单元都要说明业务目的与关键逻辑；嵌套超过 2 层必须注释业务含义；重要方法注释算法思路。
- 环境判断、响应处理等特殊处理要注释原因；密度在同文件内保持一致。
- 注释里的举例与实测数字要能**独立成立**：写「这一格窄了主标识会被截断」，而不是「某次量到 180px 不够所以调宽」。

### 日志

| 级别 | 场景 |
|------|------|
| ERROR | 业务异常、外部调用失败 — 必须打印堆栈和业务上下文 |
| WARN | 降级、重试、超时、配置缺失但可继续 |
| INFO | 请求入口、关键状态变更、外部调用耗时 >500ms |
| DEBUG | 分支走向、中间变量、循环关键节点（生产默认关闭，`AIEVAL_DEBUG=1` 打开） |

必须打日志的点位：请求入口（INFO + 标识）、外部调用（DEBUG 参数 + INFO 耗时）、异常捕获（ERROR + 堆栈 + 上下文）、关键分支（DEBUG + 依据）。

## 数据与契约

- 日志器是 `@aieval/core` 的 `createLogger(scope)`；各模块统一用它，不自己 `console`。scope 用模块名（`case-store` / `case-git` 这类），便于按来源过滤。
- 上下文一律作为 `console` 的**第二个参数**透传，**不要 `JSON.stringify`**：后者遇到循环引用或 BigInt 直接抛 `TypeError`，而它在 console 调用的实参位置求值，异常会冒进调用方——日志器不该有能力打断业务流程。Node 的 inspector 格式化能正确渲染循环引用与 BigInt。
- DEBUG 门控在**每次调用时**读 `AIEVAL_DEBUG`（`'1'` / `'true'`），不是模块加载时读一次；测试才能在同一进程里切换开关。
- 注释不是契约：能用断言 / 守卫表达的约束，写成守卫；注释只解释「为什么」。

## 机制与演化

**为什么注释只写终态**：过程文字（日期、票号、变更史、「原先 / 改成」、验证叙述）会随代码腐烂成假话——改一处忘一处，比不写更坏。读者要的是「现在怎么用、为什么这样」；过程的可追溯性归 git 历史。

**为什么日志上下文不序列化**：序列化在实参位置求值，异常会冒进调用方；日志器是诊断通道，不能成为业务失败源。结构化对象交给 console 的 inspector 渲染。

**为什么 DEBUG 默认关**：生产噪声与开销；需要时用 `AIEVAL_DEBUG=1` 打开。默认关闭不等于不能排查——WARN / ERROR 始终在。

## 已知边界与取舍

| 边界 | 处置 |
|---|---|
| 注释密度 | 同文件内保持一致；跨文件不追求统一长度 |
| 日志不是审计真源 | 运行期事实的持久证据在事件流 / 业务账本；日志只做诊断 |
| 敏感信息不进日志 | 密钥、凭据、token 一律不落日志（见《密钥与环境变量》） |
| 注释描述的数据措辞 | 「历史事件里的字符串形态」「旧 `run.json` 缺席这一格」这类描述**当前仍要兼容的数据**的措辞可以留，它不是改动史 |
