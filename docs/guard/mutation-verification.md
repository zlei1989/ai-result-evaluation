# 变异验证

新增回归守卫必须把要拦的缺陷人为制造回去、确认守卫失败、再还原并核对文件哈希——没见过失败的守卫不算守卫。

## 定位

规则真源是 `AGENTS.md`「约束」节原文：「新增回归守卫必须做**变异验证**：把要拦的缺陷人为制造回去、确认守卫失败、再还原并核对文件哈希。没见过失败的守卫不算守卫」。它针对的是本仓反复实测到的一类事实：**「看起来正确」的断言毫无区分力**——守卫全绿只证明「这一轮没踩到」，不证明守卫真的拦得住它声称要拦的缺陷。

最重的一次教训在 SSE 投递链路：api 发的是具名事件（`event: <type>`），客户端只绑 `onmessage`，真实浏览器里 7 种事件**全部没有接收者**——而两侧各自符合自己的 brief、单测各自全绿、真实链路零交付；client 侧 12 条 hook 用例与 24 个变异体**全部绿**。根因是测试替身**刻意不实现 `addEventListener`、`emit()` 一律喂 `onmessage`**（比真实浏览器弱），替身不忠实让守卫整体失去区分力。变异验证就是把这种「集体假绿」当面戳穿的动作：守卫必须**见过红**，才承认它有区分力。

适用面：**新增回归守卫时**——单测断言、静态扫描、行为判据（墙钟、进程形态）都算。计划里必须先写出「制造哪个变异体 → 期望看到什么失败输出」，没写这一步的计划不算合格的守卫计划。冒烟的真机绿不能替代它：真机绿只证明这一轮没踩到，见[冒烟测试方法论](/guard/smoke-testing)。

## 形态与交互

- **变异体**：把守卫声称要拦的那个缺陷**人为制造回去**——改实现，不改测试（改测试让测试红是显然的，说明不了守卫的区分力）。一个变异体只造一个缺陷；一处改动里有两个可分别变异的靶子时必须分两次做——只造 ① 时后者仍绿，会误判覆盖。
- **期望红先写**：动手前先写下「期望红在哪条断言 / 哪段报错原文」。跑出来红在别处，与全绿同罪——都说明对守卫的理解有误。
- **双向变异**：守卫既要见红（该拦的拦住），也要见绿（不该拦的不误伤）。根 eslint 边界规则按目录前缀化的验收就是双向的：core 里写 `import 'react'` 要报错、web-next 里同样的 import 不报错——只验前一半，前缀化漏掉会把 core 的禁用名单误伤到全部包。
- **负例要跨平台稳定**：判据「能红」要选在目标机器必然成立的形态；claude 的平台二进制守卫另用 freebsd（SDK 根本不发布的平台）做跨平台稳定的负例，避免「只在本机红过」的判据。
- **还原后必须复绿**：变异只许动实现；逐字节还原后守卫全绿，才算闭环。

## 数据与契约

变异矩阵是任务报告 / 关账记录里的固定契约，最小三列：

| 列 | 内容 | 口径 |
|---|---|---|
| 变异 | 把哪个缺陷造回去 | 指名到文件与改动形态（如「`close()` 退回 `child.kill()`」） |
| 期望红在哪 | 断言文本或报错原文 | 逐字，不是「会红」 |
| 实际结果 | 几条红、红在哪条 | 与期望逐字对照 |

- **红必须是断言或报错原文**：`Test timed out` 是噪声不是红，带负载机器上的超时先隔离复跑再定性；红要逐字命中（先例：`Cannot find module '@openai/codex-darwin-arm64/package.json'`，且只红对应那一条、其余仍绿，移回 ⇒ 7/7）。
- **红要落在业务面上**：集合型元数据的守卫先例——变异体「把 dsh 写成单元素数组」必须红在候选池 / 创建校验的正向用例上，而不是只红在元数据深比对那一条；只红在深比对等于没测到「放宽」这件事。
- **哈希契约**：`git hash-object` / `shasum -a 256` / `Get-FileHash` 任取其一，**同一个工具同一个值**贯穿基线与还原核对；还原后与变异前逐字一致（先例：claude 平台包内容挪空见红后还原，目录哈希 `c40269011cec3188e402d9179cd22028` 与变异前一致）。基线是**活值**：文件哪怕只改了两行注释，旧基线即失效，必须重取。
- **缺陷现象可复现最硬**：好的变异体把缺陷现象本身也造回来（先例：`configHome` 改回硬编码路径 ⇒ agents 守卫红**且** dsh overlay 变量同时红，仓库根重新长出 `aieval-route.patch.yml`）；三个变异体都见过红，还原后两份夹具的 sha256 与变异前逐字一致。

**脚本化矩阵（2026-10-09 先例）**：一次改动引入多条守卫时，把矩阵写成一次性脚本（`.scratch/mutation-check.mjs`，`.scratch/` 已 gitignore），一条命令跑完并逐条打印「守卫是否红 / 失败用例数 / 还原前后哈希」。每条的流程固定为：取 sha256 → 字符串替换制造变异（锚点不在就报「脚本要跟上代码」，不静默跳过）→ 跑对应守卫文件 → 从内存里的原文还原 → 再取 sha256 比对。那次是「用例从 `config.json` 搬成一文件一落 + 用例目录的 git 同步」，实测结果：

| 变异 | 期望红在哪 | 实际结果 |
|---|---|---|
| `case-store.caseFile` 去掉 `assertCaseId`（路径穿越） | `case-store.test.ts`「穿越型 id 连路径都拼不出来」 | 1 条红 ✅ 哈希一致 |
| 覆盖写改成「无条件先删目标再 rename」 | 「rename 失败时旧文件原封不动」 | 1 条红 ✅ 哈希一致 |
| `loadConfig` 重新读旧 `cases` 数组 | `config-store.test.ts`「旧 config.json 里的 cases 数组被忽略」 | 1 条红 ✅ 哈希一致 |
| `pushRemote` 的参数加 `--force` | 源码 force 守卫 **+**「分叉时 push 被拒绝，远端历史与本地提交都不动」 | **2 条红** ✅（静态与行为两条守卫同时开火，这正是「分层设防」要的形状） |
| `isRepoRoot` 改用 `--is-inside-work-tree` | 「只认「目录本身就是仓库根」」 | 1 条红 ✅ 哈希一致 |

- **「先红后绿」也是证据**：若缺陷在改动前就真实存在，那么「修之前它是红的、同一条命令修完转绿」与变异验证等价。先例：`core/src/mirror-fetch.test.ts` 的「没人监听的端口」在把 git 2.50 的原文（`Couldn't connect to server`）补进 `UNREACHABLE_PATTERNS` 之前就是红的，补完 9/9 绿——说明这条判据真的在盯 git 的 stderr 原文，而不是恒真。

## 状态机与时序

一轮变异验证的固定时序：

```text
取基线：待变异文件记 sha256；工作树里有未提交改动 ⇒ 先提交再跑变异矩阵
  └─ 制造变异体：编辑器改实现（中文源码禁用 PowerShell 的 Get-Content -Raw / Set-Content）
       └─ 备份带来源前缀：三家适配器各有一份 events.ts，备份名只取 basename 会互相覆盖
  └─ 跑守卫：确认红，且红在断言 / 报错原文；记录红输出与红的条数
  └─ 还原：反向 edit 逐字节写回（git checkout -- 只回 HEAD，不依赖它）
  └─ 核对：sha256 与基线逐字一致；git status 确认工作树干净
  └─ 复绿：守卫全绿
  └─ 记录：变异矩阵写进本次计划 / 关账记录；结论按关账回写纪律熔炼进知识文章（ADR 0001）
```

- **变异体存活（跑了仍全绿）⇒ 断言没有区分力**：改守卫改到能红，或删掉断言并把处置写进用例注释（先例：候选行形态守卫的 M4 反而全绿，该断言已删除）。不许静默放过存活的变异体。
- **行为判据同样可变异**：卡死类缺陷的守卫是墙钟——修前 62.4s 不退出、修后 7.66s 自行退出；变异把那条边造回去 ⇒ 60.01s 重新卡死，还原后哈希逐字相同。墙钟对比必须同时报用例总数与红数（快可能是因为少跑了）。

## 已知边界与取舍

| 边界 | 状态 | 处置与判据 |
|---|---|---|
| 替身弱导致守卫整体失去区分力 | 已发生过 | 12 条用例 + 24 个变异体全部绿而真实链路全死；**不具备 `addEventListener` 的替身不得用于验证订阅行为**，「替身是否忠实」本身要钉成断言 |
| 变异靶子要先验真 | 判据可能被推翻 | 「缺陷」若在依赖层行为等价（`undefined` 值的 config 键根本不外发），变异体本来就该绿；先跑最小判别实验，别拿红不出来的靶子硬凑数（先例：3 处 plan 变异判据被实现者实测推翻） |
| 属性断言没有可达的变异方向 | 不计入 | 「本地路径克隆只建一个本地分支」无论 `--mirror` 还是 `--bare` 都成立——按计划登记为属性断言，不为它强造变异 |
| 变异体可能产生真副作用 | 跑前评估 | 路径逃逸探针在守卫变异体存活期间，真的在系统共享临时根建了目录并写了 `run.json`（已清理）——探针会落盘的变异先想清楚再跑 |
| 守卫拦不住的形态 | 如实登记 | 平台二进制守卫只拦「resolve 不到 / 文件不存在」，「文件在但损坏」与 SDK 自身的 exists 检查同边界拦不住——写进用例注释，不装作拦得住 |
| `git checkout -- <文件>` 只回 HEAD | 还原坑 | 变异若加在未提交的改动上，还原会把那份改动一起抹掉；先提交再跑变异矩阵，或一律用反向 edit 还原 |
| 中文源码用 PowerShell 读写 | 禁止 | 会把 UTF-8 改坏（乱码 + `[PARSE_ERROR] Unterminated string`）；变异一律用编辑器改 |
| 逐个变异手工成本高 | 取舍 | 下限是「每条守卫至少一个对应变异体」，不为凑数批量造；靶子被实测推翻时宁可撤销，不硬造 |
| **夹具恒填空数组** ⇒ 跨家守卫天生无区分力 | 已发生过（2026-10-09） | 一致性套件新加的 §2.12「增量不产事件」按**事件条数**判，而 claude / codex / dsh 三家的夹具都把 `events` 写死成 `[]`（claude 那句注释还写着「避免与消息组的判据混淆」）⇒ 喂了增量帧、事件却恒为空数组，把 `events.ts` 的排除分支删回去照样全绿，而 claude 恰是唯一真的漏过的一家。**修法：先把夹具改成收真事件**（`onEvent` 早就在跑，只是返回值被丢掉），再让守卫断言条数。判据：夹具里出现 `events: []` 这类字面量，等于把「被测对象」换成了常量——**凡守卫读的那一格由夹具自述而不是由产品产出，先怀疑它没有区分力** |
