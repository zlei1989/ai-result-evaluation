# DeepSeek Harness 接入

## 定位

DSH（`@deepseek-ai/dsh-sdk-client`，`0.2.1-alpha.3`——该包从未发过非预发布版本，「稳定版」即 tag 线上最新的那一个预发布；三个 sdk 包的 `latest` 指的是远古的 `0.0.1-rc.*`，照它核版本会得出相反结论）是四家里两个「双协议一家」之一（另一个是 pi）：`protocolTypes: ['openai', 'anthropic']`，两条 wire 统一走 pi-ai 路由。适配器 = 路由注入（overlay patch）+ 通知投影（`session.event`）+ 关闭式释放（SDK 无 wire-level cancel）。续接走官方 wire 的 `session/resume`，见《注入与续接》。

## 形态与交互

- **SDK 入口形态**：`new DeepSeekHarness(options)` → `start()`（幂等 spawn + initialize 握手）→ `client.subscribeSessionTree(sessionId)` 拿通知流 → `run(prompt, { sessionId })`（下一次 idle 落定）。值出口 8 个（`DeepSeekHarness` / `HarnessClient` / `HarnessSession` / `JsonRpcResponseError` / `RequestTimeoutError` / `SdkProtocolError` / `TransportClosedError` / `validatedSessionEvent`）。
- **路由注入**：per-run overlay（`<configHome>/aieval-route.patch.yml`，经 `--patch <绝对路径>`——SDK 按**宿主进程 cwd** 解析相对路径，必须给绝对路径；`- id: llm-pi-ai` 定向覆盖；设置页的**自定义请求头**落在路由的 `headers` 块——按名字（不区分大小写）遇到 `llm-pi-ai` 的**保留头**（Harness 归属头）会被静默丢掉，值按字面发送、不做 `${ENV}` 插值；装配期它会过 `new Headers([[名, 值]])`，发不出去的一条会让整次启动失败 ⇒ 适配器先把发不出去的摘掉并 WARN）+ 子进程环境（`DSH_HOME`、`AIEVAL_ROUTE_API_KEY`、`DSH_PERMISSION_MODE`、**显式删除** `DEEPSEEK_*`——不显式删就会继承宿主，宿主有 key 时 `deepseek-official` 路由静默可用并悄悄计费）；**模型请求重试次数**（设置页「基础」→「模型调用重试」）写进**同一条路由**的 `retryPolicy: { mode: normal, maxRetries }`——执行者是 base profile 已挂的 `@deepseek-ai/dsh-llm-retry`（agent-step 级重试，正好对应「一次模型调用」）；`retryableCodes` / `backoff` 不写，保留厂商默认的瞬时码表与退避曲线；缺省时**整个 `retryPolicy` 块不出现**（= 吃厂商 normal 档默认 5 次）。`mode` 固定 `normal`：`always` 是无限重试，与「次数」这个设置项语义相反。
- **两条 wire**：`anthropic → anthropic-messages`（`POST {base}/v1/messages?beta=true`，`x-api-key` + `anthropic-version: 2023-06-01`）、`openai → openai-responses`（`POST {base}/v1/responses`，`Authorization: Bearer <key>`）。**不映射 chat-completions**（决策 D2）。
- **baseURL 归一化分叉是唯一正确解**：pi-ai 不做任何归一化（执行的级证据）⇒ anthropic 剥尾部 `/v1`（`stripV1Suffix`）、openai 补 `/v1`（`ensureV1Suffix`）由适配器做；写反会出现 `/v1/v1/messages?beta=true`。
- **effort 档位**（七种全接受）：`off → thinking:{type:'disabled'}` / `reasoning:{effort:'none'}`（**显式关闭**，不是不发字段）；`low / high / max` 原样（该网关七种 effort 全 200；「网关是否校验」是网关属性，换网关要重验）。anthropic 侧 `budget_tokens` 由档位名推（minimal 1024 / low 2048 / medium 8192 / high 16384，xhigh/max 夹到 high）且被 `model.maxTokens` 夹住。
- **停止通路**：`cancelMidTurn: false`——SDK 无 wire-level cancel（`HarnessClient.close()` JSDoc 逐字："There is no wire-level cancel: a timed-out request stays running server-side until the runtime is closed"）⇒ `interrupt()` 刻意空实现，终止走「等 5 秒宽限 → WARN → 强制关闭」（`RELEASE_GRACE_MS = 5_000`）。

## 数据与契约

- **协议集合判定**：`protocolTypes`（数组，替换旧单值字段——不留并存避免两份真源）+ 唯一判据 `acceptsProtocol(metadata, protocolType)`，四个消费点共用（api 创建校验 / api 候选池过滤 / 评分智能体校验 / 编排层复检）；拒绝文案抽成 `protocolMismatchMessage()`。不引入第三种 `ProtocolType`——供应商的 `protocolType` 仍是单值（协议是供应商的属性，集合是智能体的能力）。
- **通知外形**：`{method, params}`，method 只有四种：`session.event` / `session.status` / `subagent.started` / `subagent.finished`；事件全在 `session.event` 里，判别字段 `params.event.type`。事件序列：`turn/start → step/start → request/header → request/context → assistant/message → step/end → … → turn/end`；步数从 `step/start` 数——它数的是**厂商的 step**：一次尝试失败被重试时 `llm/retry-started` 把同一个 step 重新打开，于是 4 次真实 HTTP 往返可以只有 3 个 step（本仓口径与厂商一致）。
- **失败通道**：`turn/end` 的 `reason.kind === 'error'`；`reason.error` 两种形状都要认——结构化 `{message, code:"TRANSPORT"}` 与纯字符串（`errorChain` 折成 `{message, code:'UNKNOWN'}`）——否则失败运行被投影成普通日志、骨架 `ok:true, completed`。
- **逐消息用量**（这家独有）：`assistant/message` 的 `data.usage.{inputTokens, cacheReadTokens?, outputTokens, cacheWriteTokens?, totalTokens?}` 进消息信封。**缓存两格是条件写入**（`llm-pi-ai` 的 `mapUsage`：`...cacheRead > 0 ? {…} : {}`）⇒ 这两格缺席在语义上就是 **0**，不是「没采到」；而 `inputTokens` / `outputTokens` / `totalTokens` 三格**无条件写**，前两格读不到才是形状不对（那一条按未采到处置，WARN 里点名丢了什么）。`totalTokens` 是**这一条自己**的合计（不是累计快照）⇒ 与三格一样逐条相加，并按 `total = input + cached + cacheWrite + output` 校验，不成立就把 `total` 置 `null`（不给一个解释不了的数）。**没落成 `assistant/message` 的那次尝试也要算**：被重试掉的失败尝试只在 `assistant/attempt` 的 `data.stream[]` 末条 `usage` chunk 上带用量，漏读它就是静默少算（真机一次带重试的运行少算 24%，而厂商自己的 token meter 算它）。claude / codex 构造点 `usage: null`。真机：23 条 message 里 16 条带 usage、7 条 null（全是 role:'tool'）——页脚与 wire 0 处不符。消息级不进任何合计；候选级与消息级并存的差额来自流式中间帧与收尾投影（不带 usage 的投递）——不是对不上账。同一逻辑消息多次投递带的用量相同 ⇒ 合并器「带值覆盖、缺省保留」。
- **计量与计时**：`reasoningTokens` 恒 `null`（`llm-pi-ai` 的 `mapUsage()` 有意不投影，能力位 `not-projected-by-vendor`——不许拿 `outputTokens` 去凑）；`apiMs` / `ttftMs` 恒 `null`（载荷无时间字段，时间只在 `params.event.time`）⇒ `timing` 一律 `source:'events'` 且是累计口径。
- **子任务**：`agentId` 与 `childSessionId` 同值；名称 / 类型在 `subagent/catalog`；终态两格合读 `status`（ok/error）+ `stopReason`（五档）——取消是 `error + aborted`、截断是 `ok + max-tokens`，单读一个方向都会骗人。**派发调用 id 厂商不给**（`subagent.started` 只有 `{parentSessionId, childSessionId}`，SDK 的 `recordSessionRelationship` 也只读这两个 sessionId），而任务名与派发点是子任务行在界面上可达的前提 ⇒ 适配器自己**对账**：父会话 `tool/call` 记一笔「这次派发在飞」（`callId` + 入参 `description`），**工具名是枚举的两个**：`subagent` 与 `subagent_fork`——厂商把同一个派发插件（`@deepseek-ai/dsh-tool-subagent`）按 `dsh-base/cordis.patch.yml` 挂两次（`provider: spawn` + `toolName: subagent` 与 `provider: fork` + `toolName: subagent_fork`），两条路都投 `subagent.started` / `subagent/catalog`；只认前者时 fork 那条路的派发行永远拿不到 `parentCallId`（真机两臂对照：`subagent` 臂第一条之后就有值、`subagent_fork` 臂含补投那条在内全是 `null`）。`workflow` **不在**名单里：它派出的子智能体走的仍是 `subagent.*` 那两条通知（真机核实：一轮 workflow 里子任务行 3 条、带 `subagentId` 的消息 2 条），而一次 `workflow` 调用对应多个子智能体、按 `description` 认领必然零命中或多命中，`subagent/catalog` 到达时按「目录项 `label` ↔ 在飞派发的 `description` 逐字相同且唯一」认领，并把带名字与 `parentCallId` 的**运行行再投一条**（同一身份覆盖累积；收尾那条带同一格）。零条或多条命中时**不认领、不猜**——界面退回「任务名逐字相同」那条判据。
- **结构化输出走填充层**（SDK 客户端没有 schema 入参：`DeepSeekHarnessOptions` 只有 cwd / provider / model / reasoningEffort / maxTokens，argv 只有 `--profile` / `--patch`）。两件事：① 本次给了 `outputSchema` 就把 `buildStructuredOutputInstruction(schema)` 追加在调用方提示词**之后**（中性措辞，含 schema 原文与「只输出 JSON、不要围栏」；非对象按「没给」处置）；② 实现 `continue` ——骨架发现答复形状不对时回到这里，用**同一个 `sessionId`** 再跑一条 `harness.run(prompt, { sessionId })`，会话历史留在厂商进程里 ⇒ 模型手里保留工作区与自己的上一轮答复，只改形状、不重跑任务。因此 `applied.structuredOutput` **恒 `false`**：那一格记的是「有没有走原生 schema 通道」，提示词级填充不算（它是**方法**的如实记录，不代表没交付）。修正轮由骨架驱动、上限 **2 轮**（`STRUCTURED_OUTPUT_REPAIR_ROUNDS`），耗尽后 `ok` / `finalText` 保持最后一轮原样。

## wire 形态与事件

- **既成口径：用量与步数不按会话分叉**——事件投影只认 `event.type`、不按 `sessionId` 分流：`assistant/message` 无条件累进行的 usage、`step/start` 无条件 turns+1 ⇒ dsh 三格从第一天起就含子智能体，是构造上如此（有意并钉住）。分量（`subagentTokens` / `subagentTurns`）按候选子会话白名单求和；`dshSilentChildSessions` 是分量缺失谓词 + 收尾点名 WARN 的唯一判据。要改主 / 子两把尺子是另一次口径变更。
- **订阅先于提示词**：唯一事件通道是客户端订阅，`run()` 在下一次 idle 才落定；顺序错了丢开头那批事件（含 turn/start）⇒ 订阅由流自己建立，`start()` 不碰。
- **冷启动握手预算 60s**：SDK 默认 10s 不够（每个候选全新 configHome ⇒ 每次都冷启动，dsh 要解析整棵插件树才回 initialize；真机：空闲 4–7s 侥幸过、带负载两次超时，报错原文 `AGENT_FAILED  initialize timed out after 10000ms waiting for dsh profile "sdk"`）⇒ 显式 `DSH_INITIALIZE_TIMEOUT_MS = 60_000`。这类缺陷只有走真适配器的端到端能发现。
- **overlay 写入时序**：必须在 `new DeepSeekHarness(...)` 之前写好（dsh boot 时读装配清单；写晚了「run 结束后文件在」的用例照样绿而生产路由不存在）。
- **同源同算**（D7）：patch 里 `provider` / `model` / `reasoningEfforts` 与交给 harness 的三个值必须同源，dsh 的 `initialize` 会 `resolveCallConfig` 二次校验，漂移报 `UNKNOWN_MODEL` / `UNSUPPORTED_REASONING_EFFORT` / `no adapter registered for provider "…"`。路由键 `aieval-route` 不与安装态 pi-ai（`dsh-llm-pi-ai@0.2.1-alpha.3` 声明 `^1.1.0`）的 catalog 键撞车 ⇒ 走手声明路径；404 重试走 harness 的 `llm/retry`（实测 ×5），pi-ai 自己 `maxRetries: 0`，不会双重重试。
- **skills 接法**（SDK 客户端零 skill API，但运行时默认全开——「给 dsh 加 skill」= 让运行时看见文件，落在配置层）：本仓取**加法 A**——把清单整目录复制进 `<DSH_HOME>/skills/<名称>/SKILL.md`（= 候选配置目录的 `skills/`，与每个候选 `.agenthome` 隔离天然同构）；另外两条不用的加法是 **B** overlay 里 `skill-filesystem` 的 `customSkillDirs` + `includeDefaultRoots: false`（真隔离，⚠️ patch 替换整格 config 不深合并，要用的键必须全量重述）与 **C** 项目根 `.dsh/skills/` / `.agents/skills/` 自动发现（rank 100/200——静默口径差异，与 claude 的 `.claude/skills/` 问题同源同形）。
  - **skill 根表 rank**：100 project-dsh / 200 project-agents / 300 custom / 400 user-dsh / 500 user-agents / 600 bundled，rank 小者先赢同名，第一层扫描不递归 ⇒ 我们的落点是 **rank 400**，被测仓库自带的那两条（100/200）**压过**我们。
  - **时序：物化必须在 `new DeepSeekHarness(...)` 之前**——那是 boot 点，技能目录在那一刻进装配清单。写晚了这个候选照样「跑完」，但**没有任何 skill、也没有任何报错**（日志里连线索都没有），所以守卫必须在**构造那一刻**取快照，「run 结束后文件在盘」的用例对这条改动没有区分力。
  - **判据 = `user/message` 且 `source.kind === 'skill-catalog'`**：目录消息里逐条给名字（**没有来源、没有落点** ⇒ 来源分档只能记「来源未证实」，不许猜）；认不出的 `user/message` 照旧落原始 JSON（分流不是「静默丢掉不认识的消息」）。这条通道与 MCP 那条（`request/header` 的工具表）**各判各的**。
  - **没有按名字关的配置键** ⇒「停用」只能走文件级不放（被停用的根本不进清单）。
  - **隔离约束**：`dshHome` 指向空目录且无 `DEEPSEEK_API_KEY` 时运行必然 `turn/end(kind:'error')`（`llm-deepseek: no API key for provider route "deepseek-official"`）⇒ 走 pi-ai 后凭据走 `AIEVAL_ROUTE_API_KEY`，隔离目录不再隔离凭据。
- **MCP 接法**（本仓已落地）：SDK 的 JSON-RPC 方法表**封闭七个**（`initialize` / `session/prompt` / `session/resume` / `session/wait` / `session/working-directory/get` / `session/working-directory/set` / `shutdown`），服务端对未知方法直接抛错 ⇒ MCP **只能走配置文件**。一台 server = 一个插件行，**落点 = per-launch overlay（`<configHome>/aieval-route.patch.yml`）的 `insert`**——新增行必须走 `insert`（顶层 `- id:` 只能改或禁既有行）；`toDshMcpPluginLines` 一处翻译，空集一行都不插。逐字形状：`- id: mcp-<name>` / `name: "@deepseek-ai/dsh-mcp-client"` / `config: { serverName: "<我们的名字>", transport: stdio|streamable-http, command, args?, env? | url, headers? }`——`transport` 是 dsh 的两档（**不是** canonical 的 `http`），回包或请求里 http 的头**仍叫 `headers`**（与 claude 同、与 codex 的 `http_headers` 不同）。传输只有 `stdio` 与 `streamable-http`；`serverName` 须匹配 `[A-Za-z0-9_-]{1,32}`、`toolCallTimeoutMs` 默认 60000、`failOnStartupError` 默认 **false**（连接失败 harness 照常启动、工具静默消失）。stdio 子进程环境先清洗（`/KEY|PASSWORD|SECRET|TOKEN/i` 命中的与所有 `DSH_*` 被删）再合并 `config.env`——宿主的 `GITHUB_TOKEN` 不会自动传进去（这条也是验收项的检查点之一）。工具名 `mcp__<serverName>__<tool>`。
  - **判据只有工具表一条**：`request/header` 的 `data.header.tools` 里有 `mcp__<serverName>__*` ⇒ 已连上；表在、里面没有它 ⇒ **候选失败**（`AGENT_MCP_UNAVAILABLE`）——这一家起不来时工具**静默**消失、会话照常跑完、没有任何结构化错误（`failOnStartupError` 真假在观察面上无差异），**所以判据取不到「厂商状态」那一格，只能取工具表**。适配器据此每个 step 投一条 `vendor-system`（`mcpChannel: 'vendor-tool-table'`，只在表变了的时候发、每次交全量）。
  - 配置面与完整边界（含候选内 `.npmrc` 的 registry 注入、等待预算 ≥ 20 s）见[《MCP 配置》](/features/mcp-config)。
- **流式增量旁路**：通知层不投送逐字流（见「已知边界」），而打字机要 token 级增量 ⇒ 适配器**换一层拿**：`startDsh` 在 boot 前把一份零依赖插件写到 `<configHome>/aieval-stream-tap.mjs`（overlay `insert` 一条，`name: "./aieval-stream-tap.mjs"` 必须是**相对名**——运行时按 `dshHome` 解析），插件订阅 runtime 进程内的 `agent/assistant-stream`，把 `block-start` / `text-delta` / `reasoning-delta` / `block-end` 四类 chunk 帧追加写到 `<configHome>/aieval-stream-tap.jsonl`；父进程按 `DSH_STREAM_TAP_POLL_MS = 100` tail 该文件，折成 `session.event` 信封、事件类型 `aieval/delta`（`DSH_STREAM_DELTA_TYPE`）的伪通知，再由 `dshStreamDeltaDraft` 归一成 `chunk: 'delta'`、`source: 'hook'` 的内容消息。三条硬约束：① **绝不伪造 `session/event`**——runtime 对它是「先落厂商会话日志、再通知」，伪造型会混进厂商持久化日志（故走 sidecar 文件）；② 该支**只产消息、零事件草稿**（落进 `log` 兜底会把原始输出面板刷成 JSON 流水）；③ **会话门闸**——子会话的增量行可能早于 `subagent.started` 落盘，未登记的 sid 会被当主会话，故未知会话的伪通知**挂起**，等放行过 `subagent.started` 再补投。块位次按「该次尝试内首见顺序」发号（与厂商 `BlockAssembler.order` 同算法），保证增量与随后快照落进同一槽位。两条与增量帧形状有关的边界：**chunk 帧上没有 `turn` / `step`**（厂商 `AssistantStreamFrame` 只有 `start` 变体带它们）⇒ 伪事件里这两格恒 `null`，步数归属由「该会话已观察到的 step 数」回落给出（与快照同源 ⇒ 两条落进同一载体）；**旁路文件被整份重写**（长度不变或更长）也必须能被认出来——判据是「正常追加必然让长度增加」，长度为 0 增长而文件被动过、或已读过的头部 32 字节变了，就从文件头重跟（只看「变短」会把重写后的增量整段静默吞掉）。门闸**跨活动区间复用**：`close()` 的语义是「松开句柄 + 丢掉没放行的行」，不是「关掉这条通道」（首轮与每一次追问共用一个实例，每个区间收尾都会调它一次）。
- **内置工具清单**（26 项，`request/header` 原文顺序，首位是适配器 `insert` 的 `ask_user_question`）：`ask_user_question, bash, create_goal, edit, exit_plan_mode, get_goal, glob, grep, interrupt_agent, job_kill, job_list, job_output, list_agents, read, read_image, send_message, skill, subagent, subagent_fork, todo_write, update_goal, web_fetch, web_search, workflow, working_directory, write`。dsh ∩ codex = `create_goal / get_goal / update_goal / web_search`（精确同名）；claude 与另两家精确同名交集为空 ⇒ 命名不是对齐键。shell 工具是 `bash`（`pwsh` 只在 Windows 那一档出现）。

## 提问与应答面

厂商自带提问工具（`ask_user_question`）：`dsh-base` 与 `dsh-sdk-app` 两个 bundle 都不装 `@deepseek-ai/dsh-tool-ask-user`（只有 Web 的 preset 装）⇒ 适配器在 overlay 的 `insert` 里补一行。工具与提示词都是**厂商的包**，本仓声明 `askUser: yes` + `askUserChannel: 'vendor-tool'`，一致性场景走**真路径**（真运行时 + 本机假上游 + 适配器的应答者插件）。

| 面 | 现时做法 |
|---|---|
| 通道 | 厂商的提问走 runtime **进程内**的 Cordis waterfall `user-questions/request`（**return 一份 `{answers}` 即认领**、`next()` 即委派），**不投送到 SDK 约定的那条通道**（JSON-RPC 面只有七个请求、四个通知，没有「服务端问客户端」这一类）⇒ 应答者只能是一个注册在厂商进程里的**插件** |
| 递答案 | 适配器按「这一轮挂没挂应答面」把一份零依赖插件写到 `<configHome>/aieval-ask-answerer.mjs`，并在同一份 overlay 里 `insert` 一行（`name: "./aieval-ask-answerer.mjs"` 是相对名，由运行时按 `dshHome` 解析）。答案走**文件型双向 side channel**：插件把每一问连厂商的 `wait.callId` 追加进 `aieval-ask-answerer.jsonl`，适配器的桥认领后交给提问端口、再把答复追加进 `aieval-ask-replies.jsonl`，插件按该 `key` 取**最后一条**配得上的行；厂商把它渲染成模型看到的工具结果，形如 `{"answers":[{"id":"q1","selected":["选项 A"]}]}`；用户在弹层里自己写的那句话走同一批次的 `custom`（单选取代选项、多选与选项并进同一个数组），`custom` 为 `null` 时不带这个键——厂商按 `custom !== undefined` 决定要不要交给模型 |
| 等待预算 | 等待档**与应答面同源派生**：挂了应答面 ⇒ `mode: "timed"` + `timeout: -1`（源码在 `-1` 时回落**阻塞档**：既不设到点收场、又把 `wait.callId` 带出来，而 `mode: legacy` 那条路不带调用 id）；没挂 ⇒ `timed` + `timeout: 1`（无人值守下等人没有收益）。插件自己等答复的上限比端口的缺省预算长 120 秒——它只是「父进程那半整个失联」时的最后一道兜底，到点 `next()` 委派、由厂商以自己的收场结束那一问 |
| 收场 | 端口交回「收场了但没有答案」那六态时，桥写的是**委派**，由厂商以它自己的收场结束那一问——**不编空答案**（编一份空 `selected` 会被厂商读成「用户跳过了这题」） |

五条今天仍成立的边界：

- **没挂应答面时提问工具仍然挂着**（工具由适配器挂载、与应答面无关）：那一档没人应答时到点交回的是厂商设计好的**待答**结果 `{pending: true, callId, message}`（`message` 逐字写着「继续干有用的活、这不是跳过、不要当成许可」），而不是工具错误——阻塞档下才会是错误。
- **模型仍可自己给 `timeout: -1`**，那一支回落阻塞档、照旧报错 `no user-questions answerer accepted the request`（码 `NO_PROVIDER`）——厂商的工具描述本身就在引导它「必须有答复时才用 `-1`」，**宿主关不掉这个口子**。
- **「这个候选是哪一档」读的是装配产物**：dsh 从 `request/header` 里记下的**工具 schema**（`isTimedAskUserQuestionSchema`）判档、**不是**调用实参 ⇒ 档位只能落在装配产物上，不能靠调用时临时决定。⚠️ **两档的 schema 都带 `timeout` 参数**（真机逐字核过：适配器恒写 `mode: "timed"`，legacy 档不用），两档唯一的可见差异是 `timeout` 的**默认值**：挂应答面时 `(default -1)`、没挂时 `(default 1)` ——判据不能只看「有没有这个参数」。
- **子智能体发起的提问到不了应答者**：进程内服务在进 waterfall 之前先 `assertLiveRoot`（不是活着的根就抛 `CALLER_NOT_LIVE` / `DELEGATED_CALLER`）⇒ 交给提问端口的 `subagentId` 恒 `null`，本模块不做子智能体判定。
- **「待答」这一格契约里没有** ⇒ 它到模型眼里与**一个普通工具结果**无异（模型看到的就是那段 JSON 文本）。

## 注入与续接

「人往运行中的这一轮送话」与「接着一条已有会话再跑一段」是契约的两格（`AgentRunInput.inject` / `resume`），在这一家的落点如下——两档各走一条路，**都由同一个身份认人**（我们铸的 `messageId` / wire 回执的那个 id）⇒ 撤回按 id，同文本两条不会误伤。

| 面 | 现时做法 |
|---|---|
| `'idle'`（排队） | **wire**：`client.prompt(sessionId, blocks)` —— `session/prompt` 落厂商的 `followup` 队列，投递点是 `next-turn`（这一整轮没活可干了、另起一轮），一次调用就够 |
| `'round'`（立即发送） | **进程内插件**的 `agent.steer`（→ `next-step`，比 wire 早一档）。wire 上**没有**这条落点 ⇒ 只能照 stream-tap / 提问应答者那套成法写一支常驻插件：插件落 `<DSH_HOME>` 根、overlay 里以**相对名** `insert`，投递与撤回都经**一对文件型 side channel**（父进程写投递流水、插件读；插件写收据流水、父进程读；两边各自轮询） |
| 撤回 | 按同一个 `messageId` 经插件 `inbox.remove`。它的返回值**只有 `boolean`**（「还在不在待处理队列里」），分不开「已被模型吃掉」与「id 不对」⇒ 身份是我们铸的，故 `false` 读作**已被消费**（竞态里厂商赢了），等不到回执（5 秒）读作**说不出为什么** |
| 续接 | 官方 wire 的 **`session/resume`**（adopt 必须在该 id 的第一条 `prompt` 之前，见下），顺序是 `initialize → session/resume{sessionId} → session/prompt` |

**续接走官方 wire**：`session/resume` 自 `@deepseek-ai/dsh-sdk-jsonrpc-server@0.2.1-alpha.3` 起是官方 wire 方法，**本仓 pin 的就是那一版** ⇒ 留在 SDK stdio 形状上，因此**保住中途注入**、零自研。装到更旧的客户端时适配器如实抛错（不许静默开一条新会话）。另外两条**不用**的路各要放弃点什么：

- **自写插件整行替换 `sdk-jsonrpc-server`**（只覆写 `createSession`：先 `agents.resume`，仅在 `SessionPersistenceNotFoundError` 时回落 `super`）——代价是把厂商那约 300 行接过来维护。**不能做装饰器**：Cordis 服务能替换、不能包装（同名再 provide 被运行时硬拦），且 server 是插件 `apply()` 里的局部量、决策键是私有 `sessions` Map、transport handler 单槽 ⇒ 只能整行替换；
- **换 `dsh --profile headless --session-id <id>` 形状**——**丢失中途注入**（它一次只接一条 task）。这是那条路线的代价，不是 dsh 的普遍属性。

**版本事实的两处**：三个 sdk 包（`-sdk-client` / `-sdk-jsonrpc-server` / `-sdk-protocol`）的 `latest` 指的是远古的 `0.0.1-rc.*`，`0.2.0-rc.2` 曾是它们的 **`next`**，`0.2.1-alpha.3` 是 **`alpha`**（只有 `@deepseek-ai/dsh` 本体的 `latest` 才是 `0.2.0-rc.2`）⇒ 照 `latest` 去核「有没有新版本」会得出相反结论。**官方是「加一条方法」，没有把 `session/prompt` 改成 create-or-adopt** ⇒ 已存在的 id 不走 resume 直接 `session/prompt` 一律回 `already exists`，从未存在的 id 回 `not found`（不是静默新建空会话）。

四条接续接线要知道的边界：

- **adopt 必须在该 id 的「第一条 `prompt`」之前**：同一进程里对已 open 的 id 再 resume 会被拒（`SDK session is already open or opening`）。
- **resume 之后订阅到的通知流不回放历史**（只有本轮事件）⇒ 恢复判据只能是「暗号回读 + 磁盘转录」，不能拿通知流当证据。
- **SDK wire 上没有 cwd 比对闸**（headless 那条路有）：换 cwd 不报错，`getWorkingDirectory()` 回的是**记录里的**那个 cwd。
- **装到更旧的客户端时收到 `resume` 如实抛错**（中文原因），**不许静默开一条新会话**——那正是「用户以为在追问、智能体什么都不记得」的形态。

**声明的现状**：投递两档是 `yes`（真路径：真运行时 + 真插件 + 脚本式上游，判据是哨兵有没有进模型看到的那份请求体）；撤回两格是 `by-id`；续接那一格是 `yes` + `proofDriver: real-path`（`input.resume` 走 `harness.resumeSession(id)` → adopt 出来的 `session.run(text)`，`harness.run` 一次都不碰；正向判据在 `providers/dsh/resume-real-path.test.ts`——真运行时 + 脚本式上游，跨三个独立运行，判据是**第一轮的暗号出没出现在第二轮的入站请求体里**，并配一条不 resume 的阴性对照）。

| `turn/end` 的 kind 实测有 completed / error / **aborted**（子会话收尾 `{kind:'aborted', reason:{kind:'parent'}}`），类型面另有 blocked / max-tokens / interrupted / forked | 口径 | 非 `completed` 的收场落一条 WARN、**不改写结论**（与另三家同尺：截断 / 中止不等于这一轮白跑） |
| 厂商的**结构化失败码**（`LlmFailure.code`：`MISSING_CREDENTIAL` / `INVALID_CREDENTIAL` / `CONTEXT_WINDOW_EXCEEDED` …）以 `[CODE] 原文` 前缀进归因 | 已修 | 归因层在状态码分支之前认这三个码：凭证类 ⇒ `AUTH_FAILED`（与另三家的 HTTP 401 同一码）、超窗 ⇒ `AGENT_CONTEXT_OVERFLOW`（新增码，刻意不进 `TRANSIENT_CANDIDATE_RETRY_CODES`）。不认的代价是**确定性失败被自动重跑两遍**（`AGENT_FAILED` 在重试表里），而原因还指向「CLI 起不来」。真机判据：探针 `ctrl-cred-classify.mts` 三档（空 key / key 带换行 / `contextWindow` 给小 + 长提示词），守卫在 `agents/src/errors.test.ts` |
| 运行时长 `timing.totalMs` 的端点 = **我们识别到的会话事件**（`request/header` → 最后一条 `turn/end`） | 厂商形状 | 它**含**工具执行、重试等待、人工提问等待的墙钟；**不含**第一次模型往返（1.6~2.5 s）与冷启动 / 收尾（`run()` 墙钟比它多 ≈0.7 s）⇒ 短一轮的运行里拿它算 tok/s 会偏高。`durationMs` 才是墙钟 |
| `turn/end` 那条 `usage` 事件可能与同轮最后一条 `assistant/message` **逐毫秒同 `time`**、五格同值 | 厂商形状 | 去重（`sameUsage`）会把它判成「重复快照」而不发——**数字不受影响**（端点同 `time`），丢的是「本轮收尾」这条结构化信号；契约不要求每个 `turn/end` 必有一条 `usage` |
