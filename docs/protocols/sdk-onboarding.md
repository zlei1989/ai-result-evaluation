# 新增 SDK 接入流程

## 定位

给评测平台接一家新的厂商智能体 SDK 的七步接入清单与验证点。每一步都有可执行的判据；**顺序不能颠倒**——前三步（能力声明、入口定位、凭据传递）的缺陷只有真机能拦，后面几步拦不住它们：agents 包全绿也可能连挂「打包器把 `createRequire` 换掉」与「凭据 / provider 没传到厂商进程」两题。

## 形态与交互

**七步清单**：

| # | 步骤 | 判据 |
|---|---|---|
| 1 | 写**能力声明**：消息面五格（五态 × 五格）+ **注入面两格**（MCP / skills）+ **耗时量级**（`runScale`），`notes` 写清路由 / 模型 / 机器前提 | 契约层 schema 的 `superRefine` + 元数据回归网（`registry.test.ts`）；**每一格 `yes` 都要有产物级证明**（见「能力声明与产物互钉」） |
| 2 | 定**厂商入口的定位方式**，两条路各有各的坑：**子进程型**（spawn 厂商 CLI / app-server）必须**打包器免疫**——Next/Turbopack 会把 `import.meta.createRequire` 换成带 `[externals]` 的产物（报错原文 `The argument 'filename' must be a file URL object… Received '[externals]/@openai/codex/package.json [external]'`），做法是 `process.getBuiltinModule('module')` 取真 `createRequire` + 结果形状校验（`isAbsolute` 且不含 `[external`）；**in-process 型**（把厂商 SDK import 进本进程）另加四件：① **动态 import**——函数作用域懒加载，注册表查询不加载 SDK（`getProvider` 同步返回）；② **外部化**——包进 `next.config.ts` 的 `serverExternalPackages`，并在 `apps/web-next/package.json` 的 `dependencies` 逐字声明同一版本区间（外置包是运行期按裸说明符在产物目录逐级向上找 `node_modules` 定位的，少一处就 `MODULE_NOT_FOUND`）；③ **Node 版本闸**——厂商 `engines` 只是 npm 元数据、运行期不拦（包管理器顶多 WARN），要真拦得自己写；④ **WASM / 原生资产**——随包发的 `.wasm` / `.node` 不会因为「包被外置」就自动可用，先确认它读不读盘 | 静态层守卫（`static-assertions.test.ts`）＋真机冒烟第 ① 格 |
| 3 | 定**凭据与 provider 的传递**。**通则：宿主 env 是禁区**——并发多行时往 `process.env` 塞凭据会互相串（静态层用 7 种写法禁掉 `process.env` 写入）。两条落地形状按形态分：**子进程型**用**替换型子进程环境**（以宿主为底、覆盖 `HOME` / `USERPROFILE` 与厂商变量后整体交给子进程）；**in-process 型**走**内存 overlay**（内存凭据存储 + `modelsPath: null` + 内存 session / settings），并且**禁用会回落 `process.env` 的插值**——厂商自己的 shell 工具会把 `process.env` 交给被测 agent，密钥会直接落进被测仓库；并发多行下**每 run 自建 runtime + 唯一 providerId**（厂商的 provider 注册表常是按 id 索引的全局表，复用常量 id 会让两行互相改掉对方的 `baseUrl` / `apiKey`）。另两件与形态无关：provider 条目名与 `model_provider` 类字段**成对**给出；base_url 归一（该补 `/v1` 就补、该剥就剥） | 真机冒烟第 ② 格 ＋ **并发隔离的运行期用例**（两行同时跑、各自打到自己那台网关、密钥不串） |
| 4 | 写 fixture 场景，覆盖能力声明里所有 `yes` 的格；注入面的 `yes` 格给场景，**或**登记它的证明在哪一层 | 契约层「能力声明与产物互钉」+ **接入守卫**（`providers/conformance/onboarding.test.ts`，见下） |
| 5 | 接**生命周期**：取消能终止在途轮次、`dispose` 真正回收（**子进程型**杀整棵树并等 exit、清理遇 `EPERM` 有界重试；**in-process 型没有可杀的 child**——回收只能走 SDK 自己的会话 API，进程树那一层对它没有对象）、并把**静止判超时**这一层一起接上（见下） | 一致性套件「生命周期」判据（释放恰好一次 + 取消与声明一致） |
| 6 | 登记**缺失**：能力声明里非 `yes` 的格必须带 `MissingReason`（四句分工），不许静默空格 | 契约层两条 `superRefine`（消息能力格、注入面格） |
| 7 | 跑**真机冒烟**，把四格证据写进当次关账记录；关键判据额外要有一条**走真包、读真实出站请求体**的用例 | 见下 |

**接入守卫**（第 4 步的强制层）：套件的 12 组判据由各家自己在 `providers/<kind>/conformance.test.ts` 里
`import` 并调用，**没有总驱动**——少了守卫，「新家压根不写这个文件」不会让任何用例变红，套件再严也只是
自愿参加。`onboarding.test.ts` 把「参加」本身变成判据，三层：

| 层 | 判据 | 拦什么 |
|---|---|---|
| 目录与注册表 | `providers/` 下每个目录都在 `AGENT_KINDS` 里，反之亦然 | 加了目录没登记 / 登记了没目录 |
| 交 fixture | 每家都有 `conformance.test.ts`，且真的调用套件、交了 `scenarios` | 新家整份跳过套件 |
| 覆盖自家声明 | 能力声明里 `yes` 的格，其证明场景必须出现在 `scenarios` 块里；注入面 `yes` 的格要么给场景、要么登记 `injectionProofElsewhere`（守卫核对那份文件真的存在） | 声明与产物不符、登记造假 |

**翻一个 `yes` 要连带三处**（能力声明与产物互钉的完整形状）：① **能力格**本身（消息面五格 /
注入面两格，含它的 `notes`）；② **套件证明场景**（`scenarios` 块里那个能造出该块的名字，注入面走
`injectionProof`）；③ **场景计数登记**（`expectedEventCounts`——凡产物里有增量帧的场景都要给条数，
见套件那条「增量通道隔离」）。**三处缺一即红**，且三处由来不同：① 由 `checkCapabilityNailing` 运行期
对照，② 由 `onboarding.test.ts` 静态读源码比对，③ 由 `checkDeltaChannelIsolation` 运行期比条数。
`yes` 的含义是「产物级证明拿得出」——`skip`、`不适用`、`登记在别处` 都不构成 `yes` 的证明：
够不着的格只有两条合法出路，**降成非 `yes` 并给出 `MissingReason`**，或走 `injectionProofElsewhere` /
`lifecycleElsewhere` 把证明指到另一层（那时那个 `yes` 的证明在别处，而守卫会核对那份文件真的存在）。

判定方式是**运行期读声明 + 静态读 fixture 源码**：四家的 fixture 都在模块加载期用
`setAgentRuntimeForTesting` 注入各自的假厂商件（模块级），把四家 import 进同一个文件会让注入互相覆盖，
总驱动拿不到真 fixture。它判不出「场景名写了但产物是假的」——那一层由各家 fixture 的能力互钉与
`kit.test.ts` 的反例自测守。

**注入面（MCP / skills）的接入要求**：两条通路各有「我们发出去什么」与「厂商报回来什么」两份事实，
**互钉才算通过**。能力声明里 `injection.mcp` / `injection.skills` 用同一套五态 + `MissingReason`；
声明 `yes` 的家必须拿得出证明：

- **两份都给得出**：证明场景的产物挂 `injectionProbe`（请求侧）+ 带 `vendor-system` 事实（厂商侧）。
  请求侧事实只能由**假件在 run 期间记录**——cc 读假 SDK 的 `options.mcpServers` 与落盘的技能目录、dsh 读
  per-launch overlay 的插件行与技能目录、codex 读假 app-server 的 RPC 台账（`thread/start` 的
  `config.mcp_servers`，所以它那一格**起真 run** 而不是造 payload）。
- **够不着的格**（codex 的技能清单来自 `skills/list` 的**响应**）走 `injectionProofElsewhere` 登记它在
  哪一层被证明——登记不是免检，守卫核对那份文件真的存在。
- 声明非 `yes` 的格**不许**给证明场景（声明不支持却造得出事实，同样是自相矛盾）。

为什么两份都要：**只判厂商侧会放过「适配器压根没把入参交给厂商」**——夹具喂的厂商载荷照样产出那条事实，
套件全绿而 MCP 一台都没装到；只判请求侧则会放过「发出去了、厂商没认」。

厂商侧读 `vendor-system` 事件，且 MCP 那一格**两台通道合读**（服务状态表：cc 的 `mcp_servers[].status`、
codex 的 `mcpServer/startupStatus`；工具表：dsh 的 `request/header` 里 `mcp__<server>__*`）——只认服务表
会把 dsh 判成「没注入」，那是判据错不是它错。技能那一格看厂商侧非空清单。

**这一层拦的是「顺着写但漏了一环」，不是「成心骗」**：探针仍写在夹具里，刻意造假的接入者能把两边一起
写对。后者只有真机冒烟拦得住。

**生命周期（释放 / 取消）的接入要求**：这两条出口是**行为**，产物里没有它们的形状，所以各家交一个
**异步观测函数**（`ConformanceFixture.lifecycle`），套件在用例里 `await` 它：

```ts
lifecycle: async () => ({
  disposeAfterRun: …,      // 正常收尾后释放了几次（必须恰好 1）
  disposeAfterCancel: …,   // 取消之后释放了几次（同一口径）
  canceledMidTurn: …,      // 取消有没有真的终结在途轮次
}),
cancelMidTurn: provider.metadata.capability.cancelMidTurn,   // 声明；判据拿它与观测对照
```

三条判据：① 正常运行收尾后释放**恰好一次**（0 = 泄漏，>1 = 重复释放）；② 取消之后同样恰好一次；
③ `canceledMidTurn` 必须与**声明**一致——声明能中途取消却做不到，是这一层最该拦的假话。
证明不了的家在 `lifecycleElsewhere` 登记它在哪一层被证明（接入守卫核对路径存在）。

> `canceledMidTurn` 对声明 `false` 的家没有区分力（填 `false` 是必然的，如 dsh 的 5 秒兜底档）；
> 它拦的是「声明 `true` 却做不到」。

**结束信号要认厂商那一个，取消要在厂商真收到请求之后量**。两条都是「量得准」的前提，不是实现细节：

- **真结束信号唯一，不是「最后一条消息」**：`turn_end` / `agent_end` 这类之后还会有 auto-retry、compaction
  与排队输入（`steer` / `followUp`），拿「最后一条消息」当收尾会让紧接着的重试被算进下一行、或让整行提前收口。
  新家要在接入时指出**自己那一条**信号（pi 是 `agent_settled`，且它带 `aborted` 区分「谁停的」），
  并由套件的 lifecycle 观测把「取消 ⇒ 结论是被终止、且恰好释放一次」钉住（`checkLifecycle`）。
- **取消的判据要在「厂商已收到请求」之后翻信号**：装配冷启动期间翻停止信号，那一轮压根没进在途状态，
  量到的是**释放兜底窗口**（pi 是 5 秒）而不是取消——结论看着一样（照样 `canceled`），时序差一个量级，
  而 `canceledMidTurn: true` 这句声明就没被验过。两条相位各一条用例：**连响应头都没来**（在等首字节）
  与**已经开流**（正文没吐完）。翻信号的时机由假件的「第一次收到请求」钩子给（pi 的
  `runPiConformanceRow` 用 `firstRequest`），不是墙钟延时。

**新增守卫必须做变异验证，且「造不回缺陷」的守卫要如实点名**。判据是「能不能把要拦的缺陷人为造回去、
让这条守卫见红」——见红的守卫才算守卫。本仓有两条**造不回缺陷**的已知形态，接入时不要重复踩：

- **恒真守卫：拿同一个句柄现读的同一个表达式自比**。写成「探针工具表 == 从请求里现读的工具名」时，
  探针本身就是从同一个句柄现读的 ⇒ 比的是同一个表达式，对「注入整段没生效」一个字都不会说。
  破解法是**字面量**：出站工具表必须有 `mcp__probe__echo` 这一条（服务器名与工具名两处都由假件定死），
  见 `providers/pi/conformance.test.ts` 的「注入面探针挂载」。
- **同名同源的两份事实**：判据与夹具配置从同一个来源读（例如「声明的注入名单」从夹具的配置对象现读），
  给探针改个名两边一起变、守卫照样绿。破解法是两处**独立写下**：`injectedMcpServers: ['probe']` 写成字面量，
  改一处而另一处没跟就当场红（见 `kit.ts` 的 `ConformanceFixture.injectedMcpServers` 注释）。

**用量与成本：合计 = 主子 + 子分量，厂商自报的 `total` 不相加**。两格都是**合计口径**（子会话那一份
已经并进 `tokens` / `turns`），而界面按「主会话 = 合计 − 分量」推导——分量大于合计时那个减法是负数，
没有任何一层会拦，所以这条不变量由套件的 `checkUsagePairing` 在**每一次接入**上重判一遍。
「厂商自报的 `total` 不相加」是另一条：它是**单个会话 / 线程的累计快照**，两个会话的快照相加没有意义
（跨家口径各家不同），`total` 只能当证据读（`packages/server/agents/src/usage.ts` 的合并口径）。
「没采到」与「确实没有」也要分得开：分量取不到时记 `null`（或按家的口径记 `{0,0,0}` 并说明），
**绝不填 0 冒充「没花」**——零流量与零读数在界面上是两句话。

**并发隔离按形态分判据**：**子进程型**由静态层守——`static-assertions.test.ts` 用 7 种写法禁掉
`process.env` 写入，而「替换型子进程环境」是那条禁令下唯一可行的实现方式，故不必再造一个更弱的运行期判据；
**in-process 型**的载体正好是静态层拦不住的那一类（模块级缓存、按 id 索引的全局注册表、单例 runtime）
⇒ 判据必须是**运行期**的：每 run 自建 runtime + 唯一 providerId + 内存凭据，由「两行同时跑、各自打到自己
那台网关、各自的密钥不串」的用例钉住。

**「静止判超时」是第 5 步的另一半，新家必须一起接上**：本层**不设**内层超时、也没有整行级的兜底定时器
——「执行不限时间」不变，唯一的时限是骨架看门狗的两级**静止**上限（空闲 180 s / 单轮墙钟 600 s；可经
`AgentRunInput.watchdog` 覆盖、显式给 `0` 关掉那一级），`timed-out` 的**唯一生产者**就是它。它存在是因为
厂商侧的兜底在一类挂死上不成立（上游接了请求却既不回包也不报错，各家自带的流空闲容错在 300 s 上下）。
四条口径按家落地：

| 口径 | 内容 | 新家要做什么 |
|---|---|---|
| 有输出 | 「还在动」＝这一条投影交出了**任何产品事件**（行级事件 / 消息 / 子任务行 / 计量） | 确认自己的投影能把「在途但无声」与「对端挂了」分开；分不开就申请豁免 |
| 墙钟按一次往返 | 计时单位是**一次模型往返**，不是厂商的 turn（厂商一个 turn 常含多次往返） | 指出自己那条「往返结束」的信号 |
| 工具在途 | 工具在途可挂起两级计时，但只对「能合法静默」的家生效（默认**不豁免**：要放宽得先拿到「该家工具在途确实可能合法静默」的证据；代码侧是穷尽的 `Record<AgentKind, boolean>`，漏了编译期报错） | 给这一格显式定值 |
| 等待审批 | 「在等审批」不得判成静止；**识别机制按家不同**，采不到就如实登记这一格为「未豁免」 | 拿得出「待批准」事件就给判据，拿不出就登记 |

**宿主停机回收**也在这一层：`runTurn` 进出自动登记 / 注销在册会话，宿主的 SIGTERM / SIGINT 处理器调
`disposeLiveSessions()` ⇒ 新家只要做到「释放恰好一次」，这一格自动成立；`SIGKILL` 不可捕获，那一格不可闭合。

**耗时量级（`metadata.timing`）的接入要求**：声明这一家跑完一次运行是 `'seconds'` 还是 `'minutes'`，
外加这一格成立的**前提**（机器 / 模型 / 路由 / 任务规模）。

为什么是**量级**而不是精确数字：耗时由机器、模型、路由与任务共同决定，写一个精确值必然很快过期或
变成假话。量级则必须**有人消费**才有意义——真机冒烟的**等待预算按它派生**：声明 `seconds`，那一轮的
超时就是 1 分钟，跑不完会被自己的预算掐掉（红在产物格）；真机冒烟的 ⑦ 格再从结果侧判一次
「跑完了但远超声明」，即使预算被 `AIEVAL_LIVE_TIMEOUT_MS` 放大也照样红。

**已知边界**：这一层只有量级，没有精确基线——「这家比那家慢 30%」判不出来，本仓也没有 benchmark 口径。


**结构化输出这一格的接入要求**（每家都要面对入参 `outputSchema`，两种合法接法）：

- **有原生 schema 通道的家**：把它翻成厂商选项（`turn/start` 那一类一等字段），并**如实上报**本次有没有真的走成（`applied.structuredOutput`）——「厂商这一轮没照做」与「我们已经要求了」是两件事。
- **没有原生通道的家**：在适配器内部**填充**——首轮把 schema 约束（schema 原文 + 「只输出 JSON、不要围栏」）追加在调用方提示词之后，并**实现 `TurnStart.continue`**：骨架的修正轮靠它在**同一会话**里追问，模型手里保留工作区与自己的上一轮答复，只改形状、不重跑任务。
- **实现不了同会话追问的家如实收场**：答复不合格时骨架落一条 WARN，`ok` / `finalText` 保持原样，由调用方按 `finalText` 的既有契约处置（评分通路的落点是 `JUDGE_PARSE_FAILED`）——**不许假装合格**。两种接法的**保证强度不同、交付契约相同**。

**隔离序列**（新家的第一条硬约束，与「凭据不落盘」并列）：这一行跑在哪个目录、能看见宿主与**被测仓库**的什么，
由**一组开关**共同决定，只给 `agentDir` / `home` 那一格是**假隔离**——厂商的资源配置往往分叉在多个锚点上：

- **关磁盘发现**：厂商会自己扫项目目录与家目录（`.pi/extensions`、`.claude/settings.json` 这类）。
  被测仓库自带的那些是**它的内容**，但**执行**它们等于让被测仓库在我们的进程里跑任意代码 ⇒ 默认全关，
  白名单指回我们自己物化的落点。关发现与「用手册指路」是两件事：白名单通道**不受**发现开关管，
  故物化必须同时给绝对路径（相对路径按 cwd 解析，写错的表现是**一条都没有、也不报错**）。
- **对齐「该读的」与「不该执行的」**：被测仓库的 `AGENTS.md` 这类**上下文文件**是题目的一部分，别顺手关掉；
  项目技能要不要收，按「同名以谁为准」逐家确权——厂商的优先级顺序各家不同，我们这一层的口径是
  「本行白名单 ∪ 被测仓库自带」，且冲突**只作说明、不改结论**。
- **HOME 锚定的资源要单独过滤**：有些发现路径无条件可信（厂商的信任开关也砍不掉），
  只关项目层会漏进宿主个人档（技能 / 记忆 / MCP 配置）。凡「装上了没生效」「装上了却是别人的那一份」
  都先查这一格。
- **进程级全局路径是另一回事**：厂商若把某个路径硬编码成「只认进程级环境变量 / 家目录」，
  而本仓的硬不变量是**绝不写 `process.env`**，那这条隔离就**做不到** ⇒ 如实登记进知识文章的边界表
  （哪些产物落真实家目录、并发多行共享哪一部分），而不是在适配器里偷偷设一个环境变量。
- **判据**：行目录跑完只剩我们物化的东西（凭据 / 模型目录 / 厂商配置一个都不落盘）；需要真机才能判的那一格
  （真实家目录 mtime 未变）写进冒烟的四格证据。

**观测面与文案**（新家接完之后「用户看见什么」）：动手加 UI 之前先查既有组件能不能渲染——能力格、
「已超时」标签、MCP 观测格都是**数据驱动**的，今天渲染得出来的东西不必为第四家新开一个格。
三条口径：

- **沿用既有词汇，不新造**。同一件事在四家之间叫同一个名字（`子任务 · 这家结构上不支持` /
  `已下发的 MCP 服务 · connected · 判据 <哪条通道>`），跨家对比才不用先翻译一遍。
- **`notes` 是声明成立的条件，不是补充说明**。写「这家为什么只能这样」与「什么前提下这句话才成立」
  （路由 / 模型 / 机器 / 邻居行的影响）；能力随路由或模型变化的，把变化点写出来。
- **一句用户可见的话至少对应一条事实**：`notes` 与知识文章的边界表**两处同一次改**——
  改写措辞要一起改，否则界面上与文档里说的是两件事。

**第三方扩展 / 开源补齐的采纳流程**（能力整条来自我们之外的包时，五个环节）：

1. **先判有没有官方通道**。厂商自己有的（原生字段、公开选项、官方示例里的可复用件）优先；
   第三方只在官方**确实没有**时才是候选。
2. **逐案批准，不做默认采纳**。候选要过门槛：pin 到**具体版本**（并在 pin 的那一版上重跑审计，
   不拿上一版的结论当这一版的）、peer 依赖由本仓满足、**不带**与我们无关的附带面
   （skills / prompts / 自己的配置目录）、不要求我们 patch 厂商包。
3. **装载只走厂商的公开选项**。第三方包的入口字段可能全是空的、产物可能是 ESM-in-CJS ⇒
   自己 `import` 它的 `dist/` 会直接炸；用手册给的装载通道（扩展路径白名单一类）把它交给厂商自己的加载器。
4. **装不上绝不允许静默**：该行**失败并点名包名与版本**，码取 `AGENT_LOAD_FAILED`
   （「声明支持、实际没装」是假声明；归成厂商运行期错误的症状是「用户去查网关」）。
   装载断言判**厂商侧的权威面**（扩展表 / 工具表里真有那一条），不是「我们传了参数」。
5. **采纳的代价如实登记**：第三方缺陷、共享路径、并发影响、观测面外的那条捷径（模型可能绕开扩展
   自己拉起宿主 CLI 凑一个）——全部进知识文章的边界表，连带处置与判据一格。

**依赖声明面四处**（新增一家厂商包或第三方扩展包时，缺一处都是「编得过、跑不起来」）：

| # | 位置 | 为什么 |
|---|---|---|
| 1 | `packages/server/agents/package.json` 的 `dependencies` | **唯一真源**：区间写在这里，其余三处从它派生 |
| 2 | `apps/web-next/package.json` 的 `dependencies` | 外置包是**运行期**按裸说明符 / 按路径在产物目录逐级向上找 `node_modules` 定位的，pnpm 的隔离式布局不会把它链到应用侧；区间必须与 ① **逐字相同** |
| 3 | `apps/web-next/next.config.ts` 的 `serverExternalPackages` | 名单与 ① 同步；打进 server bundle 后包目录推导会失效 |
| 4 | `apps/web-next/src/runtime-deps.test.ts` 的例外表 | 只有写进 `BUNDLED_DEPENDENCIES` / `RESOLUTION_FORMS` 的名字才被排除在「必须外置且可解析」之外，每条例外都要写明理由 |

判据是 `runtime-deps.test.ts` 的三条断言（真解析、区间逐字相同、外置清单与派生集合逐项相同），
它会随 ① 自动长出新的检查项——**派生集合本身有判据**（「派生集合非空且不含工作区包」），派生被改窄成空集时那三条会静默全绿。
**别裸跑 `pnpm add`**：内网镜像缺平台可选包会直接
`ERR_PNPM_NO_MATCHING_VERSION`，且默认重解析会把厂商 SDK 声明的 peer 降级——口径是手改 `package.json`
+ 按「旧 lockfile + 新子树可达集」合并 lockfile，改完核对版本后缀并跑 `pnpm install --frozen-lockfile`。

## 数据与契约

**契约层 conformance 套件**（与厂商无关，任何一家都得过；一次接入的全部成本就是一个 fixture）：

```ts
describeProviderConformance({
  kind: '<kind>',
  capability: newProvider.metadata.messageCapability,   // 本家的消息能力声明
  injection: newProvider.metadata.injection,             // 本家的注入面声明（MCP / skills）
  injectionProof: { mcp: 'mcp-injection' },              // 声明 yes 的注入面格 → 证明场景
  scenarios: { 'plain-reply': () => …, 'thinking-full': () => …, subagent: () => … },
});
```

判据逐条挂在消息规范条目上（信封 / 内容块 / 行级事件 / 计量 / 能力声明与产物**互钉** / 子任务桥 / 环境 / 行结果 / 工具族 / 合并键）。**形状不在套件里重复写**——它由 `@aieval/contracts` 的 zod schema 管，套件只补 schema 表达不了的语义不变量（两份形状必然漂移）。

**测试里怎么替换掉真实厂商**：四家共用 `sdkModule` 一个注入字段（不另起名字），一张假模块表能同时喂饱四家；注入值不缓存（同一进程里能从「坏模块」换到「好模块」，验证「一次加载失败不会毒化后续运行」）；假件要**保真**（真生成器的排队语义、订阅关闭会 reject 挂起的等待者）——夹具悄悄变弱时用例只会**假绿**不会红，所以夹具自己也有回归网。

**旧数据兼容：新增枚举值安全，改名会丢历史行**。接入第四家要往 `AGENT_KINDS` 里加一个值，
而磁盘上已经有前三家跑出来的 `run.json` / 评分记录 / `events.jsonl` / `messages.jsonl`：

- **加值是安全的**——历史行只带老值，枚举扩了照旧解析得过。**改名不是**：老记录里的字符串会被
  schema 拒掉，而读侧对坏记录只 WARN 后跳过 ⇒ 用户在界面上看到的是「历史行凭空消失」，
  排查方向还指向存储。要改名的东西（kind 的取值、事件里的字符串形态）先想清楚历史数据怎么读回来。
- **展示面新增的格一律给默认值**：`ScoreResult` 的 `judgeAgentKind` / `judgeEffort` / `structuredOutput`
  都是 `.default(...)` / `.nullable().default(null)`——老记录里没有这一格，写成必填会让**已有评分记录**
  成片读不回来。
- **事件与消息契约里新增的格一律「可缺」**：历史 `events.jsonl` / `messages.jsonl` 没有它，
  写成必填会让回放与 SSE 续订成片解析失败；读侧把「键不存在」当「没采到」（`?? null`），
  与「采到了 0 / 空」分开。
- **编译期强制回答的清单会在加值时点名**：`Record<AgentKind, …>` 那几张表（中文标签、
  冒烟覆盖台账等）缺一格就是 `tsc` 报错——这是设计出来的，别把它当成噪声绕过去。

## 状态机与时序

**真机冒烟**（装载与传输两类缺陷的**唯一**拦法；默认跳过，不进内循环）：

```bash
AIEVAL_LIVE_SMOKE=1 AIEVAL_LIVE_KIND=<kind> \
AIEVAL_LIVE_PROVIDER_ID=<uuid> AIEVAL_LIVE_MODEL_ID=<model id> \
pnpm vitest run packages/server/agents/src/providers/live-smoke.test.ts
```

四格：① **装载**（没有落到入口解析 / 加载类失败）② **传输**（服务端记录的路由与本次选择一致、且不是凭据类失败）③ **产物**（跑到 `judged` 且有分数）④ **形状**（`messages` 接口的线上形态逐个过 schema）。`AIEVAL_LIVE_KIND` **必填**——不给默认家，避免「默认跑的那家绿了就当四家都绿」。

① 与 ② 判的是**失败归因**，读的是行契约上的那一格（`EvalRow.error.code` / `error.message`，可空）——行的形状
在测试里**直接取契约类型**，不另立影子接口：影子接口配 `as T` 强转会让字段名写错时静默通过（断言恒读到
`undefined`、那一格永远绿），而这两格是「装载与传输缺陷的唯一拦法」这句话的全部依据。

**真包证据：每条关键判据都要有一条走真包、读真实出站请求体的用例**。夹具与手搓 payload 判的是
「拿到这样一份载荷时我们读得出什么」，**不覆盖厂商在装配期做的裁决**——产品把工具整批滤掉时那种用例
照样绿。这一格有三处实例：① MCP 工具被会话白名单静默滤掉（`injection.test.ts` 的手搓
`requestPayloads` 从未经过真 SDK 的白名单交互 ⇒ 产品坏掉它照样绿，判据补在 `providers/pi/allowlist.test.ts`）；
② 出站请求里那一件 strict 工具是不是**原样**的调用方 schema（判据补在 `providers/pi/conformance.test.ts`，
它读的是可编排假网关收下的真请求体）；③ 注入面探针本身（`providers/pi/conformance.test.ts` 的
「注入面探针挂载」两条，用**字面量** `mcp__probe__echo` 钉出站工具表）。
判据的形状是「真包 + 假网关 + 读请求体」，不是「更严的断言」——**请求侧事实只能由假件在 run 期间记录**
（见《数据与契约》的注入面判据）。

**一条命令跑完几家**（日常用它，不必手拼四个环境变量）：

```bash
pnpm live-smoke                  # 跑全部有候选的家，逐家打印四格并汇总
pnpm live-smoke -- --kind cc     # 只跑一家（可重复给多次）
pnpm live-smoke -- --agent-judge # 连 ⑤⑥（智能体评分档）一起跑，七格全覆盖
pnpm live-smoke -- --dry-run     # 只检查服务与候选、打印将执行的命令（毫秒级）
```

`scripts/live-smoke.mjs` 从 `GET /api/runs/model-options` 取「哪家配哪个 provider / model」——那份知识
在服务端的候选池里（按 `acceptsProtocol` 过滤），脚本**不复制**它，也**不读配置文件、不碰密钥**。
跑完打印逐格结果与可粘贴进 `LIVE_SMOKE_COVERAGE` 的证据行；退出码 0 = 必跑格全过。

**绿的口径**：①②③④⑦ 是**必跑格**（跳过即异常），⑤⑥ 只在 `--agent-judge` 那一档有意义。
不给这个开关时 ⑤⑥ 跳过属正常，但汇总会写明「未覆盖」——**不让「绿」被读成「七格都验过了」**；
给台账的建议行也随之改写（默认档写「必跑五格通过」，开档且全过才写「七格全通过」）。

两个实测过的坑：`/api/cases` 的信封是 `{ cases: […] }`（不是裸数组）；vitest 的 `--reporter=json` 会
**吃掉**默认输出，于是前置失败（服务没起、用例 id 不存在）的原因既不在报告字段里也不在 stdout 里
——脚本因此同时挂 `--reporter=default`，并从输出里把原因抬成一行「↳ 前置失败：…」。

**单轮红先当噪声看**：真机通路会抖（同一候选、同一用例，上一轮 ③ 报 `文本 API 返回 HTTP 404`、
下一轮两条评分通路都通）。定性前先复跑一次，别把一次网关抖动写成产品缺陷或配置错误。

**判据住在 `src/testing/live-smoke-checks.ts`（纯函数），不留在那个默认跳过的文件里**：跳过意味着它们
从没有机会见红——装载那一格就因为读了行上不存在的 `errorCode` 而**恒绿**过。抽出来之后每格都有正反例
（`live-smoke-checks.test.ts`：喂一份合规的行不抛、喂一份对应缺陷的行必须抛），真机那一层只负责调用。

**覆盖台账**（`LIVE_SMOKE_COVERAGE`，同文件）逐家登记「这家怎么跑的、结论是什么」。它**不是机器验证**
——谁也拦不住随手填一句；它是一张**编译期强制回答的清单**：加第四家时 `Record<AgentKind, …>` 会缺格、
`tsc` 直接点名。值必须点名 `AIEVAL_LIVE_KIND=<kind>`，复制粘贴蒙不过去。

**同步点清单**（代码接完之后的一轮，漏一处就是「代码改了、知识库还在说三家」）：

| 面 | 位置 | 判据 |
|---|---|---|
| 协议文章 | `docs/protocols/` 的清单类文章（横向对比、`provider-run` 的能力值表与权限档表、消息规范的五态与 `MissingReason` 表、事件流、进程生命周期） | 逐表核到新家那一行；`grep -rc "三家" docs --include=*.md` 的非零项逐处判「历史叙述还是厂商清单」 |
| 功能文章 | `docs/features/**` 与 `docs/architecture/{layering,contracts}.md`、`docs/index.md` | 域内计数（「三家都会自动发现」这类）与新家的实际裁决结果对齐 |
| 目录层与导航 | `docs/faq/index.md`、`docs/.vitepress/pages.mjs` 的 `LIVING_DOCS` / `FAQ_DOCS`、`docs/.vitepress/config.mts` 的导航 | **守卫强制同步**（`kb-guards.test.ts`），少一处即红。**文档里不许引用 `.scratch/`**（它 gitignore，clone 读不到）——断链守卫按全仓扫 `.scratch/…` 路径引用，模板形态 `.scratch/<feature-slug>/` 与落盘目标除外 |
| 产物 | `docs/public/llms.txt` | `pnpm docs:build` 重新生成，**不手改**（它是构建期副产品） |
| 活文档与用户文案 | `AGENTS.md`、`packages/server/agents/README.md`、`apps/web-next` 里讲「哪几家 / 同名以谁为准」的用户可见文案 | 那句文案直接讲裁决结果，而新家的裁决与三家各不相同——不补就是界面在说假话 |

**独立复核环节**（本流程的最后一步，与真机冒烟并列）：实施者自审**抓不到**两类错——口径一致性
（同一件事两家写法相反）与规格符合性（逐条对照实现与规格），所以接入收尾要由**另一路**按双轴复核
（Standards：本仓成文规约；Spec：来源规格逐条）。两条纪律：

- **复核意见是断言、不是事实**：落地前先实测。判据冲突时以「契约 + 既有实现 + 实测」三者为准，
  顶回去要带证据——照单全改会把对的地方改坏。
- **复核对象是冻结的基线**（分支 tip / 提交），不是工作树：边审边改会让报告描述的那份代码不存在，
  也让「改完复核结论是否还成立」无从验证。

## 踩过的坑 → 必做判据

四条硬约束之外的**接入期清单**：下面每一条都是「照流程走一遍却仍然漏掉」的形态，按四类组织。
每条给四格——**现象**（能 grep 到的原文 / 关键词）、**为什么危险**（响亮失败还是**静默失败**）、
**判据**（守卫名，或如实写成证据要求）、**参考实现**（哪家哪个文件）。守卫名一律指**跨家**的判据层：
套件本体 `providers/conformance/kit.ts`、接入守卫 `providers/conformance/onboarding.test.ts`、
套件自测 `providers/conformance/kit.test.ts`，其余按路径点名；**只有这一接入里写的用例**归 `providers/<kind>/`。
工具链侧的坑（workspace 的 `allowBuilds`、「不裸跑 `pnpm add`」、eslint 边界规则前缀化等）见
`AGENTS.md` 的「边界与工具链的已知坑」表，这里不重复抄。

### 工具面 / 白名单类

#### MCP 握手成功，工具却不在出站请求的 `tools` 里

- **现象**：真包 + 本地假网关 + 真 stdio MCP 服务器跑一轮，握手全走完（服务器进程起来了、`initialize` 回了），
  而首个出站请求体里一个 `mcp__*` 都没有，**全程不报错**；厂商 SDK 的注释原文是
  `MCP tools kept registered without being named stay inactive`。
- **为什么危险**：<span style="color:#c00">**静默失败**</span>——「注册成功」与「被声明给模型」是两件事，
  中间那段落差没有任何报错，会话照常跑完，而 MCP 一台都没装上。
- **判据**：`providers/pi/allowlist.test.ts` 的两条用例（full 档：默认四件 + MCP 工具都在请求里；
  read-only 档：四件只读工具 + MCP 工具在，写能力**可证不在**），判的是**出站请求体**而不是我们传了什么参数。
- **参考实现**：`providers/pi/permission.ts`（两档白名单 + `PI_MCP_TOOL_PATTERN = 'mcp__*'`
  作**成员**拼进 `createAgentSession({ tools })`，不走 `+name` / `-name` 修饰符——修饰符形态会让白名单整个失效）。

#### 第三方扩展提供的工具同样被工具白名单滤掉

- **现象**：扩展装上了、扩展表里也有那一条，但它的工具（`Agent` 一类派发工具）不在请求的 `tools` 里；
  同一族的症状是「扩展表断言绿、模型侧看不见工具」。
- **为什么危险**：<span style="color:#c00">**静默失败**</span>——装配面上「装上了」与「模型可用」是两处读数，
  少一格不抛错；声明 `subagent: yes` 而实际调不动，是假声明。
- **判据**：**装配面**（假件）逐字含扩展工具名——`providers/pi/index.test.ts` 的
  「权限档落成工具白名单」；**真机面**（真包 + 真出站请求体）由 `providers/pi/allowlist.test.ts` 管，
  它才是「名单里的名字真的变成了模型可见的工具」这条的守卫。装配面还有一条：
  「扩展没装载 ⇒ 整行失败并点名包名与版本」（`providers/pi/index.test.ts`，码取 `AGENT_LOAD_FAILED`）。
- **参考实现**：`providers/pi/permission.ts` 的 `PI_SUBAGENTS_TOOL_NAMES` 拼进 full 档名单；
  `providers/pi/subagents.ts` 只交出扩展**入口的绝对路径**，交给厂商自己的加载器。

#### 只读档给了能写文件的派发工具

- **现象**：只读档的参数看着对（四件只读工具），实际跑起来子会话能改文件——派发工具能派一个
  **有写能力的子会话**，等价于把只读档绕过去。
- **为什么危险**：**权限提升**，且是静默的：行照跑、结论照出，只是被测仓库被写过了。
- **判据**：`permission.test.ts` 的「pi 的只读档不给任何子智能体扩展工具（`Agent` 能派发能写的子会话 ⇒
  那是权限提升）」；跨家的一条是 `permission.test.ts` 的「read-only 档在每一家都不给执行层写能力，
  且都不留人工批准的口子」。
- **参考实现**：`providers/pi/permission.ts` 的 `PI_PERMISSION_OPTIONS['read-only']` 只留
  `['read', 'grep', 'find', 'ls']`，派发工具只在 full 档。

### 隔离 / 环境类

#### 子会话与扩展把产物写进真实家目录

- **现象**：只跑一次 `--help`（本意只读）就在真实家目录长出 `~/.pi/agent/auth.json`、
  `~/.pi/agent/models-store.json`；并发跑两行时，子会话的 settings / memory / 转写也落在真实家目录。
- **为什么危险**：<span style="color:#c00">**静默失败**</span>——本仓的不变量是**绝不写 `process.env`**，
  而厂商的全局路径只认**进程级**环境变量与家目录；只给 `agentDir` 那一格是**假隔离**，
  测试环境里看不出来，隔离假设在真机上不成立。
- **判据**：**证据要求**——没有跨家守卫能拦「厂商把某个路径硬编码成只认进程级 env」。
  要求两条：① 接入期逐条核「隔离序列」的每一格（绝对路径 / 关磁盘发现 / HOME 锚定资源单独过滤 /
  进程级全局路径），把做不到的那格**如实登记**进边界表，而不是在适配器里偷偷设环境变量；
  ② 真机证据要有一条「真实家目录 mtime 未变」（写进冒烟四格）。本仓自己起厂商 CLI 或扩展的地方
  （探针 / 脚本 / 测试）一律**先把那个变量指到临时目录**——只设会话级目录变量的隔离不算隔离。
- **参考实现**：`providers/pi/conformance.test.ts`（子任务场景开跑前把 `PI_CODING_AGENT_DIR`
  指到临时目录，跑完还原）；`providers/pi/subagents.ts`（登记「扩展的会话目录不可注入」这条代价）。

#### 被测仓库的扩展目录会执行任意代码（装载发生在兜底钩子之前）

- **现象**：被测仓库自带 `.pi/extensions/*.ts`（或同族目录）被自动发现并**执行**；
  用 `extensionsOverride` 一类钩子当兜底时，钩子跑的那一刻代码已经执行过了。
- **为什么危险**：**任意代码执行**，而且是「装载即执行」——发现开关失效时装配面上不会出现任何异常。
- **判据**：`providers/pi/index.test.ts` 的三条运行期用例（发现来的扩展非空 ⇒ 按不信任项目重建装载器、
  仍挡不住 ⇒ 整行失败、我们自己的两类装载不被误伤），判据是「扩展表里的每一条都来自我们」——
  走的是**假件**（装配面），落点是「装载参数与扩展表」；静态面一条是
  `providers/pi/index.test.ts` 的「隔离序列逐条：绝对技能路径 / `noExtensions` /
  不设 `noSkills` 与 `noContextFiles`」。**断言位置本身是判据**：扩展表的断言必须在兜底**之后**读，
  否则读的是被丢掉的那一份。
- **参考实现**：`providers/pi/index.ts` 的 `createLoader()` 与它后面的兜底（重建失败时整行抛
  「扩展隔离失败：仍装载了 …」）；`providers/pi/sdk.ts` 注明发现开关**只筛发现路径**、
  白名单与内联工厂不受它管。

#### 凭据走了磁盘或环境变量插值

- **现象**：跑完一行，行目录里多出 `auth.json` / `models.json`；或厂商的 shell 工具把
  `${ENV}` 插值展开后，密钥落进**被测仓库**（它的工具拿着宿主环境）。
- **为什么危险**：<span style="color:#c00">**静默失败**</span>——默认的凭据存储会在**读一下**的时候就
  建出一个空壳文件，不抛错；插值那条更坏：密钥泄漏给被测 agent，而链路全绿。
- **判据**：`providers/pi/index.test.ts` 的「跑完行目录里只有物化的 skills（凭据与模型目录都不落盘）」
  （逐个点名 `auth.json` / `models.json` / `models-store.json` / `settings.json`，工作区也不许被写）；
  进程级写入由 `static-assertions.test.ts` 的「源码里不出现任何写入宿主环境的写法」封死
  （含裸令牌别名写入等写法）。**插值那一半没有守卫**——它是**证据要求**：接进来的装配面不许出现
  `${ENV}` 形态的键（厂商若提供插值通道，就别把宿主环境交给它），凭据只走内存 + 每 run 唯一的 providerId。
- **参考实现**：`providers/pi/index.ts` 的装配序列（内存凭据存储 + `modelsPath: null` +
  内存 session / settings，provider id 由本行目录派生）；`providers/pi/sdk.ts` 只校验
  「那个内存凭据类导出存在且可构造」。

#### 厂商写在共享临时目录的产物被另一行认领

- **现象**：扩展用 `os.tmpdir()` 加 uid 自己拼目录，不接受宿主传入的行级目录；并发跑两条 pi 行时，
  两行的子智能体转写都落进**同一个**共享目录。
- **为什么危险**：<span style="color:#c00">**静默失败**</span>——路径来源没有注入面，
  行级隔离在这一格上不成立；更坏的是**扫目录**：按「最近修改」或「目录里有什么」认领产物，
  并发的两行会互相拿到对方的子任务，界面与用量都串台而没有任何报错。
- **判据**：路径由**本行的 `cwd` 与本会话的 `sessionId`** 拼出，不扫目录
  （`providers/pi/transcript.test.ts` 的「路径 = `<tmpdir>/pi-subagents-<uid>/<cwd 编码>/<会话 id>/tasks/<身份>.output`」，
  以及「身份或会话 id 含路径分隔符时**不去拼路径**」——宁可当边界，也不碰一个可能指到别处的路径）；
  共享与清理的代价如实登记进边界表。
- **参考实现**：`providers/pi/transcript.ts`（路径公式与不扫目录的理由）。

### 观测 / 归属类

#### 子任务的步骤没以消息形式交付（界面时间轴缺段）

- **现象**：子任务行有终态与用量，点进那个节点只有一句「这个子任务没有逐条对话记录」；
  产物一侧是 `messages.jsonl` 里带非空 `subagentId` 的消息**一条都没有**。
- **为什么危险**：<span style="color:#c00">**静默失败**</span>——子会话是**另一个会话**，
  它的事件不进父会话的订阅流，投影层从来没有机会挂归属键；行照跑、分照打，界面只是缺段。
- **判据**：`providers/pi/transcript.test.ts` 的「助手行各占一轮（1..N），工具结果沿用当前号，
  且逐条带 `subagentId` 与 `session-file` 来源」「工具结果靠 `parentCallId` 配回它的调用块」
  「文件缺失：空消息 + 一条点名原因，一次都不抛」；`providers/pi/events.test.ts` 的
  「收尾把子会话转写折成子任务的消息」与缺失时不改结论那条；跨家的一条是套件的
  `checkSubagentBridge`（`parentCallId` 指向真实工具调用、`parentSubagentId` 指向真实子任务或 `null`）。
- **参考实现**：`providers/pi/transcript.ts`（收尾读扩展写的逐 agent 转写文件，正文复用既有的
  助手 / 工具结果归一，逐条盖上归属键与来源）。

#### 拿 `log` 事件找归属

- **现象**：拿执行日志翻「这条是哪个子任务说的」——找不到，也没有任何一格能挂上去。
- **为什么危险**：**白费排查时间**（判据本身不成立）：`log` 事件在契约里没有归属格，
  界面也不把 `log` 折进时间轴；它是「原始输出」面的东西，与时间轴是两条通道。
- **判据**：套件的 `checkLineEventsAndSources`（事件类型与消息来源都必须落在**契约的闭集**内、
  `log` 必须带 `stream`）——闭集从 schema 派生，不手抄一份。归属只在**消息**上，
  由 `checkSubagentBridge` 与合并键公式（`mergeKeyOf`）管。
- **参考实现**：`providers/pi/events.ts` 的三档处置（产消息 / 产事件 + 计量 / 其余落 `log`）。

#### 同一身份被投递两次

- **现象**：同一子任务在产物里出现两条行（`Agent` 工具收尾投递一次、骨架收尾对账又投递一次），
  界面上重复一个节点。
- **为什么危险**：**响亮失败**（数量对不上看得见），但成因在跨家约定那一层：骨架**允许**同一身份多次投递
  （后者是完整快照，「收尾才拿到终态」是合法形态），**收敛责任在适配器**；
  同一条约束的另一半是「**名字在派发那一刻定，收尾不许改**」——收尾改用总线描述会让界面在收尾那一刻换标题。
- **判据**：`providers/pi/events.test.ts` 的「同身份同内容只出一条」（逐字相同的重发在收数器里挡掉）；
  套件的 `checkSubagentBridge` 管身份与状态的取值口径。
- **参考实现**：`providers/pi/subagents.ts`（两条投递通路的收数与去重）。

#### 拿厂商轮号当归属键

- **现象**：拿 `AgentMessage.turn` 当「对齐没对齐」的判据，结果恒 `null` 或恒相等。
- **为什么危险**：**判据错**（不是产品缺陷）：那个格是**厂商轮号**，可空；
  界面按 `subagentId` 把消息分给会话节点、按 `roundTrip` 给每个节点分轮——归属键与轮次是两套东西。
- **判据**：套件的 `checkMergeKeys`（合并键必须等于公式
  `<subagentId ?? 'main'>|<roundTrip>|<role>|<parentCallId ?? '-'>`）与 `checkContracts`
  （消息与子任务行逐个过契约 schema）。
- **参考实现**：`providers/pi/message.ts` 的轮次口径（一次模型往返 +1），子会话的轮次按
  **该子会话自己**的往返序从 1 起（`providers/pi/transcript.ts`）。

### 装配 / 依赖类

#### 厂商声明的运行时版本要求没人自检

- **现象**：厂商 `package.json` 的 `engines.node` 写着一个下限，而本机版本更低时包照常加载，
  错误在别处以与版本无关的症状冒出来。
- **为什么危险**：**响亮但误导**——`engines` 只是 npm 元数据，运行期不拦（包管理器顶多 WARN），
  失败面因此指向别处，排查方向整个错。
- **判据**：`providers/pi/sdk.test.ts` 的一组用例（下限取自真值、含等于下限即通过、
  低于下限抛 `AGENT_LOAD_FAILED` 并点名下限与本机版本、生产路径默认读宿主版本、
  **版本闸先于形状校验**）。
- **参考实现**：`providers/pi/sdk.ts` 的版本闸（自己比一次 `process.versions.node`，
  只看 major/minor——字典序下 `22.9.0 > 22.19.0`，会把不合格的运行时放过去）。

#### 自己 `import` 第三方扩展的 `dist`

- **现象**：直接 `import '@<vendor>/<ext>/dist/index.js'` 时抛 `SyntaxError`（包没有入口字段、
  产物是 ESM-in-CJS）。
- **为什么危险**：**响亮失败**，但容易被「绕过它」修掉：真正的问题是装载通道错了——
  自己 import 等于绕开厂商的加载器，扩展的上下文 / 生命周期都不在厂商那一侧。
- **判据**：装载只走厂商的公开通道（扩展路径白名单一类），装载断言判**厂商侧的权威面**
  （扩展表 / 工具表里真有那一条），不是「我们传了参数」；装不上时该行**失败并点名包名与版本**，
  码取 `AGENT_LOAD_FAILED`（见 `providers/pi/index.test.ts` 的三条：扩展没装载、解析不出入口、
  兜底重建后仍不干净）。**静态层**：`static-assertions.test.ts` 的「厂商包只能动态 import」
  （顶层静态导入会把「一家故障」放大成「整包不可用」）。
- **参考实现**：`providers/pi/subagents.ts`（把入口的**绝对路径**交给厂商自己的加载器，不 import 产物）。

#### 依赖声明面少写了一处

- **现象**：代码改完 `pnpm typecheck` / `pnpm test` 全绿，起真服务时运行期
  `MODULE_NOT_FOUND`（外置包在产物目录里定位不到），或下一家进来时外置清单与依赖清单已经漂移。
- **为什么危险**：**响亮但只在运行期**（构建与单测都拦不住），且**第二处静默**：
  手写一份「厂商包清单」时漏一家不会有任何红——本仓的答案是那份清单**派生**自
  `packages/server/agents/package.json` 的 `dependencies`，不手写。
- **判据**：`runtime-deps.test.ts` 的四条（派生集合非空且不含工作区包、每一家的区间与 agents 包
  **逐字相同**、运行期说明符真解析得到、`serverExternalPackages` 与派生集合**逐项相同**）。
  例外表（`BUNDLED_DEPENDENCIES` / `RESOLUTION_FORMS`）每条例外都要在那份源码里写一行理由。
- **参考实现**：`apps/web-next/src/runtime-deps.test.ts`（文件头逐条说明四家的解析器为什么不同）+
  `apps/web-next/next.config.ts` 的 `serverExternalPackages` + 两侧 `package.json` 的
  `@earendil-works/*` / `@tintinweb/pi-subagents` 三条区间逐字相同。

## 已知边界与取舍

| 边界 | 处置 |
|---|---|
| 一致性套件的 `structured-output` 组：判据本体 `providers/conformance/structured-output.ts` 与运行时**共用** `src/structured-output.ts`；cc 与 dsh 的夹具已挂探针（请求侧事实分别取假 SDK 的 `options.outputFormat` 与首轮提示词里的输出约束），codex 的夹具是**消息级**的（造 `AppServerNotificationPayload` 喂归一函数，看不到 `turn/start` 的请求）⇒ 这一家在套件里仍空转 | 这一组判三件事：① **上报与请求互钉**——上报走了原生 schema 通道（`applied.structuredOutput`）就必须真的把 schema 发给了厂商，没走原生通道是**允许**的（填充层那条路）；② **答复可解析**——非失败场景的 `finalText` 必须过同一份判据（剥整段围栏 → `JSON.parse`），给了期望再逐字段比对；③ **失败可见**——失败场景必须带归因，空串不算答复（`finalText === ''` 是「没采到」的伪装）。codex 的请求侧事实由 `providers/codex/index.test.ts` 的 `turn/start` 两态断言（给 / 不给 `outputSchema`）守 |
| 无原生 schema 通道的家怎么过这一组 | 靠适配器内部的填充层（首轮提示词追加 schema 约束）交出 JSON，`applied.structuredOutput` 记 `false` **不算失败**——那一格回答的是**方法**，不是结果；答复仍不合格时走调用方的既有处置（不静默） |
| 前三步的缺陷单测拦不住（打包器改写、子进程环境差异——测试环境 ≠ 运行环境） | 真机冒烟是唯一拦法；这也是「为什么不写假 SDK 替代真机」的原因 |
| **真机冒烟的覆盖只有一张编译期清单，没有机器验证**：8 个 `live-*` 文件全部默认跳过，跑没跑过在代码与产物里不留痕 ⇒ `LIVE_SMOKE_COVERAGE` 只能保证「新家必须回答这个问题」，保证不了「答的是真话」 | 未闭合。要真正闭合，覆盖事实得落在产品侧能自动读到的地方（例如把「这一行是真机冒烟」记进行快照），代价是给产品加一个只为验证而存在的字段 |
| 一致性套件里有一组判据对四家**全部空转**：`transport` 那份「传输时序（C 类）」（无一家交得出笔迹）。`usage-pair` 那一组虽然四家都注册，但取值结构使不变量恒真 | 两组都保留：判据本身在 `kit.test.ts` 用合成 fixture 见过红，空转的是四家的输入而不是判据。补输入要各家夹具能录到「订阅与响应的先后」，那是各家的下一步 |
| 生命周期的**并发隔离**按形态分判据 | **子进程型**由静态层守：`process.env` 写入被 7 种写法的禁令封死，而「替换型子进程环境」是那条禁令下唯一可行的实现 ⇒ 真并行时的凭据串扰没有载体。**in-process 型**的载体正好是静态层拦不住的那一类（模块级缓存、按 id 索引的全局注册表、单例 runtime）⇒ 判据换成**运行期**：每 run 自建 runtime + 唯一 providerId + 内存凭据，用「两行同时跑、各自打到自己那台网关、各自的密钥不串」的用例钉住。代价：「从别的通道串」在子进程型上仍拦不住 |
| 性能只有**量级**声明，没有精确基线 | 由「声明驱动消费方」兜住：真机冒烟的等待预算与 ⑦ 格都按它判，声明小了会被自己的预算掐掉。**in-process 家要额外交代没有子进程冷启动**（量级记秒级，行内首次 import 的成本写进 `timing.notes`）。精确基线仍不补：把「我们自己的第一帧」当首字时延会与厂商的整轮耗时混成两把尺子、让 `mergeTiming` 整格作废 ⇒ in-process 家的 `ttftMs` 如实记 `null`。代价是「这家比那家慢 30%」这类差异判不出来——那需要 benchmark 口径，本仓没有 |
| codex 二进制解析「第二跳基准」守卫缺口：vitest 里裸说明符解析被运行器接管比生产宽松，基准改错仍绿 | 未闭合，两条闭合路径（真 Node 子进程验 / 形状式源码断言）都未做 |
